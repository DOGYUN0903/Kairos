# 프론트엔드 F3 혜택·후기 화면 설계 (C3)

> 작성일: 2026-11-12 · 빌더 체크 반영: 2026-11-12 · 상위: `2026-11-11-frontend-f1-foundation-design.md`(기반·규칙), `2026-11-12-frontend-f2-purchase-design.md`(구매 화면·멱등 키 규칙), `2026-11-10-c3-benefits-reviews-design.md`(혜택·후기 도메인 규칙) · ADR 0003·0004

## 1. 의도

F2에서 사는 흐름이 화면으로 이어졌다. F3는 그 위에 **쿠폰, 포인트, 후기, 좋아요 목록**을 얹는다. 백엔드(C3)는 이미 있다. 화면이 없어서 쿠폰을 받을 수도, 주문서에서 쓸 수도, 후기를 쓸 수도 없는 상태다.

쿠폰과 포인트는 결제 금액을 바꾼다. 그래서 F2의 기준이 그대로 적용된다: **금액은 서버가 계산한 값만 보여주고**, 쿠폰 받기·주문·후기 작성은 두 번 눌러도 한 번만 일어난다. 화면이 할인액이나 포인트 한도를 스스로 계산하면 실패다. 시연용 껍데기가 아니라 실제 쇼핑몰 수준의 완성도가 기준이다(사용자 결정).

표기: **사용자 결정**(확정) / **Claude 결정**(작성자 판단. "틀렸을 때 비용"을 적는다).

## 2. 목표, 비목표, 안티 목표

- **목표**
  - 시안 5개 작성과 사용자 확인 — **F3의 첫 작업**(§4).
  - 백엔드 보강 4건(§5, 전부 읽기 전용 응답 필드): 견적의 "적용 가능한 내 쿠폰", 주문 항목의 후기 상태, 후기 응답의 이미지 파일 ID, 쿠폰 정책 응답의 대상 상품 이름.
  - 구매자: 상품 상세의 쿠폰 받기·후기 영역, 주문서의 쿠폰·포인트 사용, 0원 결제, 마이페이지(주문 내역·쿠폰·포인트·내 후기·좋아요), 주문 상세의 후기 작성.
  - 판매자: 쿠폰 관리(등록·종료), 후기 관리(답글).
  - 관리자: 쿠폰 관리(상품·장바구니 쿠폰), 회원 포인트 조회.
  - E2E 3개, CLAUDE.md 갱신.
- **비목표**: 쿠폰 정책 수정(백엔드에 없다. 종료 후 새로 등록), 관리자의 포인트 수동 지급·차감, 후기 신고·관리자 삭제·추천, 쿠폰 코드 입력, 구매 확정 창의 예상 적립액 숫자(문구로만 안내 — 사용자 결정), 반품·정산(F4), 모바일, 데모 시더가 쿠폰·후기 데이터를 미리 만드는 것.
- **안티 목표(실패로 보는 것)**
  - 화면이 할인액·포인트 한도·결제 금액을 스스로 계산해 서버와 다른 숫자를 보여줌.
  - 쓸 수 없는 쿠폰을 고를 수 있게 보여주고 결제하기에서야 거절됨.
  - 쿠폰·포인트를 바꾼 뒤 옛 견적 금액으로 결제가 나감.
  - 쿠폰 받기·후기 작성 버튼을 두 번 눌러 두 번 처리되거나, 이미 받은 쿠폰이 오류로 보임.
  - 이미 후기를 쓴 항목에 "후기 작성" 버튼이 다시 보임.
  - 돈 계산 클래스(`DiscountAllocator`, `CouponTerms`, `RefundCalculator`)의 계산 결과가 바뀜. F3의 백엔드 변경은 조회 응답 필드 추가와, 결과가 같은 판정 함수 추출 하나(§5-1)뿐이다.

### 5-1. 견적에 "적용 가능한 내 쿠폰" (사용자 결정 + Claude 세부)

문제: 내 쿠폰 응답(`CouponResult`)에는 적용 대상 정보가 없어서, 주문서가 어떤 쿠폰을 어느 항목에 쓸 수 있는지 알 수 없다.

`POST /orders/quote` 응답 `OrderQuote`에 필드를 더한다.

- `items[].availableCoupons: QuoteCoupon[]` — 그 항목에 **대상이 맞는** 내 상품 쿠폰.
- `cartCoupons: QuoteCoupon[]` — 내 장바구니 쿠폰.
- `QuoteCoupon`: `couponId`, `name`, `issuerType`(PLATFORM/SELLER), `discountType`, `discountValue`, `maxDiscount?`, `minOrderAmount?`, `expiresAt`, `usable`(boolean), `unusableReason?`(`MIN_AMOUNT_NOT_MET` / `NOTHING_TO_DISCOUNT`), `expectedDiscount?`(쓸 수 있을 때, 이 쿠폰을 이 대상에 적용하면 깎이는 금액).

규칙:
- 목록에 넣는 쿠폰: 요청 회원의 것, `AVAILABLE`, 만료 전. 상품 쿠폰은 대상이 맞는 항목에만 넣는다(대상이 안 맞는 쿠폰은 아예 넣지 않는다). 정렬은 쓸 수 있는 것 먼저, 그 안에서 `expectedDiscount` 큰 순, 같으면 만료 빠른 순.
- `usable`과 `expectedDiscount`는 주문 생성이 쓰는 **같은 검증·계산**을 호출해 얻는다. 새 계산식을 만들지 않는다. `expectedDiscount`는 `CouponTerms.discountFor`, 대상 일치는 `appliesTo`다.
- **최소 주문 금액 판정 추출(사용자 결정, 빌더 체크 반영)**: 지금 이 비교는 `DiscountAllocator.allocate` 안에 섞여 있어 따로 부를 수 없다. 비교 한 줄을 `CouponTerms`의 함수(예: `meetsMinimum(targetAmount)`)로 빼고, `DiscountAllocator`(상품 쿠폰·장바구니 쿠폰 두 곳)와 견적의 `usable` 판정이 **같은 함수**를 부른다. 이것이 F3에서 돈 계산 클래스를 건드리는 유일한 변경이며 **계산 결과는 바뀌지 않는다**: 기존 `DiscountAllocator` 테스트를 고치지 않고 그대로 통과해야 하고, 새 함수에 경계 테스트(금액 = 최소 금액이면 충족, 1원 모자라면 미충족, 최소 금액 없음)를 더하며, `./gradlew pitest` 임계값을 지킨다. 상품 쿠폰의 대상 금액은 그 항목 `lineAmount`, 장바구니 쿠폰의 대상 금액은 **요청에 담긴 상품 쿠폰을 적용한 뒤**의 합계다(C3 스펙 §4-2). 그래서 상품 쿠폰 선택이 바뀌면 장바구니 쿠폰의 `usable`도 바뀔 수 있다.
- 상품 쿠폰으로 합계가 0원이 되면 장바구니 쿠폰은 전부 `usable=false`, 이유 `NOTHING_TO_DISCOUNT`다(주문 생성은 이 경우 `COUPON_NOT_APPLICABLE`로 거절한다). 화면 문구는 "할인할 금액이 없습니다".
- 지금 견적은 요청에 담긴 쿠폰 ID만 읽는다. 혜택 모듈에 "회원의 사용 가능한 쿠폰 전부와 조건"을 주는 조회와 포트 메서드를 더한다.
- 같은 쿠폰이 여러 항목의 목록에 나올 수 있다(전 상품 대상 쿠폰). "다른 항목에 이미 골랐다"는 표시는 화면이 자기 선택 상태로 한다(금액 계산이 아니다).
- 조회만 한다. 쿠폰 상태·포인트·재고를 바꾸지 않는다. 주문 → 혜택 호출은 기존처럼 포트를 거친다(`ArchitectureTest`).
- 테스트: C3 스펙 §6의 예시 주문으로 항목별 목록·`expectedDiscount`(b1 플랫폼 정액 2,000 / c1 판매자 10% → 4,000 / 장바구니 10% 최대 5,000 → 5,000), 최소 금액 미달 쿠폰은 `usable=false`+`MIN_AMOUNT_NOT_MET`, 남의 쿠폰·사용한 쿠폰·만료 쿠폰·대상이 다른 쿠폰은 목록에 없음, 상품 쿠폰을 적용해 합계가 최소 금액 아래로 내려가면 장바구니 쿠폰이 `usable=false`로 바뀜, 조회 뒤 쿠폰 상태가 그대로임.

틀렸을 때 비용: 견적 한 번에 내 쿠폰 조회가 더해진다(회원당 쿠폰 수는 적다). 응답 필드 추가라 기존 화면은 영향이 없다.

### 5-2. 주문 항목의 후기 상태 (사용자 결정 + Claude 세부)

문제: 주문 항목 응답에 후기 정보가 없어 "후기 작성" 버튼을 언제 보일지 알 수 없다.

구매자 주문 상세(`GET /orders/{orderId}`)의 `OrderItemResult`에 `review` 객체를 더한다.

- `review.status`: `NOT_ELIGIBLE`(구매 확정 전이거나 취소·반품된 항목) / `WRITABLE` / `WRITTEN` / `EXPIRED`(작성 기한 지남) / `DELETED`(삭제해서 다시 쓸 수 없음).
- `review.reviewId?`(`WRITTEN`일 때), `review.writableUntil?`(`WRITABLE`·`EXPIRED`일 때, 구매 확정 시각 + 작성 기한 설정값. **초 단위 시각**이다 — 후기 작성 검증이 이 시각을 초 단위로 본다).

규칙:
- 판정은 후기 작성이 쓰는 조건과 같아야 한다(확정된 판매자 주문의 `ORDERED` 항목, 기한, 항목당 한 개·삭제 포함). 작성 규칙 자체는 바꾸지 않는다.
- 주문 조회가 후기 모듈에 "이 항목 ID들의 후기 상태"를 **한 번에** 묻는 조회 포트를 둔다(주문 한 건당 조회 한 번, 항목마다 조회하지 않는다). 주문 → 후기 호출도 포트 경유.
- `OrderItemResult`는 구매자·판매자·관리자 응답이 함께 쓴다. `review`는 선택 필드로 두고 **구매자 주문 상세에서만 채운다**(판매자·관리자 응답에서는 없음).
- 포트 구현은 후기 조회 서비스를 부른다. 후기 작성 서비스(`ReviewService`)는 이미 주문 조회에 의존하므로 그쪽을 부르면 빈 순환이 생긴다.
- 테스트: 다섯 상태 각각, 기한 경계(`writableUntil` 시각까지 `WRITABLE`, 1초 뒤 `EXPIRED` — 작성 API의 판정과 같음), 삭제한 후기는 `DELETED`, 항목 여러 개 주문에서 조회 횟수가 항목 수에 비례하지 않음.

### 5-3. 후기 응답의 이미지 파일 ID (Claude 결정)

문제: 후기 수정 요청은 `imageFileIds`를 받는데 후기 응답은 `imageUrls`만 준다. 수정 화면이 기존 사진을 유지하려면 파일 ID가 필요하다.

- `ReviewResult`에 `images: [{fileId, url}]`를 더한다(상품의 `ProductImage`와 같은 모양, `imageUrls`는 그대로 둔다).
- 틀렸을 때 비용: 낮음. 필드 하나. 넣지 않으면 후기를 수정할 때마다 사진을 전부 다시 올려야 한다.

### 5-4. 쿠폰 정책 응답의 대상 상품 이름 (Claude 결정, 빌더 체크 반영)

문제: `CouponPolicyResult`에는 `targetProductId`만 있어, 쿠폰 관리 표와 쿠폰 카드가 "어느 상품 쿠폰인지"를 이름으로 보일 수 없다.

- `CouponPolicyResult`에 `targetProductName?`을 더한다(`targetType=PRODUCT`일 때. 목록 한 페이지당 상품 조회 한 번, 기존 `BenefitProductReader` 포트 확장). 상품이 삭제됐으면 null이고 화면은 "상품 #123"으로 보인다.
- 틀렸을 때 비용: 낮음. 필드 하나. 넣지 않으면 관리자 화면은 상품 번호만 보인다.

### 5-5. 하지 않는 것

쿠폰 정책 수정 API, 예상 적립 포인트 필드, 회원 검색 API, 후기 단건 조회 API, 주문 상세의 회원 ID, 인덱스 추가.

| `/checkout` (수정) | 할인·포인트 영역 추가 | 구매자 |
| `/my` | `/my/orders`로 보낸다 | 구매자 |
| `/my/orders`, `/my/orders/[orderId]` (수정) | 마이페이지 틀 안으로, 주문 상세에 후기 상태 | 구매자 |
| `/my/coupons` | 받을 수 있는 쿠폰 / 내 쿠폰 | 구매자 |
| `/my/points` | 잔액·만료 예정·내역 | 구매자 |
| `/my/reviews` | 내 후기 목록·수정·삭제 | 구매자 |
| `/my/likes` | 좋아요한 상품 | 구매자 |
| `/seller/coupons` | 쿠폰 정책 목록·등록·종료 | 승인된 판매자 |
| `/seller/reviews` | 내 상품 후기·답글 | 승인된 판매자 |
| `/admin/coupons` | 플랫폼 쿠폰 정책 목록·등록·종료 | 관리자 |
| `/admin/members/points` | 회원 ID로 포인트 조회 | 관리자 |

- **마이페이지 틀**(Claude 결정): `/my` 아래에 공용 레이아웃을 두고 왼쪽 메뉴(주문 내역, 쿠폰, 포인트, 내 후기, 좋아요)를 보인다. 결제 페이지(`/my/orders/[orderId]/pay`)와 주문 완료(`…/complete`)는 흐름 중간 화면이라 메뉴 없이 지금 모양을 유지한다(URL은 그대로 두고 라우트 그룹으로 나눈다). 틀렸을 때 비용: 레이아웃 파일 위치만 바꾸면 된다.
- 헤더의 "주문 내역" 링크는 "마이페이지"로 바꾼다(가는 곳은 같다). 판매자·관리자 콘솔 `SideNav`에 새 메뉴를 더한다.

## 7. 주문서의 쿠폰·포인트 (사용자 결정 + Claude 세부)

F2 주문서(F2 스펙 §8-3)에 "할인·포인트" 영역을 더한다. 배송지·결제하기 흐름과 멱등 키 규칙은 그대로다.

### 7-1. 견적이 유일한 진실

- 주문서 상태는 **선택**(항목별 상품 쿠폰 ID, 장바구니 쿠폰 ID, 사용할 포인트)과 **그 선택으로 받은 견적** 두 가지다. 화면의 모든 숫자(할인액, 항목별 금액, 결제 금액, 포인트 최대치, 쿠폰별 예상 할인)는 견적 응답 값이다.
- 선택이 바뀔 때마다 `POST /orders/quote`를 다시 부른다. 포인트 입력은 입력이 멈춘 뒤(지연 시간은 빌더) 부른다.
- **견적을 기다리는 동안과 견적이 실패한 상태에서는 결제하기를 막는다.** 결제하기는 화면에 보이는 견적의 `totalAmount`를 `expectedTotalAmount`로, 그 견적을 만든 선택을 `productCoupons`·`cartCouponId`·`pointsToUse`로 보낸다. 늦게 도착한 옛 견적 응답은 버린다(마지막 요청만 반영).
- 금액 요약: 상품 금액, 상품 쿠폰 할인, 장바구니 쿠폰 할인, 포인트 사용, 배송비, **결제 금액**. 할인 줄은 0이 아닐 때만 보인다.
- 무료배송은 할인 전 상품 금액 기준이다(C3 스펙 §4-3). 쿠폰을 써도 배송비 줄은 바뀌지 않는다 — 화면이 따로 할 일은 없고 서버 값을 그대로 보인다.

### 7-2. 쿠폰 선택

- **상품 쿠폰**: 주문 상품 줄마다 `availableCoupons`가 있으면 "쿠폰 선택" 버튼(쓸 수 있는 장수 표시), 없으면 아무것도 보이지 않는다. 누르면 선택 창: 쓸 수 있는 쿠폰(이름, 할인 조건, 만료일, `expectedDiscount` "−2,000원")과 쓸 수 없는 쿠폰(흐리게, 이유 "30,000원 이상 구매 시 사용 가능"), 그리고 "적용 안 함". 한 항목에 한 장.
- 다른 항목에 이미 고른 쿠폰은 "다른 상품에 적용됨"으로 표시하고, 고르면 **이쪽으로 옮긴다**(이전 항목에서는 해제 — Claude 결정. 틀렸을 때 비용: 낮음, 고를 수 없게 막는 쪽으로 바꾸면 된다).
- **장바구니 쿠폰**: 영역에 한 줄. `cartCoupons`가 비면 "사용 가능한 쿠폰이 없습니다". 선택 창 구조는 같다. 주문에 한 장.
- 자동 적용은 하지 않는다(Claude 결정: 처음에는 아무 쿠폰도 고르지 않은 상태. 틀렸을 때 비용: 낮음 — 실제 쇼핑몰은 최대 할인을 자동으로 골라 주기도 하지만, 조합 최적화는 서버 규칙이 필요하다. 대신 쓸 수 있는 쿠폰 장수를 눈에 띄게 보인다).
- 선택한 쿠폰이 더는 쓸 수 없게 되면(견적이 400 `COUPON_MIN_AMOUNT_NOT_MET`·`COUPON_NOT_APPLICABLE`, 409 `COUPON_NOT_AVAILABLE`, 404 `COUPON_NOT_FOUND`): **방금 바꾼 선택을 되돌리고**(직전에 성공한 선택으로) 서버 메시지를 토스트로 알린다. 직전 선택도 실패하면 쿠폰·포인트를 모두 비우고 다시 견적한다.

### 7-3. 포인트

- `GET /points/me`의 잔액을 "보유 12,300P"로 보인다. 입력 칸 + "최대 사용" 버튼.
- "최대 사용"은 견적의 `maxUsablePoints`를 넣는다(서버가 잔액·30% 상한·10P 단위를 모두 반영한 값이다). 화면은 한도를 계산하지 않는다.
- 쓸 수 없는 경우 입력을 막고 이유를 보인다: 잔액이 1,000P 미만("1,000P 이상 보유 시 사용할 수 있습니다" — 기준 숫자는 서버 메시지·`maxUsablePoints`가 0인 것으로 판단하고 문구에만 쓴다), `maxUsablePoints`가 0.
- 입력 검증(화면): 숫자만, 0 이상, 10의 배수(`money.ts`의 `mod`), `maxUsablePoints` 이하. 어기면 견적을 부르지 않고 칸 아래에 안내한다("10P 단위로 입력해 주세요", "최대 17,700P까지 사용할 수 있습니다").
- **쿠폰을 바꾸면 한도가 바뀐다.** 쿠폰 변경 견적이 `POINT_EXCEEDS_LIMIT`·`POINT_INSUFFICIENT`·`POINT_INVALID_AMOUNT`로 실패하면 포인트를 0으로 되돌려 다시 견적하고 "쿠폰이 바뀌어 포인트 사용을 초기화했습니다"를 알린다(Claude 결정. 틀렸을 때 비용: 낮음 — 새 한도로 자동 맞춤으로 바꿀 수 있다).

### 7-4. 결제하기와 0원 결제

- 주문 생성 오류에 혜택 코드가 더해진다. 전부 **자동 재제출 없음**, 다음 제출은 새 키(F2 규칙).

| 코드 | 화면 |
|---|---|
| 409 `ORDER_PRICE_CHANGED` | F2 그대로(견적 다시, 금액 변경 안내). 쿠폰·포인트 선택은 유지해 다시 견적하고, 그 견적이 실패하면 §7-2·§7-3 규칙으로 비운다 |
| 409 `COUPON_NOT_AVAILABLE`, 404 `COUPON_NOT_FOUND`, 400 `COUPON_NOT_APPLICABLE`·`COUPON_MIN_AMOUNT_NOT_MET` | 쿠폰 선택을 모두 비우고 다시 견적 + "쿠폰을 사용할 수 없습니다. 다시 선택해 주세요" |
| 409 `POINT_INSUFFICIENT`, 400 `POINT_EXCEEDS_LIMIT`·`POINT_INVALID_AMOUNT` | 포인트를 0으로, 잔액·견적 다시 + 안내 |

- **0원 결제**(사용자 결정): `totalAmount`가 0이면(빌더 체크 반영: 포인트는 쿠폰 적용 후 금액의 30%까지라 포인트로는 0원이 되지 않는다. **쿠폰이 상품 금액 전부를 덮고 배송비가 0원일 때만** 생긴다. 이때 `maxUsablePoints`는 0이라 포인트 입력은 막힌다) 서버가 PG 없이 바로 결제를 끝낸다. 버튼 문구는 "0원 결제하기"가 아니라 "주문하기"로 바꾸고, 주문 생성 응답의 `orderStatus`가 `PAID`면 결제 페이지를 거치지 않고 **주문 완료로 교체 이동**한다. 응답이 `PENDING_PAYMENT`인데 `totalAmount`가 0인 경우(서버가 승인 확정 전에 멈춘 드문 경우)는 주문 상세로 보내고, 상세의 기존 재조회·만료 안내에 맡긴다. 결제 페이지는 `totalAmount`가 0인 주문에 결제창을 열지 않는다(`pay-state.ts`의 `canPay`에 조건 추가). `PAID` 응답을 주문 완료로 보내는 분기는 F2의 `afterOrderHref`에 이미 있다.
- 주문 성공 뒤 무효화: 장바구니·주문(F2) + 내 쿠폰·포인트.

### 7-5. 주문 상세·취소에 보이는 혜택

- 결제 요약의 쿠폰·포인트 줄은 F2에서 "0이 아닐 때만" 이미 보인다. F3에서 문구와 순서를 시안에 맞춘다: 상품 쿠폰 할인, 장바구니 쿠폰 할인, 포인트 사용, 되돌려받은 포인트(`pointsRefunded`).
- 항목 취소 창(F2 `ItemCancelDialog`)은 환불 미리보기 금액만 보인다. 여기에 안내 문구를 더한다: 그 항목에 `pointsAllocated`가 있으면 "사용한 포인트 5,625P가 함께 돌아옵니다"(서버 값 그대로), `productCouponId`가 있으면 "사용한 상품 쿠폰은 유효기간이 남아 있으면 돌아옵니다". 장바구니 쿠폰은 "주문 전체를 취소해야 돌아옵니다"(주문에 `cartCouponId`가 있을 때만).
- 취소 뒤 무효화에 내 쿠폰·포인트를 더한다.

## 8. 구매자 화면

### 8-1. 상품 상세 — 쿠폰 받기

- `GET /coupons/policies?productId=`(로그인 상태에서만 부른다. 비로그인은 영역에 "로그인하고 쿠폰 받기" 링크, `next`로 돌아온다 — 이 API는 인증이 필요하다).
- 쿠폰 카드: 이름, 할인("3,000원" / "10% (최대 5,000원)"), 조건("30,000원 이상 구매 시"), 발급 주체 표시(판매자 쿠폰 / 플랫폼 쿠폰), 종류(상품 쿠폰 / 장바구니 쿠폰), 기간. `claimed`면 "받음"(비활성).
- 받기: `useIdempotentAction`으로 `POST /coupons/policies/{id}/claim`. 성공 → 토스트("쿠폰을 받았습니다. ○월 ○일까지 사용할 수 있습니다" — `expiresAt` 서버 값), 정책 목록·내 쿠폰 무효화.
- 오류: 409 `COUPON_ALREADY_ISSUED` → 오류가 아니라 "이미 받은 쿠폰입니다" 안내 후 목록을 다시 읽어 "받음"으로. 409 `COUPON_SOLD_OUT` → "쿠폰이 모두 소진되었습니다" + 목록 다시. 409 `COUPON_POLICY_ENDED` → "종료된 쿠폰입니다" + 목록 다시.
- 수량이 소진되거나 종료된 정책은 서버 목록에서 빠진다. 그래서 마지막 한 장을 받으면 다시 읽은 목록에서 카드가 "받음"이 아니라 **사라질 수 있다** — 정상 동작으로 본다(받은 쿠폰은 내 쿠폰에 있다).
- 상품 하나 대상 쿠폰은 카드에 대상 상품 이름을 보인다(§5-4).
- 정책이 없으면 영역을 숨긴다. 4장 넘으면 "쿠폰 모두 보기" 창(개수 기준은 시안에서).

### 8-2. 상품 상세 — 후기

- 상단 요약: 평균 별점(`averageRating`, 서버 값)·후기 수(`reviewCount`). 후기가 0개면 별점 숫자 대신 "아직 후기가 없습니다".
- 목록 `GET /products/{id}/reviews?page&size`(최신순, 인증 불필요): 별점, 작성자(`writerName` 마스킹 값 그대로), 작성일, 본문, 사진(누르면 크게 보기), 판매자 답글(있으면 들여쓴 상자에 답글·답글일).
- 페이지는 후기 영역 안에서만 넘긴다(Claude 결정: URL 쿼리 `reviewPage`. 페이지를 넘겨도 화면 맨 위로 튀지 않게 한다).
- 별점 표시는 채운 별 5개(정수 별점)와, 평균은 숫자 + 별(반올림 표시 규칙은 시안에서. 평균 숫자는 서버 값 그대로 한 자리).

### 8-3. 마이페이지 — 쿠폰 `/my/coupons`

- 탭 2개(URL 쿼리 `tab`): **받을 수 있는 쿠폰**(`GET /coupons/policies`, 상품 쿠폰 중 전 상품 대상과 장바구니 쿠폰이 온다. 받기 동작은 §8-1과 같은 컴포넌트) / **내 쿠폰**(`GET /coupons/me?status=`).
- 내 쿠폰 필터(URL 쿼리 `status`): 사용 가능(기본) / 사용 완료 / 기간 만료. 카드: 이름, 종류, 할인, 조건, 만료일. 사용 완료는 사용일과 "주문 보기"(`usedOrderId` → 주문 상세). 만료 7일 이내인 사용 가능 쿠폰은 "곧 만료" 표시(날짜 비교는 `lib/datetime.ts`, KST 기준).
- 내 쿠폰에는 적용 대상 정보가 없다. 카드에 대상 상품을 쓰지 않는다(주문서에서 쓸 수 있는 쿠폰이 자동으로 보인다는 안내 한 줄).

### 8-4. 마이페이지 — 포인트 `/my/points`

- 상단: 보유 포인트(`balance`), 30일 안에 만료 예정(`expiringWithin30Days`, 0이면 숨김), 안내("1,000P 이상 보유 시 10P 단위로, 상품 금액의 30%까지 사용" — 문구).
- 내역 `GET /points/me/transactions?page&size`: 일시, 내용, 변동(+214P / −10,000P, 부호와 색), 잔액(`balanceAfter`).
- 내용 문구(유형 → 문구): `EARN_PURCHASE` 구매 확정 적립 / `EARN_REVIEW` 후기 작성 적립 / `USE` 주문 사용 / `REFUND` 주문 취소 환급 / `EXPIRE` 기간 만료. `refType`이 `ORDER`면 "주문 보기" 링크(`refId` = 주문 ID). 다른 `refType`은 주문 ID를 알 수 없어 링크를 두지 않는다.

### 8-5. 주문 상세 — 후기 상태와 작성

구매 확정된 판매자 주문의 항목 줄에 `review.status`에 따라(§5-2):

| 상태 | 화면 |
|---|---|
| `WRITABLE` | "후기 작성" 버튼 + "○월 ○일 ○○:○○까지 작성 가능"(`writableUntil`, 시각까지 보인다) |
| `WRITTEN` | "내 후기 보기" → `/my/reviews`(목록 첫 페이지. 후기 단건 조회 API가 없어 특정 후기로 바로 가지는 않는다 — Claude 결정, 틀렸을 때 비용: 낮음) |
| `EXPIRED` | 버튼 없음, "후기 작성 기한이 지났습니다" |
| `DELETED` | 버튼 없음, "삭제한 후기는 다시 작성할 수 없습니다" |
| `NOT_ELIGIBLE` | 아무것도 보이지 않음 |

- 구매 확정 확인 창에 "구매 확정 시 결제 금액의 1%가 포인트로 적립됩니다"를 더하고(숫자 없음 — 사용자 결정), 확정 성공 토스트에 "포인트 내역 보기" 링크를 둔다. 확정 뒤 포인트 무효화.
- **후기 작성 창**: 상품 요약(이미지·이름·옵션), 별점 1~5(필수, 키보드로도 고를 수 있게), 본문(앞뒤 공백 뺀 길이 10~1,000자, 글자 수 표시), 사진 최대 3장, 적립 안내("글 후기 100P, 사진 후기 500P. 작성 후 사진을 추가해도 추가 적립은 없습니다").
  - 사진: `features/files`의 업로드(jpg·png·webp, 5MB 이하 — 화면에서 먼저 걸러 안내). 올리는 동안 제출을 막는다. 올린 사진은 미리보기와 삭제.
  - 제출: `useIdempotentSubmit`으로 `POST /orders/{orderId}/items/{orderItemId}/reviews`. 성공 → 토스트("후기를 등록했습니다. 500P가 적립되었습니다" — `rewardPoints` 서버 값), 주문 상세·내 후기·포인트·상품 후기 무효화.
  - 오류: 409 `REVIEW_ALREADY_WRITTEN`·`REVIEW_NOT_ELIGIBLE` → 창을 닫고 서버 메시지 토스트 + 주문 상세 다시 읽기. 400 `REVIEW_INVALID` → 폼 상단.

### 8-6. 마이페이지 — 내 후기 `/my/reviews`

- `GET /reviews/me?page&size`: 상품(이름 → 상품 상세 링크), 별점, 본문, 사진, 작성일(수정했으면 "수정됨"), 적립 포인트, 판매자 답글.
- **수정**: 작성 창과 같은 폼에 기존 값(사진은 `images`의 `fileId`로 유지 — §5-3). `PATCH /reviews/{id}`(키 없음, 이중 제출 가드). 적립 안내 대신 "수정해도 추가 적립은 없습니다".
- **삭제**: 확인 창("삭제하면 이 상품에 후기를 다시 쓸 수 없고, 적립된 포인트는 회수되지 않습니다") 뒤 `DELETE /reviews/{id}`. 404 `REVIEW_NOT_FOUND`는 이미 삭제된 것으로 보고 목록을 다시 읽는다.
- 빈 상태: "작성한 후기가 없습니다" + 주문 내역 링크.

### 8-7. 마이페이지 — 좋아요 `/my/likes`

- `GET /products/me/likes?page&size`: F1 상품 카드 격자. `productStatus`가 판매 중이 아니면 카드를 흐리게 하고 "판매 종료" 표시(링크는 유지 — 상세가 404면 F1의 없음 페이지).
- 카드의 하트로 좋아요 취소(`DELETE /products/{id}/like`, F1 `LikeButton` 동작 재사용) → 목록 다시 읽기.
- `LikedProduct`에는 정가·할인율이 없다. 카드는 판매가만 보인다.

## 9. 판매자 화면

### 9-1. 쿠폰 관리 `/seller/coupons`

- 목록 `GET /seller/coupons/policies`: 이름, 대상(내 상품 전체 / 상품 하나 — `targetProductName`, §5-4), 할인, 최소 주문 금액, 발급 수/총 수량(무제한이면 "제한 없음"), 기간, 상태(진행 중 / 종료). 기간이 지났지만 `ACTIVE`인 정책은 "기간 종료"로 보인다(날짜 비교).
- **등록 양식**(react-hook-form + zod, OpenAPI `CreateCouponPolicyRequest` 제약과 같게), `useIdempotentSubmit`으로 `POST /seller/coupons/policies`:
  - 이름(1~50자)
  - 대상: 내 상품 전체(`SELLER`) / 상품 하나(`PRODUCT` — 내 상품 목록에서 고른다)
  - 할인 유형: 정액(원, 1 이상) / 정률(**%로 입력받아 bp로 보낸다**: 1~100의 정수 → ×100. Claude 결정. 소수 %는 받지 않는다. 틀렸을 때 비용: 낮음) + 최대 할인 금액(정률이면 필수)
  - 최소 주문 금액(선택), 총 수량(선택, 비우면 무제한), 유효 일수(선택, 비우면 종료일까지)
  - 발급 기간 시작·종료(KST 일시)
  - 화면 검증: 정률이면 최대 할인 필수, 종료가 시작보다 뒤, 금액·수량은 양의 정수. 종류는 `PRODUCT` 고정이라 묻지 않는다.
  - 안내: "등록한 쿠폰은 수정할 수 없습니다. 잘못 등록했으면 종료하고 새로 등록해 주세요. 종료해도 이미 받은 고객은 사용할 수 있습니다." 그리고 "판매자 쿠폰 할인은 판매자가 부담합니다(정산 금액에서 차감)".
  - 400 `COUPON_POLICY_INVALID` → 폼 상단.
- **종료**: 확인 창 뒤 `PATCH …/end`(키 없음, 이미 종료면 200).

### 9-2. 후기 관리 `/seller/reviews`

- `GET /seller/reviews?page&size`(최신순): 상품, 별점, 작성자(마스킹), 본문, 사진, 작성일, 답글 상태.
- **답글**: 줄을 펴서 입력(1~500자, 공백만은 안 됨). `PATCH /seller/reviews/{id}/reply`(덮어쓰기, 키 없음). 이미 답글이 있으면 "답글 수정". 답글 삭제는 없다(API에 없다).
- 필터는 두지 않는다(API에 없다). 답글 없는 후기는 "미답변" 표시로 눈에 띄게만 한다.

## 10. 관리자 화면

### 10-1. 쿠폰 관리 `/admin/coupons`

- 판매자 쿠폰 관리와 같은 목록·양식 컴포넌트를 쓴다. 차이: 종류를 고른다 — 상품 쿠폰(대상: 전 상품 `ALL_PRODUCTS` / 상품 하나 `PRODUCT`, 상품 ID 직접 입력) / 장바구니 쿠폰(`CART`, 대상 `NONE`). 안내 문구는 "플랫폼 쿠폰 할인은 플랫폼이 부담합니다".
- `GET`·`POST /admin/coupons/policies`, `PATCH …/end`.

### 10-2. 회원 포인트 조회 `/admin/members/points`

- 회원 ID 입력(URL 쿼리 `memberId`, `parseId`로 검증) → `GET /admin/members/{memberId}/points`: 잔액, 만료 예정, 내역 표(구매자 포인트 내역과 같은 표 컴포넌트).

- 관리자 주문 상세에는 회원 ID가 없다. 링크는 두지 않고 직접 입력만 한다(관리자 주문 목록의 회원 ID 검색 값과 같은 번호다).
- 읽기 전용이다.

## 11. 프론트 구조와 공통 규칙

- 디렉터리(Claude 결정): `features/coupons`(받기·내 쿠폰·카드·할인 문구), `features/points`, `features/reviews`(작성·수정 폼, 목록, 별점), `features/likes`(목록), `features/mypage`(틀·메뉴), `features/seller/coupons`·`features/seller/reviews`, `features/admin/coupons`·`features/admin/points`. 주문서의 할인·포인트 영역은 `features/checkout` 안에 둔다. 쿠폰 정책 양식은 판매자·관리자가 공유한다.
- **금액·포인트**: 화면의 할인액, 예상 할인, 포인트 한도, 결제 금액, 적립 포인트는 전부 서버 값이다. F3에서 프론트가 하는 계산은 두 가지뿐이다 — 포인트 입력이 10의 배수인지(`mod`), 정률 %를 bp로 바꾸기(×100, 곱셈). bp를 %로 보여줄 때는 `money.ts`에 표시 함수(`floorDiv` 사용, 나누어떨어지지 않는 bp는 소수 표시 규칙 포함)를 두고 단위 테스트한다. `/`와 `%`는 여전히 `money.ts`에서만 쓴다.
- **할인 문구**는 한 함수에서 만든다(정액 "3,000원 할인" / 정률 "10% 할인 (최대 5,000원)" / 조건 "30,000원 이상 구매 시"). 쿠폰 카드·선택 창·관리 표가 같은 함수를 쓴다.
- **멱등성**: 서버가 키를 강제하는 요청 — 쿠폰 받기, 쿠폰 정책 등록(판매자·관리자), 후기 작성, 주문 생성 — 은 F2 키 규칙 그대로 `useIdempotentSubmit`/`useIdempotentAction`으로 보낸다. 후기 수정·삭제, 답글, 정책 종료, 좋아요는 키 없이 이중 제출 가드와 서버의 멱등 처리에 기댄다.
- **에러**: 새 코드를 `errors.ts` 표에 넣는다. 화면 동작이 따로 정해진 코드(§7-2~§7-4, §8-1, §8-5)는 그 동작으로, 나머지는 서버 메시지 토스트(F1 규칙).
- **쿼리 키**: `couponPolicies`(상품별 포함), `myCoupons`, `points`(요약·내역), `productReviews`, `myReviews`, `likes`, `sellerCouponPolicies`, `sellerReviews`, `adminCouponPolicies`, `adminMemberPoints`. 무효화는 각 절에 적은 대로.
- **상태 칩**: 쿠폰 상태(사용 가능·사용 완료·기간 만료), 정책 상태(진행 중·종료·기간 종료), 답글 상태(미답변)를 `StatusChip`에 더한다.
- **일시**: 서버의 KST 문자열을 `lib/datetime.ts`로만 다룬다. "곧 만료"·"기간 종료" 비교와 정책 기간 입력값(KST LocalDateTime 문자열로 보냄) 변환 함수를 여기에 더하고 테스트한다.
- **접근성**: 별점 입력은 라디오 그룹(방향키), 쿠폰 선택 창은 라디오 목록, 사진 삭제 버튼에 이름. F1 §13 기본 규칙 유지.

## 13. 테스트

- **백엔드**: §5 네 건에 통합 테스트 + `OpenApiContractTest`. §5-1은 C3 스펙 §6 예시 숫자를 그대로 넣는다. 돈 계산 클래스 변경은 §5-1의 판정 함수 추출 하나뿐이다(기존 금액 테스트 무수정 통과 + PIT). 그 밖에 바꿔야 하면 멈추고 사용자에게 올린다. `ArchitectureTest` 통과.
- **프론트 단위(Vitest, 이름은 한국어)**: 할인 문구 함수, bp ↔ % 변환(경계 1%, 100%, 나누어떨어지지 않는 bp), 포인트 입력 검증(10의 배수, 한도 초과, 0), 주문서 선택 상태 전이(쿠폰 옮기기, 견적 실패 시 직전 선택으로 되돌리기, 쿠폰 변경으로 포인트 초기화, 늦은 견적 응답 버리기), 견적 대기·실패 중 결제하기 차단, 0원 주문 응답 → 이동할 화면, 후기 상태 → 표시, 후기 폼 스키마(공백 뺀 10자, 사진 3장, 파일 형식·크기), 쿠폰 정책 스키마(정률이면 최대 할인 필수, 기간 역전, 대상별 필수값), 포인트 유형 → 문구, "곧 만료"·"기간 종료" 판정(KST 경계).
- **E2E(Playwright, 실제 백엔드 `local,demo` + Mock PG, 데모가 아닌 빌드)**: 각 spec은 고유 계정·판매자·상품을 스스로 만든다(`e2e/fixtures/api.ts` 확장 — 쿠폰 정책 등록, 포인트를 얻기 위한 주문·확정·후기 헬퍼). 금액은 `toHaveText`로 정확히 비교한다.
  1. `c3-coupon-checkout.spec`: 관리자가 장바구니 쿠폰·판매자가 상품 쿠폰 등록 → 구매자가 상품 상세에서 받기(연타해도 한 장, 다시 열면 "받음") → (정책 수량은 무제한으로 만든다 — 소진되면 목록에서 빠진다) 주문서에서 상품 쿠폰·장바구니 쿠폰 선택 → 금액 요약의 할인 줄과 결제 금액이 기대 숫자와 일치 → 최소 금액 미달 쿠폰은 고를 수 없고 이유가 보임 → 결제 → 주문 상세 결제 요약에 같은 할인 → 내 쿠폰에서 "사용 완료" → 항목 취소 → 상품 쿠폰이 "사용 가능"으로 돌아옴. 그리고 **0원 결제**: 5만 원 이상 상품 한 개(무료배송)에 그 금액 이상의 정액 상품 쿠폰을 쓰면 버튼이 "주문하기"로 바뀌고 포인트 입력이 막히며, 결제창 없이 주문 완료로 간다.
  2. `c3-points.spec`: 포인트를 가진 구매자(1,000P 이상이 필요하다: 5만 원 이상 주문 확정 1% + 사진 후기 500P)가 주문서에서 "최대 사용" → 입력 칸 값이 서버 한도와 같고 결제 금액이 줄어듦 → 10P 단위가 아닌 값은 안내가 뜨고 견적이 나가지 않음 → 결제 → 포인트 내역에 사용 줄 → 항목 취소 → 환급 줄.
  3. `c3-review.spec`: 주문 → 발송 → 배송 완료 → 구매 확정 → 주문 상세에 "후기 작성" → 사진 1장 후기 작성 → "500P가 적립되었습니다" → 주문 상세가 "내 후기 보기"로 바뀜 → 상품 상세 후기 수 1·평균 별점 → 판매자 답글 → 상품 상세에 답글 → 구매자 수정(사진 유지) → 삭제 → 주문 상세 "다시 작성할 수 없습니다", 상품 후기 수 0. 좋아요한 상품이 `/my/likes`에 보이고 취소하면 사라지는 것도 여기서 확인한다.
- **수동 점검**(완료 기준에 기록): 시안과 화면 대조(5개), 데모 빌드에서 관리자 → 구매자 → 판매자 흐름 한 번.
- **CI**: F1 워크플로 그대로. E2E는 로컬에서 PR 전에 돌린다(임시 스키마 사용 — F2에서 한 방식).

## 15. 빌더에게 맡기는 것

- `features/` 안의 파일 분할, 쿼리 키 이름, 스켈레톤 모양, 포인트 입력의 견적 지연 시간.
- 주문서 선택 상태를 담는 구조(리듀서·훅)와 늦은 응답을 버리는 구현.
- `QuoteCoupon`·`review` 필드의 정확한 스키마 이름, 일괄 조회 포트의 위치와 쿼리 형태(인덱스 추가 금지 규율 안에서).
- 사진 크게 보기의 형태, 별점 컴포넌트의 모양, 쿠폰 "모두 보기"의 기준 개수.
- 판매자 쿠폰 양식의 "상품 하나" 선택 UI(내 상품 목록 API 재사용).
- E2E 픽스처 구조와 사례의 구체 숫자.

## 16. 이후

F4(반품·정산)에서 주문 상세에 반품 버튼, 판매자 콘솔에 정산 화면이 붙는다. 판매자 쿠폰의 부담액이 정산에 어떻게 보이는지는 F4에서 다룬다.
