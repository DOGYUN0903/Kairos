# C2 구매 설계

## 1. 의도

C1에서 올린 상품을 실제로 살 수 있게 한다. 장바구니 → 주문 → 결제 → 배송 상태 → 구매 확정까지 이어지고, 판매자가 여러 명인 주문과 상품별 취소를 지원한다.
이 프로젝트의 한 문장 목표(데이터 정합성)에 맞게, **돈과 재고가 어긋나지 않는 것**을 가장 중요하게 본다. 결제가 두 번 승인되거나, 환불액이 틀리거나, 재고가 사라지거나 늘어나면 기능이 동작해도 실패다.

## 2. 목표와 비목표

- 목표: 장바구니, 다중 판매자 주문, 결제(토스페이먼츠 테스트 모드 + Mock PG), 결제 대기 정리, 상품별 취소와 부분 환불, 배송 상태, 구매 확정, 판매량 증감.
- 비목표: 쿠폰과 포인트(C3), 정산 집계(C4), 반품과 교환(로드맵 5장), 택배 접수(송장 발급·픽업), 실제 결제(라이브 키), 비로그인 장바구니.
- 실패로 보는 것(안티 목표): 같은 결제가 두 번 승인됨, 환불 합계가 결제 금액을 넘음, 취소했는데 재고나 판매량이 안 돌아옴, 다른 판매자의 정산 금액이 바뀜.

## 3. 주문 구조 (사용자 결정)

- 사용자는 한 번 결제하고 **주문 하나**를 본다(예: 주문번호 1001).
- 주문 안에 판매자별 묶음(이하 **판매자 주문**)이 있다. 판매자는 자기 판매자 주문만 보고 배송한다.
- 판매자 주문 안에 주문 항목(SKU, 수량)이 있다. 취소는 **주문 항목 단위**로 한다.
- 주문 항목에는 C1 13장의 인수 조건대로 주문 시점 값을 복사한다: 상품명, 브랜드명, 옵션 표시명, 판매가, 추가 금액, 판매자 ID, 판매자 수수료율.

## 4. 배송비 (사용자 결정)

- **무료배송 기준은 플랫폼 전체에 하나**: 구매자의 주문 상품 금액 합계가 5만 원 이상이면 무료배송. 기준 금액과 기본 배송비(3,000원)는 설정값으로 둔다.
- 배송비는 **판매자 주문마다** 생긴다(판매자마다 따로 보내므로).
- 무료배송이면 그 배송비는 **플랫폼이 부담**한다. 아니면 구매자가 낸다.
- 판매자 주문에는 배송비 금액과 **누가 냈는지**(구매자/플랫폼)를 기록한다. C4 정산은 판매자에게 "상품 금액 + 배송한 판매자 주문의 배송비"를 준다. 누가 냈는지는 판매자 정산에 영향이 없다.

## 5. 취소와 환불 (사용자 결정 + 작성자 판단)

- 취소는 판매자가 **배송을 시작하기 전**까지만, 주문 항목 단위로 가능하다. 배송 후 반품은 C2 범위 밖이다.
- 한 판매자 주문의 항목이 **모두** 취소되면 그 판매자 주문은 배송하지 않으므로 배송비가 사라진다(판매자 몫 0원).
- 취소 후 남은 상품 금액 합계가 무료배송 기준 아래로 떨어지면, **기본 배송비 1회분(3,000원)을 환불액에서 뺀다**(사용자 결정, 빌더 검토 후 수정 2026-11-09). 차감액은 그 취소의 환불 대상 금액을 넘지 않는다(환불액 ≥ 0). 한 주문에서 이 차감은 **한 번만** 일어난다.
  - 남은 판매자 주문들의 배송비는 계속 플랫폼 부담으로 기록하고, 구매자 차감액은 **플랫폼 배송비 부담을 줄이는 회수금**으로 주문에 기록한다. 판매자 정산(상품 금액 + 배송한 판매자 주문의 배송비)은 어떤 경우에도 바뀌지 않는다.
  - 처음 방식(남은 판매자 주문 배송비 전부 전환)은 판매자가 많을 때 환불액이 음수가 되어 버렸다.
- 예시(사용자와 확인): B 3만 원 + C 3만 원 = 6만 원, 무료배송. C 항목 취소 → 남은 금액 3만 원 → 환불 30,000 − 3,000 = 27,000원. B 정산은 30,000 + 3,000 그대로, C는 0원. 플랫폼은 B 배송비 3,000원을 부담하고 구매자 차감 3,000원을 회수해 순부담 0원.
- 반대로 이미 구매자가 배송비를 낸 판매자 주문이 전부 취소되면 그 배송비도 환불한다.
- 환불 금액 계산은 **한 곳(도메인 함수)** 에서만 한다. 불변식: 0 ≤ 각 환불액, 누적 환불액 ≤ 결제 금액, 그리고 (결제 금액 − 누적 환불액) = 남은 상품 금액 + 구매자가 낸 배송비(결제 시 낸 것 중 남은 것 + 취소 차감액).
- 환불은 PG 부분 취소 API로 한다.

### 취소 처리 순서와 주체 (작성자 판단, 빌더 검토 반영)

- 취소는 항목을 `CANCEL_REQUESTED`로 바꾼 뒤 트랜잭션 밖에서 PG 부분 취소를 호출한다. 성공하면 `CANCELED` 확정, 재고 복구, 판매량 감소를 한 트랜잭션에서 한다. 결과가 불확실하면 그대로 두고, 정리 작업이 PG 조회로 실제 결과를 확인해 맞춘다. 같은 항목 재취소 요청은 멱등 처리.
- 취소 주체: 구매자, 판매자(배송 전, 재고 착오 등), 관리자. 판매자·관리자 취소는 판매자 귀책으로 보고 배송비 차감 없이 전액 환불하며, 무료배송이 깨져도 차이는 플랫폼이 부담한다. 취소 사유를 기록한다.

## 6. 재고 (작성자 판단)

- **주문 생성(결제 대기 진입) 시 재고를 차감**하고, 15분 안에 결제 승인이 없으면 정리 작업이 주문을 취소하고 재고를 되돌린다. 15분은 설정값.
- 차감은 SKU별 조건부 UPDATE(`stock >= 수량`)로 한다. 여러 SKU를 한 트랜잭션에서 차감하고 하나라도 실패하면 전부 롤백한다. 데드락을 줄이려고 SKU ID 오름차순으로 차감한다.
  - Phase 1의 "락 금지" 규칙은 핫딜 기준선 측정용이었다. 일반 구매는 정합성이 우선이라 C2에서는 조건부 UPDATE를 쓴다. 핫딜 트래픽에서의 방식 비교(조건부 UPDATE vs 비관적 락 vs Redis)는 Phase 3-1에서 한다.
- 취소되면 재고를 되돌린다. 단종(`DISCONTINUED`) SKU여도 재고 숫자는 되돌린다.
- 주문 생성 트랜잭션에서 order가 catalog의 재고를 함께 바꾸는 것은 "애그리거트당 한 트랜잭션"의 예외다. ADR로 남긴다. catalog application에 조건부 차감·복구·판매량 증감 포트를 추가하고, 구현은 Product 애그리거트를 로드하지 않고 바로 UPDATE할 수 있다.

## 7. 결제 (작성자 판단, 사용자 확인)

- `PgClient` 인터페이스 하나에 토스페이먼츠 테스트 모드 구현과 Mock PG 구현을 둔다. 설정으로 고른다. 테스트와 부하 측정은 Mock PG.
- 흐름: 주문 생성(결제 대기, 재고 차감) → 클라이언트가 토스 결제창 → 성공 리다이렉트 → 서버가 **결제 승인 API** 호출(paymentKey, orderId, amount) → 금액이 주문 금액과 같은지 확인 → 승인.
- 금액이 다르면 승인하지 않는다.
- 승인 요청이 늦게 와서 이미 정리 작업이 주문을 취소했다면 승인하지 않는다. PG에서 이미 승인된 상태라면 즉시 결제 취소를 호출한다.
- 승인 시작 시 결제를 `IN_PROGRESS`로 선점한다. 정리 작업은 `IN_PROGRESS`/`UNKNOWN` 결제의 주문을 만료 취소하지 않고 PG 조회로 먼저 확정한다.
- PG 호출 실패나 타임아웃: 승인 결과가 불확실하면 결제를 "확인 필요" 상태로 두고, 정리 작업이 PG 조회 API로 실제 상태를 확인해 맞춘다.
- 기존 Phase 1 규칙(주문 트랜잭션 안 동기 PG 호출)은 핫딜 측정용이다. C2에서는 PG 호출을 DB 트랜잭션 밖에서 한다. 결제 분리(Saga)는 Phase 4.

## 8. 멱등성 (사용자 요구)

- **POST**(주문 생성, 결제 승인, 취소 요청): `Idempotency-Key` 헤더 필수. 키와 사용자, 요청 본문 해시, 응답을 저장한다. 같은 키 재요청은 처음 응답을 그대로 돌려준다. 같은 키에 다른 본문이면 에러. 처리 중인 같은 키는 409.
- 결제 승인은 추가로 **paymentKey UNIQUE**로 두 번 승인을 막는다(헤더가 빠져도 지켜지는 마지막 방어선).
- **PATCH**(배송 시작, 배송 완료, 구매 확정): 이미 목표 상태면 성공으로 응답한다. 순서에 맞지 않는 변경은 에러.
- 키 보관 기간: 24시간(설정값).

## 9. 상태

- 주문: `PENDING_PAYMENT` → `PAID` → (항목이 전부 끝나면) `COMPLETED`, 또는 `CANCELED`(결제 전 만료·취소, 결제 후 전부 취소).
- 판매자 주문: `PAID` → `SHIPPING` → `DELIVERED` → `CONFIRMED`, 또는 `CANCELED`.
- 주문 항목: `ORDERED`, `CANCEL_REQUESTED`, `CANCELED`.
- 결제: `READY`, `IN_PROGRESS`, `APPROVED`, `PARTIAL_CANCELED`, `CANCELED`, `UNKNOWN`(확인 필요), `FAILED`.
- 배송 상태는 판매자가 바꾸고, 택배 조회로 배송 완료를 자동 반영한다(10-1장). 구매 확정은 판매자 주문 단위로, 사용자가 누르거나 `DELIVERED` 후 7일 뒤 자동.

## 9-1. 배송지 (사용자 결정, 2026-11-09)

- 주문 생성 시 수령인, 연락처, 우편번호, 주소, 상세 주소, 배송 메모를 직접 입력하고 주문에 복사해 둔다.
- 판매자는 자기 판매자 주문 상세에서 배송지를 본다. 회원 배송지록은 만들지 않는다.

## 10. 장바구니 (작성자 판단)

- 로그인 사용자만, 서버 저장. 같은 SKU를 다시 담으면 수량을 더한다.
- 가격은 저장하지 않고 조회와 주문 시 현재 가격으로 계산한다. 주문 요청에 클라이언트가 본 총액을 넣고, 서버 계산과 다르면 거절해 사용자가 바뀐 가격을 확인하게 한다.
- 품절, 판매 중지, 단종 항목은 남겨 두고 표시만 하며 주문에서 막는다.
- 주문은 장바구니에서 고른 항목으로, 또는 상세 화면에서 바로 구매로 만든다. 결제가 승인되면 주문한 항목을 장바구니에서 지운다.

## 10-1. 배송 조회 (사용자 결정, 2026-11-09)

- 판매자는 배송 시작 시 택배사 코드와 송장번호를 입력한다(필수).
- `DeliveryTracker` 인터페이스에 Mock 구현과 스마트택배(SweetTracker) 조회 구현을 두고 설정으로 고른다. 키는 `.env`로만 주입한다.
- 정리 작업이 `SHIPPING` 판매자 주문을 주기적으로 조회해 배송 완료면 `DELIVERED`로 바꾼다. 판매자가 직접 배송 완료를 누르는 기능도 유지한다.
- 외부 조회 실패나 지연은 주문 상태에 영향을 주지 않는다(다음 주기에 다시 조회). 조회는 DB 트랜잭션 밖에서 한다.
- 택배 접수(송장 발급)는 사업자 계약이 필요해 하지 않는다.

## 11. 판매량

- 결제 승인 시 상품 `sales_count`를 수량만큼 늘리고, 결제 후 취소 시 줄인다. 결제 전 만료는 늘린 적이 없으니 건드리지 않는다.

## 12. 기존 코드와의 관계

- 기존 `order`, `payment`, `deal` 모듈은 Phase 1 핫딜 프로토타입용이다. 로드맵대로 C2에서 order와 payment를 새 구조로 다시 짠다. `v0-hotdeal-prototype` 태그에 보존되어 있다. deal은 C6에서 다시 짠다(C2에서는 건드리지 않거나 컴파일만 유지).
- 새 모듈 후보: `cart`. 주문이 상품·SKU 정보를 얻을 때는 catalog의 application 서비스를 인터페이스로 호출한다(CLAUDE.md 모듈 규칙).

## 13. API (SDD)

`docs/api/openapi.yaml`을 먼저 고친다. 대략:
- 사용자: 장바구니 CRUD, 주문 생성, 결제 승인, 주문 목록·상세, 항목 취소, 구매 확정.
- 판매자: 내 판매자 주문 목록·상세, 배송 시작, 배송 완료.
- 관리자: 주문 조회(문제 확인용).

## 14. 완료 기준

- 위 기능이 동작하고 테스트가 모두 통과한다.
- 정합성 테스트: 같은 Idempotency-Key 동시 요청, 같은 paymentKey 두 번 승인, 만료와 승인 동시 도착, 같은 SKU 동시 주문(재고가 음수가 되지 않음), 부분 취소 여러 번 후 환불 합계, 5장 예시의 금액.
- ArchitectureTest 통과.

## 15. 빌더에게 맡기는 것

테이블 세부 컬럼과 인덱스, 정리 작업 실행 방식(@Scheduled 주기), 토스 API 클라이언트 구현 세부, 화면(API 이후 별도).
