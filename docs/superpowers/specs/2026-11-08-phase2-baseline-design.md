# Phase 2 기준선 측정 설계

> 작성일: 2026-11-08 · 상위 설계: `2026-11-08-kairos-design.md` 8장 Phase 2 · 관측 도구: `2026-11-08-observability-design.md`

## 1. 의도

최적화(Phase 3) 전에 지금 시스템이 오픈 순간 주문 폭주를 어떻게 처리하는지 **수치로 남긴다.** 이 결과가 Phase 3의 "전" 데이터이고, 결제 지연 조건의 결과는 Phase 4 MSA 전환의 근거가 된다.

비용 제약 때문에 측정은 로컬에서 한다(사용자 결정). 그래서 절대 수치가 아니라 **같은 조건에서의 상대 비교와 정합성(초과 판매)** 을 신뢰할 수 있는 결과로 삼고, 측정 조건을 통제해 재현성을 확보한다.

## 2. 측정 장면 (사용자 결정)

**재고 100개 딜에 1,000명이 오픈 순간 동시에 1개씩 주문한다** (경쟁률 10:1, 1인 구매 제한 1개).

1. **준비**: 회원 1,000명 가입·로그인, 토큰 확보. 측정에서 제외한다.
2. **오픈 직전 (60초)**: 사용자들이 딜 상세를 반복 조회하며 대기한다(조회 트래픽).
3. **오픈 순간 (스파이크)**: 1,000명이 오픈 시각에 맞춰 거의 동시에 주문 1건씩 요청한다.
4. **결과 수집**: 순판매량, 초과 판매 수량, 결과별 주문 수, 응답 시간, 커넥션 풀·스레드 최대치.

조건 두 가지를 같은 시나리오로 측정한다.
| 조건 | Mock PG 지연 | 목적 |
|---|---|---|
| A. 기본 | 100ms | Phase 3 비교 기준선, 초과 판매 재현 |
| B. 결제 지연 | 1s | 결제 지연이 커넥션 풀·스레드를 고갈시키는 모습 (MSA 전환 근거) |

Mock PG 실패율은 0으로 둔다(결과 해석을 단순하게).

## 3. 목표

- 위 장면을 한 명령으로 재현할 수 있다(준비 → 측정 → 결과 수집).
- 측정 조건(자원 제한, 설정, 반복 횟수)이 고정되어 있어 Phase 3에서 같은 조건으로 다시 돌릴 수 있다.
- 조건 A·B 각각 3회 실행한 결과와 대시보드 스크린샷이 리포트로 남는다.
- 리포트가 "무엇이 일어났고 왜 그런지"를 설명한다: 초과 판매 발생 여부와 수량, 병목 위치.

## 4. 하지 않을 것

- 성능 개선(락, 인덱스, 캐시, 설정 튜닝) — Phase 3.
- 클라우드 환경 측정 — 비용 제약. MSA 단계에서 필요하면 단기간만 검토.
- 절대 처리량 주장("TPS N을 달성") — 로컬 측정의 한계로 하지 않는다.
- 다른 시나리오(장시간 부하, 다수 딜 동시 오픈) — 필요해지면 Phase 3에서 추가.

## 5. 실패로 볼 것

- 실행할 때마다 조건이 달라 결과를 비교할 수 없는 것(자원 제한 없음, 이전 실행 데이터 잔존).
- 부하 생성기(k6)와 앱이 CPU를 다퉈서 측정값이 k6 한계를 반영하는 것.
- 준비 단계(가입·로그인, BCrypt)가 측정 구간에 섞이는 것.
- 결과가 대시보드 화면에만 있고 수치·조건 기록이 남지 않는 것.

## 6. 측정 환경 (작성자 판단)

### 6.1 앱 컨테이너화와 자원 제한
- 앱을 Docker 이미지로 빌드한다(멀티 스테이지, JDK 21 런타임).
- 측정용 compose 프로필(`perf`)에서 앱·MySQL·Redis를 자원 제한과 함께 띄운다.

| 서비스 | CPU | 메모리 |
|---|---|---|
| app | 2 | 1.5GB (JVM 힙 1GB) |
| mysql | 2 | 2GB |
| redis | 0.5 | 256MB |

- 근거: 측정 머신은 10코어/32GB(Docker 할당 10 CPU/7.6GB). 앱·DB에 4.5 CPU를 주고 나머지를 k6와 Prometheus·Grafana가 쓴다. k6는 호스트에서 실행한다.
- 앱 설정은 기본값 그대로 둔다(HikariCP 최대 10, Tomcat 최대 스레드 200). 튜닝은 Phase 3에서 한다. 실제 값은 리포트에 기록한다.
- Prometheus는 앱 컨테이너의 관리 포트(8081)를 수집하도록 perf 프로필용 대상을 추가한다.

### 6.2 측정 데이터 격리
- 매 실행마다 **새 딜**을 만든다(오픈 시각 = 준비 완료 시점 + 60초). 딜별 메트릭(`dealId`)이 섞이지 않는다.
- 회원 1,000명은 실행마다 새로 만들지 않고 고정 계정(`perf-user-0001` ~ `1000`)을 재사용한다. 이미 있으면 가입을 건너뛰고 로그인만 한다. 1인 제한은 딜 단위이므로 새 딜에서는 문제없다.
- 각 실행 전 앱을 재시작해 메모리 메트릭과 JVM 상태를 초기화한다(워밍업 포함).

### 6.3 워밍업과 반복
- 측정 전 워밍업: 별도 딜에 소량 주문(예: 50건)으로 JIT·커넥션 풀을 데운다.
- 조건별 3회 실행, 지표는 중앙값으로 보고하고 3회 값을 모두 표에 남긴다.

## 7. 산출물

```
perf/
  k6/
    setup-users.js       회원 1,000명 가입·로그인 → 토큰 파일
    timedeal-open.js     오픈 직전 조회 + 오픈 순간 주문 스파이크
  scripts/
    run-baseline.sh      앱 재시작 → 워밍업 → 딜 생성 → k6 실행 → 결과 수집 (조건 인자: A|B)
    collect-result.sh    DB·Prometheus에서 결과 수집 → JSON
  results/               실행별 결과 JSON (커밋)
docs/perf/
  2026-11-XX-phase2-baseline.md   리포트 (조건, 3회 결과 표, 중앙값, 스크린샷, 해석)
  images/                대시보드 스크린샷
```

### 7.1 결과 지표 (실행마다)
- 주문 요청 수, 결과별 건수(PAID, SOLD_OUT, LIMIT_EXCEEDED 등)
- **순판매량(커밋된 PAID 수량 합)과 초과 판매 수량** — DB의 `orders`(PAID 합)와 메트릭 `kairos_deal_sold` 두 값을 함께 기록하고 일치 여부를 확인한다
- DB `stock.remaining_quantity` 최종값 (lost update의 흔적: 판매량과 맞지 않음)
- 주문 API 응답 시간 p50/p95/p99/최대, 에러율 (k6)
- HikariCP 대기 커넥션 최대치, Tomcat 사용 스레드 최대치 (Prometheus)
- 결제 소요 시간 p95

## 8. 완료 기준

- `perf/scripts/run-baseline.sh A`와 `B`가 각각 한 번에 끝까지 실행되고 결과 JSON을 남긴다.
- 조건 A·B 각 3회 결과가 `perf/results/`에 있고, 리포트에 표·중앙값·스크린샷·해석이 있다.
- 리포트 해석에 포함할 것: 초과 판매 발생 여부와 규모, 재고 최종값이 판매량과 어긋나는 이유(lost update), 조건 B에서 병목이 어디서 생기는지, 측정 오버헤드(샘플링 100% 추적, JSON 파일 로그)와 로컬 측정의 한계.
- README Phase 2 체크.

## 9. 세부 결정 (작성자 판단, 리뷰 반영)

- **초과 판매가 0인 실행도 그대로 보고한다.** 커넥션 풀 10개 기준으로 동시에 겹치는 트랜잭션이 많지 않아 실행마다 초과 판매 규모가 다를 수 있다. 결과를 맞추려고 조건을 조정하지 않고, 3회 값을 모두 표에 남긴다. 경쟁 조건은 비결정적이라 중앙값만으로는 약하다는 점을 리포트에 명시한다.
- **재시작은 앱만 한다.** MySQL·Redis는 유지한다. Prometheus는 이력을 유지하므로 실행별 지표는 스크립트가 기록한 시작·종료 시각 구간으로 조회한다(`max_over_time`, `increase`).
- **perf 대상은 1초 간격으로 수집한다.** 몇 초짜리 스파이크의 최댓값(HikariCP 대기, Tomcat 스레드)을 놓치지 않기 위해서다.
- **토큰은 실행마다 새로 발급한다.** 앱 재시작 후 측정 전에 1,000명이 로그인한다(측정 구간 밖). 가입·로그인은 동시성 20~50 정도로 제한한다(BCrypt가 CPU 2개짜리 앱을 막지 않도록).
- **스파이크 폭**: 공유 시작 시각 기준 1,000건 요청이 약 1~2초 안에 도착하면 충분하다. 연결은 오픈 직전 조회 단계에서 미리 맺어 둔다.
- **타임아웃과 오류도 결과 분류에 포함한다.** 조건 B에서는 결제 1초 × 커넥션 10개라 대기가 길어져 HikariCP 커넥션 타임아웃(30초)과 500 응답이 생길 수 있다. 이것이 측정하려는 현상이므로 정상 결과로 기록한다(k6 기준 상태 코드별 건수 + 메트릭 OTHER).
- **스크린샷은 수동으로 찍는다.** 스크립트가 실행 구간이 맞춰진 Grafana 링크를 출력하고, 사람이 열어서 캡처한다. "한 명령"은 측정과 수치 수집까지를 뜻한다.
- 결과 JSON에는 토큰, 비밀번호 등 `.env`에서 온 값을 넣지 않는다.
- 이 장면에서 1인 제한은 모두 1개씩 주문하므로 LIMIT_EXCEEDED는 0이 예상된다. 주요 결과는 PAID와 SOLD_OUT이다.
- 자원: k6는 Docker VM 밖(macOS 호스트)에서 돌아 컨테이너 CPU 할당과는 겹치지 않지만 VM과 같은 물리 코어를 쓴다. 측정 중에는 다른 무거운 프로그램을 끈다.

## 10. 빌더에게 맡기는 것

- k6 시나리오의 세부 실행기(executor) 선택과 오픈 시각 동기화 방법(단, 1,000건 주문이 오픈 직후 짧은 구간에 몰려야 한다).
- Dockerfile 세부, perf 프로필 구성 방식.
- 결과 JSON 형식.
