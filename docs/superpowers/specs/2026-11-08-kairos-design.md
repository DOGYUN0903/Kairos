# Kairos 설계 문서

> Kairos: 놓치면 다시 오지 않는 순간을 위한 타임딜 서비스
> 작성일: 2026-11-08

## 1. 의도와 배경

MSA를 직접 경험하기 위한 개인 토이 프로젝트다. 이전 프로젝트 flashdeal은 모놀리식(로드밸런서까지 사용)에서 끝났다. Kairos는 flashdeal을 이어받지 않고 **새로 시작**한다.

핵심 스토리는 다음과 같다.

> 스펙부터 작성하고(SDD), 모놀리식에서 쓸 수 있는 최적화를 모두 적용하고 각각의 효과를 수치로 남긴다. 그래도 남는 한계(장애 격리, 독립 확장)를 근거로 MSA로 전환하고, 마지막으로 장애 실험으로 검증한다.

MSA는 목적이 아니라 **필요해져서 선택하는 결과**여야 한다.

## 2. 목표

1. **SDD(Spec Driven Development)**: API 스펙(OpenAPI)을 먼저 쓰고, 이를 기준으로 구현하고 테스트한다. MSA 단계의 이벤트 스펙은 AsyncAPI로 작성한다.
2. **모놀리식 최적화를 끝까지**: 인덱스, 락 전략, 캐싱, CQRS를 단계별로 적용하고, 단계마다 같은 부하 시나리오로 수치를 측정해 비교한다.
3. **MSA 전환**: 남은 한계를 근거로 서비스를 분리한다. 분리 순서와 이유는 ADR로 남긴다.
4. **장애 대응**: 결제 지연이나 다운 같은 장애 시나리오를 실험하고 결과를 기록한다.
5. **아키텍처 의사결정 기록**: 주요 결정은 `docs/adr/`에 ADR로 남긴다.

## 3. 하지 않을 것 (Non-goals)

- 프론트엔드 화면. 백엔드 API만 만든다. 간단한 데모 화면은 MSA 전환 이후의 선택지로 남긴다.
- 소셜 로그인, 이메일 인증, 비밀번호 찾기
- 배송, 리뷰, 장바구니
- 실제 PG 연동. 결제는 Mock으로 처리한다.
- 처음부터 MSA로 시작하기

## 4. 실패로 볼 것 (Anti-goals)

- 근거 없이 MSA로 쪼개는 것. "필요해서 분리했다"는 수치나 시나리오 없이 분리하면 실패다.
- 최적화 전후 수치가 남지 않는 것
- 재고가 음수가 되거나 초과 판매(oversell)가 발생하는 것
- 스펙과 구현이 따로 노는 것. 스펙은 장식이 아니라 구현과 테스트의 기준이어야 한다.
- 인프라 세팅에만 시간을 다 쓰고 핵심 흐름을 검증하지 못하는 것

## 6. 기능 범위

### 회원 / 인증
- 이메일과 비밀번호로 회원가입, 로그인, 로그아웃
- JWT Access/Refresh 토큰, 토큰 재발급
- 권한은 `USER`와 `ADMIN` 두 가지

### 타임딜 (관리자)
- 딜 등록: 상품 정보, 정가, 할인가, 총 수량, 1인당 구매 제한 수량, 오픈 시각, 종료 시각
- 딜 수정과 취소. 오픈 전에만 가능하다.

### 타임딜 (사용자)
- 딜 목록 조회: 오픈 예정, 진행 중, 종료 상태별
- 딜 상세 조회: 남은 수량 포함

### 주문
- 주문 생성: 딜이 진행 중인지 확인하고, 1인당 제한 수량을 확인하고, 재고를 차감한다.
- 결제 대기 상태의 주문은 **일정 시간 안에 결제하지 않으면 자동 취소**하고 재고를 복구한다.
- 내 주문 내역 조회
- 사용자가 직접 주문 취소. 결제 전이거나 결제 완료 후에도 가능하며, 재고를 복구한다.

### 결제 (Mock)
- Mock PG가 결제를 승인하거나 거절한다.
- **지연 시간과 실패율을 설정으로 조절**할 수 있어야 한다. 장애 실험에 쓴다.
- 결제에 실패하면 주문을 취소하고 재고를 복구한다.

### 주문 상태 흐름
```
CREATED(재고 차감됨, 결제 대기) ──결제 성공──▶ PAID
        │                                    │
        ├──결제 실패/시간 초과──▶ CANCELLED(재고 복구)
        └──사용자 취소─────────▶ CANCELLED(재고 복구)
PAID ──사용자 취소──▶ CANCELLED(재고 복구, 환불은 Mock)
```

### 세부 규칙 (작성자 판단, 확인 필요)
- 한 주문에 여러 개를 살 수 있다(수량 ≥ 1). 1인당 제한은 해당 딜에서 **취소되지 않은 주문 수량의 합**으로 확인한다. 취소된 주문은 제한에 포함되지 않으며, 보상 처리 시 사용자별 카운터도 함께 되돌린다.
- 주문 상태 전이는 **먼저 확정된 쪽이 이긴다.** 상태 변경은 조건부 UPDATE(현재 상태 확인)로 처리한다. 시간 초과나 사용자 취소로 이미 CANCELLED가 된 뒤 결제 승인이 도착하면, 그 결제는 거절하고 Mock 환불 처리한다.
- 결제 대기 시간 제한은 설정값으로 둔다. 기본 10분, 부하 테스트에서는 짧게 조정한다.
- 딜 진행 중에 복구된 재고는 다시 판매 가능 수량이 된다. 딜 종료 후의 취소는 재고 수치만 되돌리고 판매는 재개되지 않는다.
- PAID 주문 취소는 기간 제한 없이 가능하다.

## 7. 핵심 불변 조건

- 취소되지 않은 주문 수량의 합(순판매량)은 총 수량을 절대 넘지 않는다(oversell 0건).
- 재고는 음수가 되지 않는다.
- 한 사용자가 한 딜에서 구매 제한 수량을 넘지 않는다.
- 취소된 주문의 재고는 정확히 한 번만 복구된다.

모든 최적화 단계의 부하 테스트는 이 조건을 함께 검증한다. 수치가 좋아져도 불변 조건이 깨지면 실패다.

## 8. 진행 단계와 완료 기준

기간보다 **단계별 완료 기준**을 우선한다.

### Phase 0. 스펙과 기반
- 6장 기능의 OpenAPI 스펙을 먼저 작성한다.
- Docker Compose로 MySQL을 띄우고 Flyway로 초기 스키마를 만든다.
- **완료 기준**: 스펙 문서가 있고, 앱과 DB가 로컬에서 뜬다.

### Phase 1. 모놀리식 기본 구현
- 모듈러 모놀리식으로 구현한다. 패키지 경계는 `member`, `deal`, `order`, `payment`로 나누고, 모듈끼리 서로의 내부 구현(엔티티, 리포지토리)을 직접 참조하지 않는다. 나중에 분리할 때 경계가 그대로 서비스 경계가 된다.
- 재고 차감은 가장 단순한 방식(락 없는 조회 후 차감)으로 구현한다. 의도적으로 최적화하지 않으며, **동시 주문 시 초과 판매가 발생할 수 있음을 허용한다**(사용자 결정). Phase 1 테스트는 단일 요청 기준 동작만 검증하고, 동시성 문제는 Phase 2에서 재현해 기록한다. 4장의 "초과 판매는 실패" 조건은 Phase 3 이후에 적용한다.
- 결제는 **주문 요청 안에서 Mock PG를 동기 호출**하고 결과를 기다린다(사용자 결정). PG 지연이 요청 스레드와 DB 커넥션을 붙잡는 상황을 모놀리식의 한계로 측정하기 위해서다. Phase 4 Saga는 주문 생성 이벤트에서 시작한다.
- **완료 기준**: 6장의 모든 기능이 스펙대로 동작하고 통합 테스트(Testcontainers)를 통과한다.

### Phase 2. 기준선 측정
- k6 부하 시나리오를 작성한다. 시나리오: 오픈 직전 딜 상세 조회가 몰리고, 오픈 순간 주문이 폭주한다.
- TPS, p95/p99 응답 시간, 에러율, 불변 조건 위반 여부를 기록한다.
- **완료 기준**: 기준선 리포트가 `docs/perf/`에 남는다. 동시성 문제(oversell 등)가 드러나면 그것도 기록한다.

### Phase 3. 모놀리식 최적화
각 단계마다 Phase 2와 같은 시나리오로 측정하고 전후를 비교해 기록한다.

1. **DB 최적화**: 실행 계획 확인, 인덱스 설계, 쿼리 튜닝
2. **재고 차감 락 전략 비교**: 비관적 락, 낙관적 락, 조건부 원자적 UPDATE를 비교한다. InnoDB 락 동작과 데드락 사례도 기록한다.
3. **캐싱**: 딜 조회는 Redis 캐시로, 재고는 Redis 원자 연산으로 처리하고 DB와 동기화한다.
4. **CQRS**: 조회 모델과 주문/재고 쓰기 모델을 분리한다.
5. 그 밖에 측정 결과 필요해진 것. 예: 가상 스레드, 커넥션 풀 튜닝

- **완료 기준**: 단계별 수치 비교 리포트가 있고, 남은 한계를 수치나 시나리오로 정리한 "MSA 전환 근거" 문서가 있다. 근거는 성능 한계뿐 아니라 **장애 격리**(결제가 느려지면 조회까지 느려지는 문제)와 **독립 확장**(조회와 주문의 확장 요구가 다름)을 포함한다.

### Phase 4. MSA 전환
- 전환 근거 문서를 바탕으로 분리 순서를 ADR로 정한다. 예상 첫 분리 대상은 Payment이다.
- 이벤트 스펙(AsyncAPI)을 먼저 작성한다.
- Kafka와 Transactional Outbox를 도입하고, 주문, 재고, 결제 흐름을 Saga로 처리한다. 보상 트랜잭션도 구현한다.
- Spring Cloud Gateway에서 JWT를 검증하고 사용자 정보를 내부 서비스로 전달한다.
- 이벤트 소비는 멱등하게 처리한다.
- **완료 기준**: 분리된 서비스에서도 불변 조건이 지켜지고, 같은 부하 시나리오로 측정한 결과가 있다.

### Phase 5. 장애 대응
- Resilience4j로 Circuit Breaker, Timeout, Retry를 적용한다.
- 장애 시나리오: Mock PG 지연, Mock PG 다운, 결제 서비스 다운, Kafka 지연
- 분산 트레이싱(OpenTelemetry 등)과 대시보드(Grafana)로 관측한다.
- **완료 기준**: 시나리오별로 무슨 일이 일어났고 어떻게 대응했는지 기록한 실험 리포트가 있다.
