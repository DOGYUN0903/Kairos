# Kairos 설계 문서

> Kairos: 놓치면 다시 오지 않는 순간을 위한 타임딜 서비스
> 작성일: 2026-11-08

## 1. 의도와 배경

MSA를 직접 경험하기 위한 개인 토이 프로젝트다. 이전 프로젝트 flashdeal은 모놀리식(로드밸런서까지 사용)에서 끝났다. Kairos는 flashdeal을 이어받지 않고 **새로 시작**한다.

핵심 스토리는 다음과 같다.

> 스펙부터 작성하고(SDD), 모놀리식에서 쓸 수 있는 최적화를 모두 적용하고 각각의 효과를 수치로 남긴다. 그래도 남는 한계(장애 격리, 독립 확장)를 근거로 MSA로 전환하고, 마지막으로 장애 실험으로 검증한다.

MSA는 목적이 아니라 **필요해져서 선택하는 결과**여야 한다.

## 2. 목표

1. **SDD(Spec Driven Development)**: API 스펙(OpenAPI)을 먼저 쓰고, 이를 기준으로 구현하고 테스트한다. MSA 단계의 이벤트 스펙은 AsyncAPI로 작성한다.
2. **모놀리식 최적화를 끝까지**: 인덱스, 락 전략, 캐싱, CQRS를 단계별로 적용하고, 단계마다 같은 부하 시나리오로 수치를 측정해 비교한다.
3. **MSA 전환**: 남은 한계를 근거로 서비스를 분리한다. 분리 순서와 이유는 ADR로 남긴다.
4. **장애 대응**: 결제 지연이나 다운 같은 장애 시나리오를 실험하고 결과를 기록한다.
5. **아키텍처 의사결정 기록**: 주요 결정은 `docs/adr/`에 ADR로 남긴다.

## 3. 하지 않을 것 (Non-goals)

- 프론트엔드 화면. 백엔드 API만 만든다. 간단한 데모 화면은 MSA 전환 이후의 선택지로 남긴다.
- 소셜 로그인, 이메일 인증, 비밀번호 찾기
- 배송, 리뷰, 장바구니
- 실제 PG 연동. 결제는 Mock으로 처리한다.
- 처음부터 MSA로 시작하기

## 4. 실패로 볼 것 (Anti-goals)

- 근거 없이 MSA로 쪼개는 것. "필요해서 분리했다"는 수치나 시나리오 없이 분리하면 실패다.
- 최적화 전후 수치가 남지 않는 것
- 재고가 음수가 되거나 초과 판매(oversell)가 발생하는 것
- 스펙과 구현이 따로 노는 것. 스펙은 장식이 아니라 구현과 테스트의 기준이어야 한다.
- 인프라 세팅에만 시간을 다 쓰고 핵심 흐름을 검증하지 못하는 것

## 6. 기능 범위

### 회원 / 인증
- 이메일과 비밀번호로 회원가입, 로그인, 로그아웃
- JWT Access/Refresh 토큰, 토큰 재발급
- 권한은 `USER`와 `ADMIN` 두 가지

### 타임딜 (관리자)
- 딜 등록: 상품 정보, 정가, 할인가, 총 수량, 1인당 구매 제한 수량, 오픈 시각, 종료 시각
- 딜 수정과 취소. 오픈 전에만 가능하다.

### 타임딜 (사용자)
- 딜 목록 조회: 오픈 예정, 진행 중, 종료 상태별
- 딜 상세 조회: 남은 수량 포함

### 주문
- 주문 생성: 딜이 진행 중인지 확인하고, 1인당 제한 수량을 확인하고, 재고를 차감한다.
- 결제 대기 상태의 주문은 **일정 시간 안에 결제하지 않으면 자동 취소**하고 재고를 복구한다. Phase 1(동기 결제)에서는 Mock PG 타임아웃(`kairos.mock-pg.timeout`, 기본 3초) 초과를 `PAYMENT_TIMEOUT` 취소로 처리하고, 스케줄러 기반 자동 취소는 결제가 비동기가 되는 Phase 4에서 구현한다.
- 내 주문 내역 조회
- 사용자가 직접 주문 취소. 결제 전이거나 결제 완료 후에도 가능하며, 재고를 복구한다.

### 결제 (Mock)
- Mock PG가 결제를 승인하거나 거절한다.
- **지연 시간과 실패율을 설정으로 조절**할 수 있어야 한다. 장애 실험에 쓴다.
- 결제에 실패하면 주문을 취소하고 재고를 복구한다.

### 주문 상태 흐름
```
CREATED(재고 차감됨, 결제 대기) ──결제 성공──▶ PAID
        │                                    │
        ├──결제 실패/시간 초과──▶ CANCELLED(재고 복구)
        └──사용자 취소─────────▶ CANCELLED(재고 복구)
PAID ──사용자 취소──▶ CANCELLED(재고 복구, 환불은 Mock)
```

### 세부 규칙 (작성자 판단, 확인 필요)
- 한 주문에 여러 개를 살 수 있다(수량 ≥ 1). 1인당 제한은 해당 딜에서 **취소되지 않은 주문 수량의 합**으로 확인한다. 취소된 주문은 제한에 포함되지 않으며, 보상 처리 시 사용자별 카운터도 함께 되돌린다.
- 주문 상태 전이는 **먼저 확정된 쪽이 이긴다.** 상태 변경은 조건부 UPDATE(현재 상태 확인)로 처리한다. 시간 초과나 사용자 취소로 이미 CANCELLED가 된 뒤 결제 승인이 도착하면, 그 결제는 거절하고 Mock 환불 처리한다. (Phase 1은 동기 결제라 이 경합이 생기지 않으므로 Phase 4에서 구현한다.)
- 결제 대기 시간 제한은 설정값으로 둔다. Phase 4 비동기 결제 기준 기본 10분, 부하 테스트에서는 짧게 조정한다.
- 딜 진행 중에 복구된 재고는 다시 판매 가능 수량이 된다. 딜 종료 후의 취소는 재고 수치만 되돌리고 판매는 재개되지 않는다.
- PAID 주문 취소는 기간 제한 없이 가능하다.

## 7. 핵심 불변 조건

- 취소되지 않은 주문 수량의 합(순판매량)은 총 수량을 절대 넘지 않는다(oversell 0건).
- 재고는 음수가 되지 않는다.
- 한 사용자가 한 딜에서 구매 제한 수량을 넘지 않는다.
- 취소된 주문의 재고는 정확히 한 번만 복구된다.

모든 최적화 단계의 부하 테스트는 이 조건을 함께 검증한다. 수치가 좋아져도 불변 조건이 깨지면 실패다.

## 8. 진행 단계와 완료 기준

기간보다 **단계별 완료 기준**을 우선한다.

### Phase 0. 스펙과 기반
- 6장 기능의 OpenAPI 스펙을 먼저 작성한다.
- Docker Compose로 MySQL을 띄우고 Flyway로 초기 스키마를 만든다.
- **완료 기준**: 스펙 문서가 있고, 앱과 DB가 로컬에서 뜬다.

### Phase 1. 모놀리식 기본 구현
- 모듈러 모놀리식으로 구현한다. 패키지 경계는 `member`, `deal`, `order`, `payment`로 나누고, 모듈끼리 서로의 내부 구현(엔티티, 리포지토리)을 직접 참조하지 않는다. 나중에 분리할 때 경계가 그대로 서비스 경계가 된다.
- 재고 차감은 가장 단순한 방식(락 없는 조회 후 차감)으로 구현한다. 의도적으로 최적화하지 않으며, **동시 주문 시 초과 판매가 발생할 수 있음을 허용한다**(사용자 결정). Phase 1 테스트는 단일 요청 기준 동작만 검증하고, 동시성 문제는 Phase 2에서 재현해 기록한다. 4장의 "초과 판매는 실패" 조건은 Phase 3 이후에 적용한다.
- 결제는 **주문 요청 안에서 Mock PG를 동기 호출**하고 결과를 기다린다(사용자 결정). PG 지연이 요청 스레드와 DB 커넥션을 붙잡는 상황을 모놀리식의 한계로 측정하기 위해서다. Phase 4 Saga는 주문 생성 이벤트에서 시작한다.
- **완료 기준**: 6장의 모든 기능이 스펙대로 동작하고 통합 테스트(Testcontainers)를 통과한다.

### Phase 2. 기준선 측정
- k6 부하 시나리오를 작성한다. 시나리오: 오픈 직전 딜 상세 조회가 몰리고, 오픈 순간 주문이 폭주한다.
- TPS, p95/p99 응답 시간, 에러율, 불변 조건 위반 여부를 기록한다.
- **완료 기준**: 기준선 리포트가 `docs/perf/`에 남는다. 동시성 문제(oversell 등)가 드러나면 그것도 기록한다.

### Phase 3. 모놀리식 최적화
각 단계마다 Phase 2와 같은 시나리오로 측정하고 전후를 비교해 기록한다.

1. **DB 최적화**: 실행 계획 확인, 인덱스 설계, 쿼리 튜닝
2. **재고 차감 락 전략 비교**: 비관적 락, 낙관적 락, 조건부 원자적 UPDATE를 비교한다. InnoDB 락 동작과 데드락 사례도 기록한다.
3. **캐싱**: 딜 조회는 Redis 캐시로, 재고는 Redis 원자 연산으로 처리하고 DB와 동기화한다.
4. **CQRS**: 조회 모델과 주문/재고 쓰기 모델을 분리한다.
5. 그 밖에 측정 결과 필요해진 것. 예: 가상 스레드, 커넥션 풀 튜닝

- **완료 기준**: 단계별 수치 비교 리포트가 있고, 남은 한계를 수치나 시나리오로 정리한 "MSA 전환 근거" 문서가 있다. 근거는 성능 한계뿐 아니라 **장애 격리**(결제가 느려지면 조회까지 느려지는 문제)와 **독립 확장**(조회와 주문의 확장 요구가 다름)을 포함한다.

### Phase 4. MSA 전환
- 전환 근거 문서를 바탕으로 분리 순서를 ADR로 정한다. 예상 첫 분리 대상은 Payment이다.
- 이벤트 스펙(AsyncAPI)을 먼저 작성한다.
- Kafka와 Transactional Outbox를 도입하고, 주문, 재고, 결제 흐름을 Saga로 처리한다. 보상 트랜잭션도 구현한다.
- Spring Cloud Gateway에서 JWT를 검증하고 사용자 정보를 내부 서비스로 전달한다.
- 이벤트 소비는 멱등하게 처리한다.
- **완료 기준**: 분리된 서비스에서도 불변 조건이 지켜지고, 같은 부하 시나리오로 측정한 결과가 있다.

### Phase 5. 장애 대응
- Resilience4j로 Circuit Breaker, Timeout, Retry를 적용한다.
- 장애 시나리오: Mock PG 지연, Mock PG 다운, 결제 서비스 다운, Kafka 지연
- 분산 트레이싱(OpenTelemetry 등)과 대시보드(Grafana)로 관측한다.
- **완료 기준**: 시나리오별로 무슨 일이 일어났고 어떻게 대응했는지 기록한 실험 리포트가 있다.

## 9. 아키텍처 규칙

DDD와 클린 아키텍처를 따른다(사용자 결정). 아래 세부 규칙은 작성자 초안이다.

### 9.1 바운디드 컨텍스트 = 모듈 = 미래의 서비스

| 모듈 | 책임 | 애그리거트 |
|---|---|---|
| `member` | 회원, 인증, 권한 | Member |
| `deal` | 타임딜과 재고 | Deal, Stock |
| `order` | 주문과 주문 상태 흐름, 1인당 구매 제한 | Order |
| `payment` | 결제와 Mock PG 연동 | Payment |
| `common` | 공통 타입만(예외 기반 클래스, 공통 값 객체). 비즈니스 로직 금지 |  |

모듈 경계는 Phase 4에서 그대로 서비스 경계가 된다. Stock은 Deal과 별도 애그리거트로 둔다. 딜 정보 수정과 재고 차감의 경합을 분리하고, Phase 3의 재고 최적화(Redis, 원자적 UPDATE)를 Deal과 독립적으로 바꾸기 위해서다.

### 9.2 모듈 내부 레이어

```
com.dogyun.kairos.{module}
  domain/          애그리거트, 엔티티, 값 객체, 도메인 서비스, 도메인 이벤트, 리포지토리 인터페이스
  application/
    port/in/       유스케이스 인터페이스 + Command/Query/Result
    port/out/      외부 의존 인터페이스 (영속성, 외부 API, 다른 모듈)
    service/       유스케이스 구현
  adapter/
    in/web/        Controller, 요청/응답 DTO
    out/persistence/  JPA 엔티티, Spring Data 리포지토리, 매퍼, port/out 구현
    out/external/  Mock PG 클라이언트 등
    out/module/    다른 모듈 호출 어댑터
```

**의존성 규칙**: `adapter → application → domain` 한 방향만 허용한다.
- `domain`은 Spring, JPA, Jackson 등 프레임워크에 의존하지 않는 순수 Kotlin이다.
- `application`은 트랜잭션(`@Transactional`)과 DI 어노테이션까지만 허용하고, 웹과 JPA 타입은 모른다.
- 이 규칙은 ArchUnit 테스트로 강제한다. 의존성은 Phase 1에서 추가한다.

### 9.3 도메인 모델과 영속성 모델 분리

- 도메인 모델과 JPA 엔티티를 **분리한다**. JPA 엔티티는 `adapter/out/persistence`에만 존재하고, 매퍼로 변환한다.
- 매핑 코드가 늘어나는 비용을 감수한다. 그 대신 Phase 3에서 영속성 전략(원자적 UPDATE, Redis, CQRS 조회 모델)을 바꿔도 도메인과 유스케이스는 바뀌지 않아야 한다. 이것이 분리하는 이유이며, 최적화 단계에서 이 효과를 기록한다.

### 9.4 DDD 규칙

- 애그리거트 간에는 **ID로만 참조**한다. 객체 참조와 JPA 연관관계를 맺지 않는다.
- 상태 변경은 애그리거트의 도메인 메서드로만 한다(예: `order.pay()`, `stock.decrease(qty)`). 외부에 public setter를 두지 않는다. Kotlin에서는 `private set`을 쓴다.
- 불변 조건은 애그리거트 안에서 검증한다. 서비스에 `if` 검증이 흩어지지 않게 한다.
- 값 객체를 적극 사용한다. 예: `Money`, `Quantity`, `Email`, 각 ID 타입(`DealId`, `OrderId`). Kotlin `value class`나 `data class`로 만든다.
- 리포지토리는 애그리거트 루트 단위로만 둔다.
- 유스케이스 하나에서 **한 애그리거트만 변경**하는 것을 원칙으로 한다. Phase 1에서 주문 생성은 재고 차감과 주문 저장을 한 트랜잭션에서 처리하는 것을 예외로 허용하고, 이 예외는 Phase 4에서 Saga로 대체한다. 예외 지점에는 주석과 ADR로 표시한다.

### 9.5 모듈 간 통신

- 다른 모듈은 **그 모듈의 `port/in` 유스케이스 인터페이스로만** 호출한다. 다른 모듈의 `domain`, `adapter`, JPA 엔티티를 import하지 않는다.
- 호출하는 쪽은 자기 `port/out`에 필요한 인터페이스를 정의하고, `adapter/out/module`에서 상대 모듈의 `port/in`을 호출해 구현한다. Phase 4에서는 이 어댑터만 HTTP나 Kafka 클라이언트로 교체한다.
- 모듈 간에 주고받는 값은 ID와 전용 DTO뿐이다.
- 부가 작업(알림, 통계 등)은 도메인 이벤트로 처리한다. 모놀리식에서는 Spring `ApplicationEvent`와 `@TransactionalEventListener`를 쓴다.

### 9.6 웹, 예외, 응답

- Controller는 요청 DTO를 Command/Query로 변환해서 유스케이스를 호출만 한다. 비즈니스 로직을 두지 않는다.
- 도메인 예외는 모듈별로 정의하고, 공통 `@RestControllerAdvice`에서 HTTP 상태와 에러 코드로 변환한다.
- 에러 응답 형식은 하나로 통일하고 OpenAPI 스펙에 정의한다.

### 9.7 JPA 규칙

- 스키마는 Flyway로만 관리한다. `ddl-auto: validate`를 쓴다.
- `open-in-view: false`
- 연관관계는 같은 애그리거트 안에서만, 기본 `LAZY`로 맺는다(사용자 결정 포함).
  - 기본은 **`@ManyToOne` 단방향 매핑**이다.
  - 양방향 매핑은 되도록 쓰지 않고, 정말 필요한 경우에만 쓴다. 쓸 때는 이유를 코드 주석에 남긴다.
  - **`@ManyToMany`, `@OneToOne`은 사용하지 않는다.** 다대다는 중간 엔티티로 풀고, 일대일은 ID 참조로 대체한다.
- JPA 엔티티에는 비즈니스 로직을 두지 않는다. 비즈니스 로직은 도메인 모델에 둔다.
- **모든 JPA 엔티티는 `BaseEntity`를 상속한다**(사용자 결정). `BaseEntity`는 `created_at`, `created_by`, `modified_at`, `modified_by`, `status`를 관리한다.
  - `created_*`, `modified_*`는 Spring Data JPA Auditing으로 채운다. `*_by`는 인증된 회원 ID이며, 인증 전 요청(회원가입 등)과 시스템 작업은 `0`(SYSTEM)으로 기록한다(작성자 판단).
  - `status`는 **레코드 상태**(`ACTIVE`, `DELETED`)다(작성자 판단). 주문 상태 같은 도메인 상태와 섞이지 않도록 도메인 상태 컬럼은 `order_status`, `deal_status`, `payment_status`처럼 이름을 따로 짓는다.
- **소프트 딜리트를 사용한다**(사용자 결정). 삭제는 `status = DELETED`로 바꾸는 것이며 물리 삭제(`DELETE`)를 하지 않는다. 조회는 기본적으로 `ACTIVE`만 대상으로 하며, 엔티티에 `@SQLRestriction("status = 'ACTIVE'")`를 붙여 강제한다.
- 감사 필드와 레코드 상태는 영속성 관심사이므로 도메인 모델에는 두지 않는다. 도메인에서 삭제가 필요하면 리포지토리 포트의 `delete` 메서드로 표현하고, 어댑터가 소프트 딜리트로 구현한다.
- 조회 성능 문제(N+1 등)는 Phase 2 측정 후 Phase 3에서 해결한다. Phase 1에서 미리 최적화하지 않는다.
