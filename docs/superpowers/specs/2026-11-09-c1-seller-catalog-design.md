# C1 판매자와 상품 설계

> 작성일: 2026-11-09 · 상위: `2026-11-09-commerce-roadmap-design.md` 3장 C1

## 1. 의도

Kairos를 "여러 브랜드가 입점한 마켓플레이스"로 바꾸는 첫 단계다. 판매자가 입점하고, 브랜드를 만들고, 상품을 올리고, 관리자가 심사해 판매가 시작되기까지를 만든다. 사용자는 카테고리, 브랜드, 필터, 정렬, 검색으로 상품을 찾는다.

이 단계의 상품 목록과 검색은 대용량 단계(3-2)에서 최적화할 대상이다. 그래서 지금은 **기능이 맞는 단순한 구현**을 하고, 최적화는 하지 않는다(단계 전환 원칙: 데이터가 쌓이고 측정한 뒤에 고친다).

## 2. 역할

| 역할 | 하는 일 |
|---|---|
| 사용자(USER) | 상품 찾기, 상세 보기 |
| 판매자(SELLER) | 입점 신청, 브랜드 신청, 상품 등록·수정, 판매 중지·종료, 가격·재고 변경 |
| 관리자(ADMIN) | 판매자·브랜드·상품 심사, 판매자 정지, 카테고리 관리 |

- 판매자 계정은 회원 계정과 같은 로그인을 쓴다(작성자 판단). 판매자 안에 직원 계정을 여러 개 두지 않는다.
- **SELLER는 JWT 역할로 두지 않는다(작성자 판단).** `Role`(USER, ADMIN)은 그대로 둔다. 판매자 API는 요청마다 `memberId`로 판매자 테이블을 조회해 상태를 확인한다. 그래서 승인이나 정지가 토큰 재발급 없이 바로 반영된다. 회원 한 명당 판매자는 하나다(`member_id` UNIQUE).

## 3. 도메인 (사용자 결정 + 작성자 판단)

### 3.1 판매자 (사용자 결정: 판매자 하나가 여러 브랜드 운영, 정산은 C4)
- 입점 신청 정보: 회사명, 사업자등록번호(형식만 검증, UNIQUE), 대표자명, 연락처, 정산 계좌(은행, 계좌번호, 예금주), 기본 수수료율(관리자가 승인할 때 정한다).
- 상태: `PENDING` → `APPROVED` 또는 `REJECTED`(사유) → (승인 후) `SUSPENDED`(사유) ↔ `APPROVED`.
- 반려되면 내용을 고쳐 다시 신청할 수 있다.
- 정지되면 그 판매자의 모든 상품이 사용자 화면에서 숨겨지고, 판매자는 새 신청을 할 수 없다. 해제되면 다시 보인다.

### 3.2 브랜드
- 승인된 판매자가 신청하고 관리자가 승인한다. 이름(전체에서 UNIQUE), 영문명, 로고 이미지, 소개.
- 상태: `PENDING` → `APPROVED` 또는 `REJECTED`.
- 상품은 브랜드에 속한다. 사용자 화면에서 브랜드 페이지(브랜드 정보 + 상품 목록)를 볼 수 있다.

### 3.3 카테고리
- 관리자가 관리하는 2단계 트리(대분류 > 소분류). 상품은 소분류 하나에 속한다.
- 노출 순서를 둔다. 상품이 있는 카테고리는 삭제할 수 없다(소프트 딜리트 전 검사).

### 3.4 상품 (사용자 결정: 관리자 검수 후 판매)
- 정보: 브랜드, 소분류 카테고리, 상품명, 설명(텍스트), 대표 이미지와 추가 이미지(최대 10장), 정가, 판매가.
- 판매 상태: `PENDING_REVIEW` → `ON_SALE` 또는 `REJECTED`(사유), `ON_SALE` ↔ `PAUSED`(판매자 일시 중지), → `ENDED`(판매 종료, 되돌릴 수 없음).
- 품절은 상태가 아니다. 모든 SKU의 재고가 0이면 화면에 "품절"로 표시한다.
- **바로 반영되는 변경**: 판매가, SKU별 재고와 추가 금액, SKU 판매 여부.
- **재검수가 필요한 변경**: 상품명, 설명, 이미지, 카테고리, 옵션 구성. 검수 중에는 기존 내용으로 계속 판다. 승인되면 바뀐 내용으로 교체되고, 반려되면 변경 요청만 버린다. 구현은 "변경 요청"을 따로 저장하는 방식으로 한다(작성자 판단).
- 판매자는 자기 브랜드의 상품만 다룰 수 있다. 다른 판매자의 상품에 접근하면 존재를 드러내지 않고 `PRODUCT_NOT_FOUND`를 돌려준다.

### 3.5 옵션과 SKU
- 옵션 축은 0~2개(예: 색상, 사이즈). 축이 없으면 SKU가 하나다.
- 축 값의 모든 조합이 SKU가 된다(예: 블랙/L). SKU마다 추가 금액(0 이상), 재고, 판매 여부를 둔다.
- 주문, 재고 차감, 핫딜은 모두 SKU 단위다(C2, C6). C1에서는 재고를 판매자가 숫자로 설정만 한다.

## 4. 사용자 상품 찾기 (사용자 결정: 모두 넣는다)

- 노출 조건: 상품 `ON_SALE`, 브랜드 `APPROVED`, 판매자 `APPROVED`.
- 필터: 대분류 또는 소분류, 브랜드, 가격대(판매가 기준 최소·최대).
- 검색어: 상품명과 브랜드명에 대한 부분 일치(`LIKE '%키워드%'`). 의도적으로 단순하게 둔다. 3-2에서 측정하고 개선한다.
- 정렬: 최신순(승인 시각), 가격 낮은순, 가격 높은순, **인기순**.
  - 인기순은 누적 판매 수량 기준이다. C1에서는 상품에 `sales_count` 컬럼만 두고(0), C2에서 결제가 완료될 때 늘린다. 같은 값이면 최신순.
- 목록 응답: 상품 ID, 대표 이미지, 브랜드명, 상품명, 정가, 판매가, 할인율, 품절 여부. `PageResponse`, 기본 20개.
- 상세: 위 정보 + 설명, 이미지 목록, 옵션 축과 SKU 목록(추가 금액, 품절 여부). 재고 숫자 자체는 사용자에게 보여 주지 않는다.
- 인덱스는 PK와 UNIQUE 외에 추가하지 않는다. 3-2에서 쌓인 데이터로 측정한 뒤 추가한다(기존 Phase 규율과 같은 이유).

## 5. 이미지 (작성자 판단)

- 이미지 업로드 API는 저장소 인터페이스(`ImageStorage`) 뒤에 둔다. 로컬과 테스트에서는 파일 시스템에 저장하고, 배포 단계에서 S3 구현을 추가한다.
- 형식은 jpg, png, webp만, 파일 하나당 최대 5MB. 상품과 브랜드에는 업로드 결과로 받은 URL을 저장한다.

## 6. 기존 코드와의 관계

- 기존 `deal`, `order`, `payment` 모듈과 API는 C1에서 건드리지 않는다. C2에서 주문과 결제를 SKU 기반으로 다시 짜고, C6에서 핫딜을 상품 SKU 위에 다시 만든다. 그때까지 기존 테스트는 계속 통과해야 한다.
- 새 모듈 이름(작성자 판단): `seller`(판매자, 브랜드), `catalog`(카테고리, 상품, 옵션, SKU, 상품 검색). 서로는 ID로만 참조하고, 다른 모듈 호출 규칙(CLAUDE.md)을 따른다. 노출 조건을 확인하려면 catalog가 seller의 application 인터페이스를 호출한다.
- 상품 검색처럼 여러 테이블을 한 번에 조회하는 쿼리는 catalog의 infrastructure에서 QueryDSL로 작성한다. 판매자·브랜드 상태가 필요하면 조회 전용으로 조인하는 것을 허용하고, 이 예외를 ADR로 남긴다(모듈 간 조인은 MSA로 갈 때 나눌 대상이라는 기록).

## 7. API (SDD)

OpenAPI를 먼저 고친다. 경로 규칙(작성자 판단):
- 사용자: `/api/v1/products`, `/api/v1/products/{id}`, `/api/v1/categories`, `/api/v1/brands/{id}`
- 판매자: `/api/v1/seller/...` (입점 신청, 내 판매자 정보, 브랜드, 상품, SKU, 이미지 업로드)
- 관리자: `/api/v1/admin/...` (판매자·브랜드·상품 심사 목록과 승인·반려, 판매자 정지·해제, 카테고리 관리)
- 심사 목록은 상태 필터와 페이징을 지원한다.

## 8. 하지 않을 것

- 판매자 직원 계정, 판매자 등급, 상품 Q&A, 상품 고시 정보, 배송 정보.
- 재고 차감(C2), 정산(C4), 핫딜(C6).
- 검색 최적화(전문 검색 인덱스, Elasticsearch), 캐시, 인덱스 추가 — 3-2.
- 화면 — 아래 9장 참고.

## 9. 화면

C1 백엔드가 끝나면 **화면 디자인 방향과 시안을 별도 작업으로** 시작한다(디자인 → 시안 → 프론트, 사용자 결정). 사용자, 판매자, 관리자 화면 중 C1 범위(상품 찾기와 상세, 입점·브랜드·상품 등록, 심사)를 먼저 만든다. 이 문서는 백엔드만 다룬다.

## 10. 완료 기준

- OpenAPI와 구현이 계약 테스트로 맞는다.
- 상태 전이 규칙(판매자, 브랜드, 상품, 변경 요청)이 도메인 단위 테스트로 검증된다. 허용되지 않는 전이는 409(`INVALID_STATE_TRANSITION` 계열 에러 코드)다.
- 권한: 다른 판매자의 상품·브랜드 접근 불가, SELLER가 관리자 API 호출 불가(테스트).
- 노출 조건 테스트: 판매자 정지, 브랜드 미승인, 상품 일시 중지 또는 종료면 목록과 상세에 나오지 않는다.
- 필터, 정렬, 검색, 페이징 조합이 통합 테스트(Testcontainers)로 검증된다.
- ArchitectureTest 통과, 기존 테스트 통과.
- README와 CLAUDE.md의 모듈 목록 갱신.

## 11. 빌더에게 맡기는 것

- 엔티티와 테이블의 세부 구성(변경 요청 저장 형태 등), 에러 코드 이름.
- 상태 전이를 도메인 객체에서 표현하는 방식.
- 로컬 이미지 저장 위치와 정적 서빙 방식.
- 개발용 초기 데이터(카테고리 몇 개, 샘플 판매자·상품)를 넣을지 여부. 대용량 데이터는 C5에서 만든다.

## 12. 세부 결정 (작성자 판단, 빌더 검토 반영)

- **반려 후 재신청은 같은 행을 쓴다.** 판매자, 브랜드, 상품 모두 반려된 행을 고쳐 다시 `PENDING`(상품은 `PENDING_REVIEW`)으로 보낸다. 반려 이력은 심사 이력 테이블에 남긴다(누가, 언제, 결과, 사유).
- **변경 요청은 상품당 최대 1개만 대기할 수 있다.** 판매자는 대기 중인 변경 요청을 철회할 수 있다. 가격, 재고, SKU 판매 여부처럼 바로 반영되는 변경은 변경 요청과 관계없이 언제든 할 수 있다.
- **옵션 구성 변경과 SKU.**
  - 승인되면 SKU를 다시 만든다. 옵션 값 조합이 같은 SKU는 ID, 재고, 추가 금액을 그대로 이어받는다.
  - 새 조합은 재고 0, 추가 금액 0으로 생성된다.
  - 사라진 조합의 SKU는 소프트 딜리트한다. C2 주문이 그 SKU를 참조하고 있을 수 있어서 행을 남긴다.
  - `sales_count`는 상품 단위라 영향이 없다.
- **가격 규칙.**
  - 판매가는 정가 이하이고, 둘 다 0보다 크다.
  - 할인율은 `floor((정가 - 판매가) / 정가 × 100)`이다.
  - 가격 필터와 정렬은 상품 판매가 기준이다. SKU 추가 금액은 반영하지 않는다.
- **판매자 상태별 권한.**
  - `PENDING`·`REJECTED` 판매자는 자기 신청 정보만 보고 고칠 수 있다.
  - `SUSPENDED` 판매자는 조회와 판매 중지·종료만 할 수 있다. 등록, 수정, 신청은 막는다.
  - 상태 때문에 막힌 요청은 403이 아니라 409 `SELLER_NOT_ACTIVE`로 응답한다. 인증된 판매자의 상태 문제이기 때문이다.
  - 판매자가 아닌 회원이 판매자 API를 부르면 403이다.
- **이미지 URL.**
  - 상품과 브랜드에는 이 서버가 발급한 업로드 URL만 저장할 수 있다. 업로드 기록과 대조해 검증하고, 업로드한 판매자 본인 것만 허용한다.
  - 연결되지 않은 업로드를 정리하는 작업은 이번에 하지 않는다.

## 13. 아키텍처 검토 반영 (fable 검토 + 사용자 승인, 2026-11-09)

- **SKU 단종 상태 (사용자 승인).** 12장의 "사라진 조합은 소프트 딜리트"를 대체한다.
  - SKU는 BaseEntity의 `status=DELETED`를 쓰지 않는다. 대신 `sku_status`(`ACTIVE`/`DISCONTINUED`)를 둔다. 소프트 딜리트하면 `@SQLRestriction` 때문에 C2 주문 내역, C4 정산, C6 핫딜에서 그 SKU를 조회하지 못하기 때문이다.
  - 옵션 구성에서 사라진 조합은 `DISCONTINUED`가 된다. 같은 조합이 다시 생기면 그 행을 `ACTIVE`로 되살리고, 재고는 0으로 둔다.
  - 조합은 옵션 값 이름이 아니라 **옵션 값 ID**로 맞춘다. 옵션 값 이름만 바꾸면 ID, 재고, 추가 금액이 유지된다.
  - 사용자 상세 화면에는 `ACTIVE` SKU만 보인다.
- **`product.seller_id` 비정규화 (사용자 승인).** 상품에 판매자 ID를 직접 저장한다. 브랜드의 판매자와 같아야 하며, 브랜드는 다른 판매자로 옮겨지지 않는다. 노출 조건, 판매자 권한 검사, C2 판매자별 주문 분할, C4 정산이 상품 → 브랜드 → 판매자 순서로 찾아가지 않고 이 컬럼을 쓴다.
- **인기순 판매량은 취소·환불 시 줄인다 (사용자 결정).** 인기순은 실제로 팔린 수량 기준이다. C2에서 구현한다.
- **판매자 상태 확인은 한 곳에서 한다.** 판매자 API는 `@AuthenticatedSeller` 같은 인자 하나로 판매자 조회와 상태 확인을 받는다. 컨트롤러마다 반복하지 않는다. 요청마다 DB를 조회하는 비용은 ALB 단계에서 캐시가 필요한지 측정할 후보로 남긴다.
- **최신순 기준 시각은 덮어쓰지 않는다.** 상품의 최초 판매 시작 시각 `on_sale_at`은 처음 승인될 때만 기록한다. 변경 요청이 승인되거나 일시 중지가 풀려도 바뀌지 않는다. 최신순 정렬은 이 값을 쓴다.
- **판매자와 브랜드에는 삭제 경로가 없다.** 정지와 반려만 있다. 그래서 사업자등록번호, `member_id`, 브랜드명의 UNIQUE 제약이 소프트 딜리트와 충돌하지 않는다.
- **`sales_count` 경합은 일부러 남긴다.** C6에서 핫딜이 열리면 같은 상품 행에 `sales_count` UPDATE가 몰린다. 이것은 Phase 3-1에서 측정하고 개선할 지점이라 지금은 최적화하지 않는다.
- **C2 인수 조건.** 주문 항목에는 주문 시점의 값을 복사해 둔다. 상품명, 브랜드명, 옵션 표시명, 판매가, 추가 금액, 판매자 ID, 판매자 수수료율이다. 가격과 수수료가 나중에 바뀌어도 주문과 정산이 흔들리지 않게 하기 위해서다.
- **미뤄 둔 결정.** 핫딜이 걸린 상품의 옵션 구성을 바꿀 수 있는지는 C6에서 정한다.
