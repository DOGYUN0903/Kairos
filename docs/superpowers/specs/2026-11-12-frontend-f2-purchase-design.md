# 프론트엔드 F2 구매 화면 설계 (C2)

> 작성일: 2026-11-12 · 빌더 체크 반영: 2026-11-12 · 상위: `2026-11-11-frontend-f1-foundation-design.md`(기반·규칙, 17장 F2 범위), `2026-11-09-c2-purchase-design.md`(구매 도메인 규칙) · ADR 0003·0004

## 1. 의도

F1에서 상품을 보고 등록·검수하는 데까지 화면이 생겼다. F2는 **실제로 사는 흐름**을 화면으로 끝까지 잇는다: 장바구니 → 주문서 → 결제 → 주문 완료 → 주문 내역·상세(항목 취소, 구매 확정), 그리고 그 주문을 받아 발송하는 판매자 화면과 문제를 확인하는 관리자 화면.

이 프로젝트의 핵심은 **돈과 재고가 어긋나지 않는 것**이다. F2 화면은 그 규칙을 흐리지 않고 그대로 드러내야 한다: 금액은 서버가 계산한 값만 보여주고, 주문·결제·취소는 두 번 눌러도 한 번만 일어나며, 결제 결과가 불확실한 순간("확인 중")도 숨기지 않고 화면에 보여준다. 시연용 껍데기가 아니라 실제 쇼핑몰 수준의 완성도가 기준이다(사용자 결정).

표기: **사용자 결정**(확정) / **Claude 결정**(작성자 판단. "틀렸을 때 비용"을 적는다).

## 2. 목표, 비목표, 안티 목표

- **목표**
  - 핵심 화면 5개 시안(장바구니, 주문서+모의 결제창, 주문 상세, 주문 내역, 판매자 주문 관리) 작성과 사용자 확인 — **F2의 첫 작업**(§4).
  - 백엔드 보강 5건(§5): 환불 미리보기 API, 주문 응답의 상품 이미지·배송 진행, 장바구니·견적의 판매자 정보, 장바구니 담기 멱등 경로, 장바구니의 판매자 상태 반영.
  - 구매자: 상품 상세의 장바구니·바로 구매, 장바구니, 주문서, 결제(모의/토스 테스트), 주문 완료, 주문 내역·상세, 항목 취소(환불 미리보기), 구매 확정, 결제 대기 주문 재결제.
  - 판매자: 주문 목록·상세, 발송 처리(택배사·송장), 배송 완료, 배송 전 항목 취소.
  - 관리자: 주문 목록(상태·회원·주문번호 검색)·상세, 항목 취소.
  - 구매 흐름 E2E 3개, CLAUDE.md 갱신.
- **비목표**: 쿠폰·포인트(F3. 주문서에 자리도 두지 않는다), 후기·좋아요 목록(F3), 반품·정산(F4), 회원 배송지록, 비로그인 장바구니, 실제 결제(라이브 키), 모바일, 데모 시더가 주문 데이터를 미리 만드는 것(시연은 화면에서 직접 주문한다).
- **안티 목표(실패로 보는 것)**
  - 결제하기·취소 버튼을 두 번 눌러 주문·결제·환불이 두 번 일어남.
  - 프론트가 금액(합계·배송비·환불액)을 스스로 계산해 서버와 다른 숫자를 보여줌.
  - 가격이 바뀌었는데 사용자가 모르는 금액으로 결제됨.
  - 결제 결과가 불확실한데 "결제 완료" 또는 "결제 실패"로 단정해 보여줌.
  - 운영 번들에 모의 결제의 실패 선택지나 데모 계정이 들어감. 토스 시크릿 키가 프론트 어디에든 들어감.
  - PG 호출이 DB 트랜잭션 안으로 들어가는 백엔드 변경(ADR 0003 위반). F2의 백엔드 변경은 읽기 전용 조회·응답 필드 추가와 멱등 경로 한 줄뿐이다.

## 3. F1 기반 재사용 (바꾸지 않는다)

- `src/api/client.ts`(토큰 메모리, 401 → 단일 reissue → 1회 재시도), `src/api/errors.ts`(코드 → 배치 표), `useIdempotentSubmit`(§11에서 키 규칙만 고친다), `lib/money.ts`(나눗셈은 여기서만), `lib/datetime.ts`, `safeNext`, `RequireAuth`/`RequireRole`/`SellerGate`, `ConsoleShell`·`SideNav`·`StoreHeader`, `StatusChip`·`Money`·`EmptyState`·`ErrorState`·`Pagination`·`ConfirmDialog`, 데모 바(`features/demo`), `check:api`·`check:bundle`, Playwright(`scripts/e2e-server.sh`, `:3100`, `e2e/fixtures/api.ts`).
- 규칙도 그대로다: `app/`은 조립만·기능은 `features/`, 낙관적 업데이트 없음, GET만 1회 재시도·뮤테이션은 재시도 없음, 목록 필터·페이지는 URL 쿼리가 단일 진실, 로딩·빈·오류 세 상태, 접근성 기본(F1 스펙 §13), 데스크톱 전용 1280px.

## 4. 시안 (사용자 결정)

- **F2의 첫 작업은 시안 5개다.** `design/`에 정적 HTML로 그리고(공용 `assets/kairos.css` 재사용, 필요한 클래스는 추가만) `design/index.html`에 링크를 더한다. **사용자가 확인한 뒤** 프론트 구현을 시작한다. 백엔드 보강(§5)은 시안과 독립이라 시안 확인을 기다리지 않고 진행해도 된다.

| 파일 | 담는 것 |
|---|---|
| `user-cart.html` | 판매자별 묶음, 선택 체크박스, 수량, 구매 불가 항목 표시, 오른쪽 금액 요약(무료배송 안내 포함), 빈 장바구니 |
| `user-checkout.html` | 배송지 폼(주소 검색·최근 배송지), 판매자별 주문 상품, 결제 금액, 결제하기. **모의 결제창**(정상/거절/응답 없음 — 데모 표시 포함)도 같은 파일에 상태로 그린다 |
| `user-order-detail.html` | 상태 헤더(결제 대기 남은 시간·확인 중 포함), 판매자 주문 카드(배송 상태·송장·항목), 항목 취소 창(환불 미리보기), 구매 확정, 결제·환불 요약, 배송지 |
| `user-order-list.html` | 주문 카드(이미지, 대표 상품 외 n건, 금액, 진행 상태), 빈 상태 |
| `seller-order.html` | 주문 목록(상태 탭·표)과 상세(배송지, 항목, 발송 처리 창, 배송 완료, 항목 취소) |

- 시안 없이 토큰·공용 컴포넌트로 바로 만드는 화면: 주문 완료, 결제 처리 중·확인 중·실패 안내, 결제 페이지(주문 요약 + 결제창 열기), 관리자 주문 목록·상세(판매자 주문 화면과 같은 표·카드 구조), 상품 상세의 버튼(기존 시안에 있음), 헤더 아이콘.
- 색·글꼴·간격은 F1 토큰 그대로. `hot` 색은 여전히 핫딜 전용이라 F2에서 쓰지 않는다. 시안 제작에 claude.ai Artifact·Claude Design을 쓰지 않는다(사용자 규칙).

## 5. 백엔드 보강 (OpenAPI 먼저 — SDD)

전부 **읽기 전용 조회 또는 응답 필드 추가**다(멱등 경로 한 줄 제외). 주문·결제·취소의 트랜잭션 구조, 락 순서, 금액 계산 클래스는 건드리지 않는다. 순서는 항상 `docs/api/openapi.yaml` → 구현 → `OpenApiContractTest` → `pnpm gen:api`(같은 커밋).

### 5-1. 환불 미리보기 API (사용자 결정)

- `GET /api/v1/orders/{orderId}/items/{orderItemId}/cancel-preview` (구매자, 인증 필요, `Idempotency-Key` 없음).
- 응답 `CancelPreview`: `orderItemId`, `paidAmount`(항목의 현금 결제 몫), `shippingFeeRefund`(판매자 주문이 통째로 비어 돌려받는 배송비), `shippingFeeDeducted`(무료배송 기준이 깨져 차감되는 배송비), `shippingFeeReturned`(마지막 취소라 되돌려받는 앞선 차감액), `refundAmount`(최종 환불액), `pointsRefund`.
- 계산은 실제 취소와 **같은 함수** `RefundCalculator.plan(order, itemId, CancelActor.BUYER, policy)`를 부른다. 새 계산 코드를 만들지 않는다. 상태를 바꾸지 않고, 주문 행 락을 잡지 않는 읽기 전용 트랜잭션이다(쓰기를 결정하는 읽기가 아니므로 스냅샷 읽기로 충분하다).
- 오류는 취소와 같다: 404 `ORDER_NOT_FOUND`(남의 주문 포함)/`ORDER_ITEM_NOT_FOUND`, 409 `ORDER_ITEM_NOT_CANCELABLE`/`ORDER_INVALID_STATE_TRANSITION`.
- 미리보기와 실제 취소 사이에 상태가 바뀔 수 있다. **진실은 취소 응답**이며 화면은 취소 뒤 실제 환불액을 다시 보여준다(§8-6).
- 테스트(돈이라 엄격하게): C2 스펙 5장 예시(6만 원 무료배송에서 3만 원 취소 → 27,000원, 차감 3,000원), 정확히 5만 원 남음(차감 없음), 이미 차감된 뒤의 취소(차감 없음), 마지막 취소(앞선 차감 반환), 구매자가 배송비를 낸 판매자 주문이 비는 취소(배송비 환불), **미리보기 값 = 직후 실제 취소 응답 값**(같은 주문으로 연속 호출), 미리보기가 아무것도 바꾸지 않음(주문·결제·재고 불변), 남의 주문 404.
- Claude 결정: 판매자·관리자용 미리보기는 만들지 않는다. 그쪽 취소는 배송비 차감이 없는 전액 환불이라 확인 창에 "배송비 차감 없이 환불됩니다"를 쓰고 실제 금액은 취소 응답으로 보여준다. 틀렸을 때 비용: 같은 서비스 메서드에 actor만 바꾼 엔드포인트 두 개를 더한다.

### 5-2. 주문 응답 보강 (사용자 결정: 이미지 / Claude 결정: 배송 진행)

- `OrderItemResult.thumbnailUrl`(nullable), `OrderSummary.thumbnailUrl`(첫 항목, nullable), `SellerOrderSummary.thumbnailUrl`(nullable)을 추가한다. 주문 시점 복사가 아니라 **조회할 때 상품의 현재 대표 이미지**를 가져온다(DB 변경 없음). 상품이 삭제됐으면 null이고 화면은 자리 표시 이미지를 쓴다. `order.application`의 기존 `ProductReader` 포트에 "상품 ID 목록 → 대표 이미지" 일괄 조회를 더하고(목록 한 페이지에 조회 1번, N+1 금지), 구현은 `order.infrastructure`에서 catalog의 application 서비스를 부른다(모듈 규칙). 틀렸을 때 비용: 판매자가 이미지를 바꾸면 과거 주문의 이미지도 바뀐다 — 스냅샷이 필요해지면 컬럼과 마이그레이션을 추가한다.
- `OrderSummary.sellerOrderStatuses`(`SellerOrderStatus` 배열, 판매자 주문 수만큼)를 추가한다(Claude 결정). 주문 상태는 `PAID`에서 `COMPLETED`까지 한 값이라, 이것이 없으면 주문 내역 카드에 "배송 중"을 보여줄 수 없다. 한 페이지의 주문 ID로 일괄 조회한다. 틀렸을 때 비용: 필드 하나와 조회 하나를 뺀다(목록 카드는 "결제 완료"만 보인다).
- 구매자·관리자 목록이 같은 `OrderSummary`를 쓰므로 둘 다 채워진다.
- (사용자 결정, 시안 확인 2026-11-12) `OrderDetail.remainingAmount`(= 결제 금액 − 누적 환불액)와 `OrderSummary.expiresAt`을 추가한다. 주문 상세의 "남은 결제 금액" 한 줄과 주문 내역 결제 대기 카드의 남은 시간을 프론트 계산 없이 보여주기 위해서다.

### 5-3. 장바구니·견적의 판매자 정보 (사용자 결정 + Claude 세부)

- `CartItemResult`에 `sellerId`, `sellerName`을 추가한다(SKU가 사라진 `DISCONTINUED` 항목은 nullable).
- `QuoteLine`에 화면 표시에 필요한 값을 추가한다: `productId`, `productName`, `brandName`, `optionDisplayName`, `thumbnailUrl`, `unitPrice`, `sellerId`. 바로 구매는 장바구니를 거치지 않으므로 주문서가 견적 응답만으로 상품을 그릴 수 있어야 한다(Claude 결정. 틀렸을 때 비용: 주문서가 SKU마다 상품 상세를 따로 조회해야 한다).
- `OrderQuote`에 `sellerQuotes`(배열: `sellerId`, `sellerName`, `itemsAmount`, `shippingFee`, `shippingFeePayer` BUYER|PLATFORM)와 `freeShippingThreshold`, `baseShippingFee`를 추가한다. 프론트는 5만 원·3,000원을 **하드코딩하지 않는다**.
- 금액 계산 로직은 바꾸지 않는다. 주문 생성과 같은 계산이 이미 판매자별 배송비를 만들고 있으므로 응답에 싣기만 한다. 테스트: 판매자 2명·5만 원 미만(배송비 3,000 × 2, BUYER), 5만 원 이상(PLATFORM, `buyerShippingFee` 0), `sellerQuotes`의 구매자 부담 배송비 합 = `buyerShippingFee`, `sellerQuotes.itemsAmount` 합 = `itemsAmount`.

### 5-4. 장바구니 담기 멱등 경로 (Claude 결정)

- `IdempotencyProperties.paths`에 `/api/v1/cart/items`를 추가하고 OpenAPI의 `addCartItem`에 `Idempotency-Key`(필수)를 적는다. 담기는 수량을 **더하는** POST라 네트워크 재전송이 수량을 두 배로 만든다. F1의 카테고리 생성과 같은 처리다. 틀렸을 때 비용: 경로 한 줄. `perf/` 스크립트나 기존 테스트가 이 경로를 키 없이 부르면 함께 고친다(빌더가 확인).

### 5-5. 장바구니가 판매자 상태를 본다 (사용자 결정, 빌더 체크 반영)

- 지금 장바구니의 `availability`는 상품·SKU 상태만 본다. 판매자가 정지(`SUSPENDED`)돼도 `AVAILABLE`로 나오는데, 견적·주문은 활성 판매자가 아니면 409 `SKU_NOT_ORDERABLE`로 거절한다. 그대로 두면 장바구니 금액 요약이 계속 실패하고 사용자는 원인 항목을 알 수 없다.
- `GET /cart`가 **주문 가능한 판매자(견적·주문과 같은 기준)가 아닌 항목을 `availability=PAUSED`로** 내려준다. 새 enum 값은 만들지 않는다(구매자에게는 둘 다 "판매 중지"다). `sellerId`·`sellerName`(§5-3)은 정지 판매자여도 채운다(묶음 표시용).
- 구현: `cart.application`에 판매자 상태 조회 포트를 두고 `cart.infrastructure`에서 seller의 application 서비스를 부른다(모듈 규칙). 장바구니 한 번 조회에 판매자 조회 1번(일괄).
- `POST /cart/items`(담기)는 바꾸지 않는다. 정지 판매자의 상품을 담는 것은 막지 않고, 장바구니에서 구매 불가로 보인다.
- 테스트: 판매자 정지 → 장바구니 항목 `PAUSED`·`availableAmount`에서 제외, 정지 해제 → 다시 `AVAILABLE`, **장바구니가 `AVAILABLE`이라고 한 항목만으로 부른 견적은 판매자 사유로 409가 나지 않는다**(두 기준이 같다는 것을 한 테스트로 묶는다).

### 5-6. 하지 않는 것

- 프론트에 PG 종류를 알려주는 엔드포인트는 만들지 않는다(§7-1에서 프론트 설정으로 정한다).
- 데모 시더의 주문 데이터, 구매자용 결제 대기 주문 취소 API, 택배사 목록 API.

## 6. 화면 흐름과 라우트

```
상품 상세 ─ 장바구니 담기 ─────────→ /cart ─ 선택 항목 주문 ─┐
         └ 바로 구매 ──────────────────────────────────────┤
                                                           ▼
                                   /checkout (배송지 + 견적 + 결제하기)
                                                           │ 주문 생성 (Idempotency-Key)
                                                           ▼
                                   /my/orders/{id}/pay (결제창: 모의 또는 토스)
                             닫음 ↙                         │ 결제 인증 성공
        주문은 결제 대기로 남음(15분)                          ▼
        → 주문 상세에서 다시 결제        /checkout/success (결제 승인 호출, Idempotency-Key)
                                       ├ APPROVED → /my/orders/{id}/complete
                                       ├ UNKNOWN·진행 중 → 확인 중 화면(자동 재조회)
                                       └ 거절(402) → 주문 취소됨 안내 → 장바구니
```

| 경로 | 화면 | 접근 |
|---|---|---|
| `/cart` | 장바구니 | 로그인 |
| `/checkout` | 주문서 (`?cartItemIds=1,2` 또는 `?skuId=&qty=`) | 로그인 |
| `/checkout/success`, `/checkout/fail` | 결제 승인 처리 / 결제창 실패·취소 | 로그인 |
| `/my/orders`, `/my/orders/[orderId]` | 주문 내역 / 주문 상세 | 로그인 |
| `/my/orders/[orderId]/pay`, `/complete` | 결제 페이지 / 주문 완료 | 로그인 |
| `/seller/orders`, `/seller/orders/[sellerOrderId]` | 판매자 주문 목록 / 상세 | 판매자(`SellerGate`) |
| `/admin/orders`, `/admin/orders/[orderId]` | 관리자 주문 목록 / 상세 | ADMIN |

- 구매자 화면은 `(store)` 레이아웃 아래 `RequireAuth`. 비로그인은 `/login?next=`로 가고 로그인 뒤 돌아온다(`safeNext`). 바로 구매가 URL로 상품·수량을 넘기므로(Claude 결정) 로그인 복귀·새로고침에도 주문서가 유지된다.
- 헤더: F1에서 숨겼던 **장바구니 아이콘(담긴 항목 수 배지)과 마이 아이콘**을 로그인 상태에서 켠다. 마이는 `/my/orders`로 간다(마이 페이지의 다른 메뉴는 F3에서 추가).
- 사이드바: 판매자 콘솔에 "주문 관리"(발송 대기 수 배지 — `?status=PAID&size=1`의 `totalElements`, F1 검수 배지와 같은 방식), 관리자 콘솔에 "주문"을 추가한다.

## 7. 결제 (사용자 결정 + Claude 세부)

### 7-1. 두 가지 결제 방식, 프론트 설정으로 고른다

- `NEXT_PUBLIC_PG_PROVIDER` = `mock`(기본) | `toss`. 백엔드 `KAIROS_PG_PROVIDER`와 **같은 값으로 맞춘다**(`frontend/.env.example`과 README에 적는다). 서로 다르면 승인이 실패하므로 조용히 틀리지 않는다.
- `toss`일 때 `NEXT_PUBLIC_TOSS_CLIENT_KEY`(토스 **테스트 클라이언트 키**, 공개용)를 쓴다. 시크릿 키(`TOSS_SECRET_KEY`)는 지금처럼 백엔드 `.env`에만 있고 프론트의 어떤 파일·번들에도 넣지 않는다.
- 두 방식은 **결제창만 다르고 그 뒤는 같은 길**을 탄다: 결제창이 끝나면 `/checkout/success?oid={주문 ID}&orderId={orderNo}&paymentKey=&amount=`로 가고, 이 페이지가 `POST /payments/confirm`을 부른다. `orderId`·`paymentKey`·`amount`는 토스의 성공 리다이렉트 형식이고, 모의 결제도 같은 주소로 이동해 승인 코드가 한 벌만 있게 한다.
- **숫자 주문 ID 전달**(Claude 결정, 빌더 체크 반영): 구매자 API는 주문번호로 주문을 찾지 못하고 숫자 ID는 승인 성공 응답에만 있다. 그래서 성공·실패 주소에 우리 쿼리 `oid`(숫자 주문 ID)를 붙여 보내고, 결제창을 열기 전에 `sessionStorage`에 `orderNo → orderId`도 적어 둔다(토스가 기존 쿼리를 보존하지 않는 경우의 대비 — 빌더가 토스 문서로 확인). 둘 다 없으면 "주문 내역에서 확인" 링크로 보낸다. 백엔드에 주문번호 조회는 추가하지 않는다. 틀렸을 때 비용: `GET /orders?orderNo=` 필터 하나를 추가한다.

### 7-2. 모의 결제창

- 우리 화면의 다이얼로그다. 주문명·결제 금액을 보여주고 "결제"를 누르면 `paymentKey`를 만들어 성공 주소로 보낸다. "닫기"는 아무것도 호출하지 않고 결제 페이지에 머문다.
- `paymentKey`는 프론트가 만든다: 정상 `mock-{uuid}`. **데모 모드(`NEXT_PUBLIC_DEMO_MODE`)에서만** 결과 선택지가 보인다: "카드사 거절"(`fail-{uuid}`), "응답 없음 — 실제로는 승인됨"(`unknown-{uuid}`), "응답 없음 — 승인도 안 됨"(`lost-{uuid}`). `MockPgClient`의 접두사 규칙 그대로다. 선택지에는 "시연용" 표시를 붙인다.
- 실패 선택지 코드는 `features/demo` 아래에 두고 데모 플래그 리터럴 비교로 감싸 운영 번들에서 빠지게 한다. `check:bundle`에 "데모가 아닌 번들에 실패 선택지 문자열(`fail-`, `unknown-`, `lost-` 접두사 상수)이 없음"을 추가한다.

### 7-3. 토스 테스트 결제창

- 토스 결제 SDK를 결제 페이지에서 필요할 때 불러와 결제창을 연다. `orderId`=주문번호(`orderNo`), `amount`=주문 총액, `successUrl`=`/checkout/success?oid=…`, `failUrl`=`/checkout/fail?oid=…`(§7-1).
- 토스는 **전체 페이지 이동**으로 돌아온다. 액세스 토큰은 메모리에만 있어 사라지지만 `AuthProvider` 부트스트랩(쿠키 reissue)이 다시 로그인 상태를 만든다. 성공 페이지는 부트스트랩이 끝난 뒤에 승인을 호출한다.
- 토스 결제는 E2E로 자동화하지 않는다. 테스트 키로 사람이 한 번 확인하는 수동 점검 항목이다(§13). 사용자가 토스 테스트 키를 준비하지 않았으면 이 점검만 뒤로 미루고 나머지는 모의 결제로 완료한다.
- SDK 패키지·호출 형태(결제위젯 vs 결제창)는 빌더가 현재 토스 문서를 확인해 정한다. 조건: 백엔드 승인 API(`paymentKey`, `orderNo`, `amount`)와 맞을 것, 프론트 번들에 시크릿 키가 필요 없을 것.

### 7-4. 승인 처리 (`/checkout/success`)

- 쿼리의 `orderId`(주문번호), `paymentKey`, `amount`로 `POST /payments/confirm`을 **한 번** 부른다. `Idempotency-Key`는 `paymentKey`마다 하나를 만들어 `sessionStorage`에 두고, 새로고침·뒤로 가기로 페이지가 다시 떠도 같은 키를 쓴다(토큰이 아니므로 storage 금지 규칙과 무관). React StrictMode·재렌더로 두 번 호출되지 않게 막는다.
- 결과별 화면:

| 응답 | 화면 |
|---|---|
| 200 `paymentStatus=APPROVED` | `/my/orders/{id}/complete`로 교체 이동(뒤로 가기로 승인 페이지에 돌아오지 않게). 장바구니·주문 쿼리 무효화 |
| 200 `UNKNOWN`, 409 `PAYMENT_IN_PROGRESS`, 409 `IDEMPOTENCY_IN_PROGRESS`, 네트워크 오류·5xx | **"결제 확인 중"**: 결제 완료도 실패도 단정하지 않는다. 주문 상세(`oid`)를 3초 간격으로 다시 조회해(최대 2분 — 대사 작업이 60초 주기로 `UNKNOWN` 결제를 확정하므로 보통 그 안에 풀린다) 승인되면 완료 화면, 주문이 취소되면 실패 안내로 바꾼다. 2분이 지나면 "주문 내역에서 결과를 확인해 주세요"와 주문 상세 링크 |
| 402 `PAYMENT_REJECTED` | "결제가 거절되어 주문이 취소되었습니다. 재고와 장바구니는 그대로입니다" + 장바구니로 |
| 400 `PAYMENT_AMOUNT_MISMATCH`, 409 `ORDER_INVALID_STATE_TRANSITION`(만료 등), `PAYMENT_KEY_DUPLICATED`, 404 | 서버 메시지 + 주문 상세 링크. 주문 상세가 실제 상태를 보여준다 |

- 장바구니 비우기는 서버가 승인 시 한다. 프론트는 장바구니 쿼리만 무효화한다.
- `/checkout/fail`(토스 실패·사용자 취소, 모의는 쓰지 않음): 사유 메시지와 "다시 결제"(→ 결제 페이지) / "주문 상세". 주문은 결제 대기로 남아 있다.

### 7-5. 결제 페이지 (`/my/orders/[orderId]/pay`)

- 주문 상세를 읽어 `PENDING_PAYMENT`이고 결제가 진행 중이 아닐 때만 결제창을 연다. 주문서에서 넘어온 직후에는 자동으로 연다. 결제 대기 주문의 "결제하기"(주문 상세·내역)도 이 페이지로 온다 — 재결제 경로를 하나로 둔다(Claude 결정. 틀렸을 때 비용: 페이지 하나를 다이얼로그로 바꾼다).
- 남은 시간(`expiresAt`)을 보여준다. 만료됐거나 주문이 이미 `PAID`/`CANCELED`면 결제창을 열지 않고 주문 상세로 보낸다.
- 0원 주문은 주문 생성 응답이 이미 `PAID`다. F2에서는 쿠폰·포인트가 없어 생기지 않지만, 주문 생성 응답이 `PAID`면 결제 페이지를 건너뛰고 완료 화면으로 가는 분기를 지금 넣는다(F3 대비 한 줄).

## 8. 구매자 화면

### 8-1. 상품 상세 (F1 화면 수정)

- F1에서 숨겼던 "장바구니"·"바로 구매" 버튼을 켜고 안내 문구를 지운다. 옵션을 다 고르지 않았거나 품절 조합이면 비활성.
- 장바구니: `POST /cart/items`(`Idempotency-Key`, 이중 제출 가드). 성공하면 그 자리에 머물고 "장바구니에 담았습니다 · 장바구니 보기" 토스트, 헤더 배지 갱신. 400 `CART_INVALID`(합산 999 초과)·409 `SKU_NOT_ORDERABLE`은 서버 메시지 토스트.
- 바로 구매: `/checkout?skuId=&qty=`로 이동(장바구니에 넣지 않는다). 비로그인은 로그인 뒤 같은 주소로 돌아온다.

### 8-2. 장바구니 `/cart`

- `GET /cart`. 항목을 `sellerName`별로 묶는다. 항목: 이미지, 브랜드, 상품명(상세 링크), 옵션, 단가, 수량 입력, 금액, 삭제.
- 선택은 화면 상태다(서버에 저장하지 않음). 처음에는 `AVAILABLE` 항목을 모두 선택한다. `SOLD_OUT`·`PAUSED`·`ENDED`·`DISCONTINUED` 항목은 흐리게 하고 사유를 표시하며 **선택할 수 없고 삭제만 된다**. 전체 선택·판매자별 선택·선택 삭제.
- 수량 변경(`PATCH /cart/items/{id}`)은 입력을 잠깐 모아 보내고 응답 뒤 장바구니를 다시 읽는다. 삭제는 확인 없이 바로(되돌리기 쉬운 작업).
- **금액 요약은 서버 견적으로 채운다**: 선택 항목으로 `POST /orders/quote`를 불러 상품 금액, 판매자별 배송비, 결제 예정 금액을 보여준다. 선택·수량이 바뀌면 다시 부른다(이전 응답은 버린다). 선택이 없으면 견적을 부르지 않고 0원과 비활성 "주문하기".
- 무료배송 안내: `freeShippingThreshold − itemsAmount`가 양수면 "○원 더 담으면 무료배송", 아니면 "무료배송". 뺄셈은 `money.ts`의 함수로 한다. 5만 원 미만에서 판매자가 여럿이면 판매자 묶음마다 배송비가 보여 합계가 설명된다.
- "주문하기" → `/checkout?cartItemIds=…`. 견적이 409 `SKU_NOT_ORDERABLE`이면(그 사이 품절·중지·판매자 정지) 장바구니를 다시 읽어 구매 불가 표시를 갱신한다(§5-5로 판매자 정지도 표시된다).
- 빈 장바구니: "장바구니가 비어 있습니다 → 상품 보러 가기".

### 8-3. 주문서 `/checkout`

- 항목 결정: `cartItemIds`면 장바구니에서 해당 항목(구매 가능한 것만)을, `skuId`·`qty`면 그 한 건을 쓴다. 쿼리가 잘못됐거나 항목이 0개면 장바구니로 보낸다.
- `POST /orders/quote`(쿠폰·포인트 없이 `items`만)로 화면을 그린다: 판매자별 주문 상품(견적의 표시 필드), 판매자별 배송비와 부담 주체, 상품 금액, 배송비, **결제 금액 `totalAmount`**. 프론트는 이 숫자들을 다시 계산하지 않는다.
- 배송지 폼(react-hook-form + zod, OpenAPI `ShippingAddress` 제약과 같게): 수령인(50), 연락처(20, 숫자·하이픈), 우편번호(10), 주소(200), 상세 주소(200), 배송 메모(200, 선택).
  - **주소 검색**: 카카오(다음) 우편번호 서비스를 버튼을 누를 때 불러 우편번호·주소를 채운다. 스크립트를 못 불러오면(오프라인) "주소 검색을 불러오지 못했습니다. 직접 입력해 주세요" 안내. 우편번호·주소는 **직접 입력도 가능**하다(오프라인 시연·E2E).
  - **최근 배송지 불러오기**: 내 주문 목록의 가장 최근 주문 상세에서 배송지를 가져와 채운다(주문이 없으면 버튼을 숨긴다). 서버에 따로 저장하지 않는다.
- **결제하기**: `useIdempotentSubmit`으로 `POST /orders`(`items`, `expectedTotalAmount`=화면에 보이는 견적의 `totalAmount`, `shippingAddress`). 성공하면 결제 페이지로 **교체 이동**한다. 응답을 받지 못해 다시 누르면 같은 키라 같은 주문이 돌아온다(§11 키 규칙).
- 오류:

| 코드 | 화면 |
|---|---|
| 409 `ORDER_PRICE_CHANGED` | 견적을 다시 불러 바뀐 금액을 보여주고 "금액이 변경되었습니다. 확인 후 다시 결제해 주세요" 안내. **자동으로 다시 제출하지 않는다**. 다음 제출은 새 키다(§11) |
| 409 `STOCK_SOLD_OUT`, `SKU_NOT_ORDERABLE` | 안내 + 장바구니로(바로 구매는 상품 상세로) |
| 400 `ORDER_INVALID` | 폼 상단 |
| 422 `IDEMPOTENCY_KEY_REUSED`, 409 `IDEMPOTENCY_IN_PROGRESS` | F1 표 그대로(폼 상단 / 토스트) |

- 쿠폰·포인트 영역은 두지 않는다(F3).

### 8-4. 주문 완료 `/my/orders/[orderId]/complete`

- 주문번호, 결제 금액, 배송지 요약, "주문 상세 보기"·"쇼핑 계속하기". 주문이 `PAID`가 아니면 주문 상세로 보낸다.

### 8-5. 주문 내역 `/my/orders`

- `GET /orders?page&size`. 카드: 주문일, 주문번호, 이미지, "상품명 외 n건", 결제 금액, 진행 상태, "주문 상세". 결제 대기 주문에는 "결제하기"(남은 시간).
- 진행 상태 문구는 주문 상태와 `sellerOrderStatuses`로 만든다(순수 함수 + 단위 테스트): `PENDING_PAYMENT` 결제 대기 / `CANCELED` 취소·만료 / `COMPLETED` 구매 확정 / `PAID`는 판매자 주문 상태 묶음(예: "배송 준비 중", "배송 중", "배송 완료", 섞여 있으면 "배송 중 1 · 배송 준비 1").

### 8-6. 주문 상세 `/my/orders/[orderId]`

- `GET /orders/{id}`. 404면 주문 없음 페이지.
- **상태 헤더**: 결제 대기(남은 시간 + "결제하기", 만료되면 자동 취소 안내), 결제 확인 중(결제 `IN_PROGRESS`/`UNKNOWN` — "결제 결과를 확인하고 있습니다"), 결제 완료, 구매 확정, 취소.
- **판매자 주문 카드**(판매자별): 판매자명, 상태 칩(`PAID` 배송 준비 중 / `SHIPPING` 배송 중 / `DELIVERED` 배송 완료 / `CONFIRMED` 구매 확정 / `CANCELED` 취소), 택배사명·송장번호(있으면), 배송비와 부담 주체, 항목 목록(이미지, 상품명, 옵션, 수량, 금액, 항목 상태).
  - **항목 취소**: 주문 `PAID` + 판매자 주문 `PAID` + 항목 `ORDERED`일 때만 버튼. 누르면 취소 창이 `cancel-preview`를 불러 **환불 예정 금액과 내역**(항목 금액, 배송비 환불, 배송비 차감 — 0이 아닌 줄만)을 보여준다. 사유(필수, 500자)를 받고 "취소하기"로 `POST …/cancel`(`Idempotency-Key`, `useIdempotentSubmit`). 미리보기가 409면 창에 취소 불가 사유를 보여주고 버튼을 막는다.
  - 취소 응답: `CANCELED`면 실제 `refundAmount`·`shippingFeeDeducted`를 토스트로 알리고 상세를 다시 읽는다. `CANCEL_REQUESTED`면 "취소를 확인하고 있습니다" — 항목에 "취소 확인 중" 칩. 409 `PAYMENT_CANCEL_FAILED`는 "취소가 거절되었습니다. 주문은 그대로입니다".
  - **구매 확정**: 판매자 주문 `DELIVERED`일 때 버튼. 확인 창("확정하면 되돌릴 수 없습니다") 뒤 `PATCH …/confirm`(키 없음, 이중 제출 가드, 서버가 이미 확정이면 200). 409 `SELLER_ORDER_HAS_OPEN_RETURN`은 서버 메시지.
  - 반품 관련 항목 상태(`RETURN_*`, `RETURNED`)는 데이터가 있을 수 있으므로 칩 문구만 정의한다. 반품·후기 버튼은 두지 않는다(F3·F4).
- **결제 요약**(전부 서버 값): 상품 금액, 배송비(구매자 부담), 결제 금액, 환불 금액(`refundedAmount`), 무료배송 기준 미달로 차감된 배송비(`shippingFeeRecovered`, 0이면 숨김), 남은 결제 금액(`remainingAmount`). 쿠폰·포인트 필드는 0이 아닐 때만 줄을 보인다(F3 전에도 데이터가 있을 수 있다).
- **배송지**: 읽기 전용.
- **자동 재조회**: 결제가 `IN_PROGRESS`/`UNKNOWN`이거나 `CANCEL_REQUESTED` 항목이 있으면 3초 간격으로 다시 읽는다(최대 2분, 그 뒤 "새로고침" 안내). 결제 대기 남은 시간이 0이 되면 한 번 다시 읽는다.
- 남은 시간 계산: `expiresAt`은 오프셋 없는 KST 문자열이다. `lib/datetime.ts`에 "KST LocalDateTime까지 남은 초"를 구하는 함수를 추가한다(문자열에 `+09:00`을 붙여 해석 — 브라우저 시간대에 흔들리지 않게). 표시용 포맷은 기존 규칙대로 문자열만 다룬다.

## 9. 판매자 화면

- **주문 목록 `/seller/orders`**: `GET /seller/orders?status&page&size`. 상태 탭(전체 / 발송 대기 `PAID` / 배송 중 / 배송 완료 / 구매 확정 / 취소), 표(이미지, 주문번호, "상품명 외 n건", 상품 금액, 상태 칩, 주문 일시). 탭·페이지는 URL 쿼리.
- **주문 상세 `/seller/orders/[sellerOrderId]`**: `GET /seller/orders/{id}`. 배송지(수령인·연락처·주소·메모), 내 항목, 배송비와 부담 주체, 진행 시각(발송·배송 완료·확정).
  - **발송 처리**(`PAID`): 창에서 택배사 선택 + 송장번호(1~50자) → `PATCH …/ship`. 택배사 목록은 프론트 상수(스마트택배 코드: CJ대한통운 `04`, 한진 `05`, 롯데 `08`, 우체국 `01`, 로젠 `06` 등 — 빌더가 `SweetTrackerDeliveryTracker`가 받는 코드와 맞는지 확인한다). 같은 상수로 구매자 화면이 코드를 택배사명으로 바꾼다(모르는 코드는 코드 그대로 표시). 409(다른 송장으로 재전송, 취소 확인 중 항목 있음)는 서버 메시지.
  - **배송 완료**(`SHIPPING`): 확인 뒤 `PATCH …/deliver`.
  - **항목 취소**(판매자 주문 `PAID`·항목 `ORDERED`): 사유 필수, "배송비 차감 없이 환불됩니다" 안내, `POST …/cancel`(`Idempotency-Key`). 결과 금액은 응답으로 알린다.
  - `SUSPENDED` 판매자: 서버가 409 `SELLER_NOT_ACTIVE`를 주는 동작은 F1 배너 규칙을 그대로 따른다. 어떤 버튼을 미리 막을지는 빌더가 서버 동작을 확인해 `useSellerCapabilities`에 맞춘다.
- **대시보드**: 기존 판매자 대시보드에 "발송 대기 n건" 카드와 바로 가기를 더한다.

## 10. 관리자 화면

- **주문 목록 `/admin/orders`**: `GET /admin/orders?status&memberId&orderNo&page&size`. 필터(상태 선택, 주문번호 정확히 일치, 회원 ID), 표(주문번호, 대표 상품, 금액, 상태, 주문 일시). 필터는 URL 쿼리.
- **주문 상세 `/admin/orders/[orderId]`**: `GET /admin/orders/{id}`(구매자 상세와 같은 `OrderDetail`). 구매자 상세의 표시 컴포넌트를 재사용하되 구매자 전용 행동(결제하기, 구매 확정)은 없다. 결제 정보(상태, 결제 금액, 환불 금액, `paymentKey`)를 문제 확인용으로 더 보여준다.
  - **항목 취소**: 사유 필수, `POST /admin/orders/{id}/items/{itemId}/cancel`(`Idempotency-Key`). 판매자 취소와 같은 안내.

## 11. 프론트 구조와 공통 규칙

- 디렉터리(Claude 결정, F1 구조를 따름): `features/cart`, `features/checkout`(주문서·배송지·주소 검색), `features/payment`(결제 페이지·승인 처리·모의 결제창·토스), `features/orders`(구매자 내역·상세·취소·확정, 표시 컴포넌트는 관리자와 공유), `features/seller/orders`, `features/admin/orders`. 모의 결제의 실패 선택지만 `features/demo`.
- **멱등 키 규칙 수정**(Claude 결정, 빌더 체크 반영): 서버는 5xx가 아닌 응답(409·402 포함)을 키와 함께 저장해 24시간 그대로 재생하고, 같은 키에 본문이 다르면 422다. 그래서 키 규칙을 **"응답을 받지 못한 시도(네트워크 오류·5xx)만 같은 키로 다시 보내고, 서버가 답한 뒤(2xx·4xx)의 다음 제출은 항상 새 키"**로 바꾼다. F1의 `useIdempotentSubmit`은 "폼 값이 같으면 같은 키"라서, 가격 변경(409) 뒤 재결제가 422로 막히고 취소 거절(409) 뒤 재시도가 저장된 409만 돌려받는다. 이 훅 하나만은 §3의 "바꾸지 않는다"의 예외로 고치고 단위 테스트를 새 규칙으로 바꾼다(F1 폼들도 같은 훅을 쓰므로 함께 올바르게 된다). 틀렸을 때 비용: 훅 한 파일과 테스트.
- **멱등성**: 서버가 키를 강제하는 요청 — 장바구니 담기, 주문 생성, 결제 승인, 항목 취소(구매자·판매자·관리자) — 은 반드시 키를 보낸다. 폼이 있는 제출은 `useIdempotentSubmit`, 폼이 없는 요청(장바구니 담기, 결제 승인)은 같은 원칙(위 키 규칙, 처리 중 재호출 무시)을 지키는 얇은 훅으로 한다 — 기존 훅을 일반화할지 새로 둘지는 빌더가 정한다. 상태 전이 PATCH(발송, 배송 완료, 구매 확정)와 장바구니 수량 변경·삭제는 키 없이 이중 제출 가드와 서버 상태 검사에 기댄다(F1 규칙).
- **금액**: 화면의 모든 합계·배송비·환불액은 서버 응답 값이다. 프론트 계산은 두 가지뿐이다 — 상품 상세의 선택 합계(F1에 이미 있음)와 "무료배송까지 남은 금액"(뺄셈). 둘 다 `money.ts` 함수로 하고 단위 테스트를 둔다. 표시는 `<Money>`/`formatKrw`만 쓴다.
- **에러**: 새 코드를 `errors.ts` 표에 넣는다(메시지를 바꾸거나 배치가 토스트가 아닌 것만): `ORDER_NOT_FOUND`·`SELLER_ORDER_NOT_FOUND` → 페이지, `ORDER_INVALID` → 폼, `ORDER_PRICE_CHANGED`·`STOCK_SOLD_OUT`·`SKU_NOT_ORDERABLE`·`PAYMENT_REJECTED`·`PAYMENT_CANCEL_FAILED`·`ORDER_ITEM_NOT_CANCELABLE` 등은 §7·§8의 화면 동작으로 처리한다. 표에 없는 코드는 서버 메시지를 그대로 보여주는 F1 규칙 유지.
- **상태 칩**: `StatusChip`에 주문·판매자 주문·주문 항목·결제 상태를 추가한다(문구는 §8-6, 색은 시안 `.chip-*`).
- **쿼리 키**: `cart`, `orders`(목록·상세), `sellerOrders`, `adminOrders`를 `query-keys.ts`에 추가한다. 무효화: 담기·수량·삭제 → 장바구니(+헤더 배지), 승인 → 장바구니·주문, 취소·확정·발송·배송 완료 → 해당 주문 상세와 목록.
- **환경 변수**: `frontend/.env.example`에 `NEXT_PUBLIC_PG_PROVIDER`, `NEXT_PUBLIC_TOSS_CLIENT_KEY`(주석 처리, 설명 포함)를 추가한다. E2E 서버 스크립트는 `mock`으로 빌드한다.

## 12. 데모

- 데모 바(F1)는 그대로다. 구매자 → 판매자 → 관리자 전환으로 "주문 → 발송 → 배송 완료 → 구매 확정"을 한 화면 흐름으로 시연할 수 있다.

- 번들 규칙: 어떤 빌드에도 실제 관리자 계정 값(`KAIROS_ADMIN_*`)과 토스 시크릿 키가 없다. 데모가 아닌 빌드에는 데모 계정·실패 선택지가 없다. `check:bundle`이 확인한다.

## 13. 테스트

- **백엔드**: §5의 각 보강에 통합 테스트 + `OpenApiContractTest`. 환불 미리보기는 §5-1의 금액 사례를 전부 넣는다. 돈 계산 클래스는 바꾸지 않으므로 PIT 대상 변경은 없다 — 만약 바꾸게 되면 `./gradlew pitest` 임계값을 지킨다. `ArchitectureTest` 통과.

- **E2E(Playwright, 실제 백엔드 `local,demo` + Mock PG, 데모가 아닌 빌드)**: 각 spec은 F1처럼 고유 계정·판매자·상품을 스스로 만든다(`e2e/fixtures/api.ts` 확장). 3개:
  1. `c2-purchase.spec`: 상세에서 장바구니 담기 → 장바구니(판매자 2명, 5만 원 미만이라 배송비 2건) → 주문서(배송지 직접 입력) → 모의 결제 → 주문 완료 → 주문 내역·상세 → 판매자 발송 처리 → 배송 완료 → 구매자 구매 확정 → 주문 `구매 확정`. 결제하기 연타에도 주문이 하나만 생기는지 확인한다. 주문서를 연 뒤 판매자가 가격을 바꾸면 "금액 변경" 안내가 뜨고 다시 눌러 주문이 되는 것도 확인한다(422가 나지 않음).
  2. `c2-cancel.spec`: 판매자 2명 각 3만 원(합 6만 원, 무료배송) 주문 → 한 항목 취소 창에 **환불 예정 27,000원·배송비 차감 3,000원** → 취소 → 주문 상세의 환불 금액 27,000원 → 나머지 항목도 취소 → 누적 환불 = 결제 금액, 주문 `취소`. 판매자가 배송 전 항목을 취소하는 경로도 한 번(차감 없음).
  3. `c2-payment-failure.spec`: 결제창을 닫음 → 주문 상세에 결제 대기 → "결제하기"로 재결제 성공. 그리고 **결제 거절**: 데모가 아닌 빌드에는 실패 선택지가 없으므로 Playwright가 `/payments/confirm` 요청의 `paymentKey`를 `fail-` 접두사로 바꿔 보낸다(실제 백엔드가 거절·주문 취소·재고 복구) → 거절 안내 → 장바구니에 항목이 남아 있음 → 다시 주문해 성공. 같은 방식으로 `unknown-`도 한 번 보내 "확인 중" 화면이 뜨는 것을 확인한다(대사 작업 주기를 기다리지 않고 화면 표시까지만).
- **수동 점검**(완료 기준에 기록): 토스 테스트 결제창으로 결제 1건(테스트 키가 있을 때), 카카오 주소 검색으로 주소 입력, 데모 빌드의 실패 선택지 3종.
- **CI**: F1 워크플로(`check:api`, `lint`, `typecheck`, `test`, `build`) 그대로. E2E는 로컬에서 PR 전에 돌린다.

## 14. 완료 기준

- 시안 5개가 `design/`에 있고 사용자가 확인했다.
- §5 백엔드 보강이 OpenAPI → 구현 → 계약 테스트 순서로 끝났고 `./gradlew test`가 통과한다.
- `pnpm check:api`·`lint`·`typecheck`·`test`·`build`·`check:bundle`이 통과한다.
- §6의 모든 화면이 실제 백엔드로 동작하고 E2E 3개가 로컬에서 통과한다(F1의 기존 E2E도 그대로 통과).
- 수동 점검 결과가 PR 본문에 적혀 있다(하지 못한 항목은 "미실시"와 이유).
- CLAUDE.md: 문서 목록에 이 스펙과 F2 계획 추가, "현재 단계" 갱신, 프론트엔드 절에 F2 규칙(결제 방식 설정, 서버 강제 멱등 요청 목록, 금액은 서버 값만) 반영, 멱등 경로 추가 반영. README에 결제 방식 설정 방법.
- 끝나면 백그라운드 Gradle·도커·미리보기 서버를 정리한다.
