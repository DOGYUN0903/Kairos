# 프론트엔드 F4 반품·정산 화면 설계 (C4)

> 작성일: 2026-11-12 · 빌더 체크 반영: 2026-11-12 · 상위: `2026-11-11-frontend-f1-foundation-design.md`(기반·규칙), `2026-11-12-frontend-f2-purchase-design.md`(구매 화면·멱등 키 규칙), `2026-11-12-frontend-f3-benefits-design.md`(혜택 화면·마이페이지 틀), `2026-11-10-c4-returns-settlement-design.md`(반품·정산 도메인 규칙) · ADR 0003·0004·0005

## 1. 의도

F3까지 사고, 할인받고, 후기를 쓰는 화면이 생겼다. F4는 **배송 뒤 반품**과 **판매자 정산**을 화면으로 잇는다. 백엔드(C4)는 이미 있다.

둘 다 돈이다. 반품은 "얼마를 돌려받는가"가 사유와 주문 상태에 따라 달라지고(단순 변심이면 반품비 3,000원, 무료배송 주문이면 왕복 6,000원), 정산은 판매자에게 줄 돈의 계산 내역이다. 화면은 이 숫자를 **서버가 계산한 값 그대로** 보여주고, 환불이 실행되는 버튼(수거 확인)은 두 번 눌러도 한 번만 일어나며, 환불 결과가 불확실한 순간도 숨기지 않는다. 시연용 껍데기가 아니라 실제 쇼핑몰 수준의 완성도가 기준이다(사용자 결정).

표기: **사용자 결정**(확정) / **Claude 결정**(작성자 판단. "틀렸을 때 비용"을 적는다).

### 5-1. 반품 환불 미리보기 (사용자 결정)

문제: 구매자가 반품을 요청할 때 얼마를 돌려받는지 알려주는 API가 없다. 환불액은 수거 확인 때 계산된다.

- `GET /api/v1/orders/{orderId}/items/{orderItemId}/return-preview?reason=`(인증, 헤더 없음) → `ReturnPreview { orderItemId, reason, feeBearer, paidAmount, returnFee, outboundFeeRecovered, shippingFeeRefund, refundAmount, pointsRefund, productCouponReturnable }`. 금액은 전부 required int64, `productCouponReturnable`은 boolean(그 항목에 상품 쿠폰이 있었는지 — 실제 반환은 만료 전일 때만).
- 오류는 **반품 요청과 같은 판정**이다: 404 `ORDER_NOT_FOUND`/`ORDER_ITEM_NOT_FOUND`(남의 주문 포함), 409 `RETURN_NOT_ELIGIBLE`, `RETURN_WINDOW_EXPIRED`, `RETURN_ALREADY_REQUESTED`, 400 `RETURN_INVALID`(사유 enum 아님). 미리보기가 성공하면 바로 뒤의 요청도 성공해야 하고, 실패하면 같은 코드로 실패해야 한다.
- **돈 계산 클래스 변경(사용자 결정, 방법 A)**: 지금 `ReturnRefundCalculator.plan(order, returnId, fees)`은 승인된 반품만 계산한다(사유를 저장된 요청에서 읽고 상태를 검사한다). 금액을 정하는 본체(사유·항목·주문 → `ReturnRefundPlan`, 불변식 `check` 포함)를 **함수 하나로 추출**하고, 기존 `plan`과 새 미리보기 진입점이 **같은 본체**를 부른다. 이것이 F4에서 돈 계산 클래스를 건드리는 유일한 변경이며 **계산 결과는 바뀌지 않는다**: 기존 `ReturnRefundCalculatorTest`·`OrderReturnServiceTest`의 단언을 고치지 않고 그대로 통과해야 하고, `./gradlew pitest` 임계값을 지킨다. 현재 PIT 점수가 기준선(79%)이므로 새 진입점에 테스트를 충분히 붙여 점수가 내려가지 않게 한다.
- 추출 범위(빌더 체크 반영): 본체는 `(order, sellerOrder, item, reason, fees)`만으로 금액을 정하는 부분이다. `plan`의 상태 검사(승인된 반품인지)와 **"다른 항목이 `CANCEL_REQUESTED`·`RETURN_REFUNDING`이면 거절" 검사는 `plan`에만 남긴다**(반품 요청 API에는 이 검사가 없으므로 미리보기에 넣으면 요청은 되는데 미리보기만 실패한다).
- 미리보기의 자격 판정은 `Order.requestReturn`이 하는 검사를 **상태를 바꾸지 않는 함수로 추출해 그대로** 쓴다(검사 순서 포함: 열린 반품 → `RETURN_ALREADY_REQUESTED`; 주문·판매자 주문·항목 상태 → `RETURN_NOT_ELIGIBLE`; 기한 → `RETURN_WINDOW_EXPIRED`; 철회가 아닌 기존 반품 행 → `RETURN_ALREADY_REQUESTED`). `requestReturn`도 그 함수를 부르게 해 규칙을 한 곳에 둔다. 사유 enum 검증은 주문 조회보다 먼저다.
- 미리보기는 **예상값**이다. 계산은 호출 시점의 주문 상태로 한다. 실제 환불은 수거 확인 때 다시 계산하며, 그 사이 같은 주문의 다른 항목이 취소·반품되면 달라질 수 있다(발송 구간 3,000원 회수는 주문당 한 번, 판매자 귀책 반품의 발송 배송비 환불은 그 판매자 주문에서 마지막으로 끝나는 반품). API 설명에 이 점을 적는다.
- 조회만 한다. 주문·반품·결제·재고를 바꾸지 않는다.
- 테스트: C4 스펙 §5-1 예시 A(a2 변심: 반품비 3,000 + 발송 회수 3,000 → 14,000; 이어서 a1: 3,000만 → 37,000), B(불량: 배송비 3,000 환불 → 33,000), C(취소 차감 뒤 변심: 3,000만 → 27,000), D(포인트 3,000 반환, `paidAmount` 38,000, 쿠폰 반환 가능)의 숫자 그대로. **미리보기 금액 = 다른 변화가 없을 때 요청 → 승인 → 수거 확인의 실제 환불 금액**(일치 테스트). 기한 경계(7일 − 1초 성공, + 1초 `RETURN_WINDOW_EXPIRED`), 확정된 판매자 주문·이미 요청한 항목·거절된 항목의 오류 코드가 요청 API와 같음, 호출 전후 주문 응답 본문 동일.

### 5-2. 반품 응답의 표시용 필드 (사용자 결정 + Claude 세부)

문제: `ReturnRequestResponse`에는 상품 이름과 수량뿐이다.

- 추가(사용자 결정): `thumbnailUrl`(nullable — 상품 삭제·이미지 없음), `optionDisplayName`, `orderNo`, `sellerName`.
- 추가(Claude 결정): `paidAmount`(그 항목의 현금 결제 몫 — 환불 내역을 "결제 금액 − 반품비 = 환불"로 보여주려면 필요하다), `autoApproveAt`(nullable — `REQUESTED`일 때 `requestedAt + return-auto-approve-after`. 판매자 목록에 "○월 ○일 자동 승인"을 보이려면 필요하고, 기간 설정은 서버에만 있다). 틀렸을 때 비용: 낮음, 필드 두 개.
- 구매자·판매자·관리자의 목록·상세·요청 응답 모두 같은 스키마다. 이미지는 목록 한 페이지당 조회 한 번(F2 `findThumbnailUrls` 재사용), 판매자 이름은 주문 스냅샷(`seller_order.seller_name`)에서 읽는다.
- 테스트: 세 역할의 목록·상세에 필드가 있음, 삭제된 상품은 `thumbnailUrl=null`, 한 페이지의 이미지 조회 1회, `autoApproveAt`은 `REQUESTED`에서만 값이 있고 요청 시각 + 3일.

### 5-3. 정산 시연 데이터 (사용자 결정, demo 프로필 전용)

문제: 정산은 끝난 주의 확정 주문으로만 만들어진다. 화면에서 만든 주문은 확정 시각이 "지금"이라, 새 환경에서는 다음 주 월요일까지 정산을 만들 수 없다. E2E와 시연에서 정산 화면에 데이터가 없다.

- **demo 프로필에서만** 동작하는 시더가 "지난주(가장 최근에 끝난 월~일 기간)에 구매 확정된 판매자 주문"을 만든다. prod와 demo가 함께 켜지면 기동 실패하는 기존 규칙을 그대로 따른다(기존 데모 시더와 같은 위치·조건).
- 금액을 직접 써넣지 않는다. **기존 주문 생성·결제 승인(Mock PG)·발송·배송 완료·구매 확정·반품 흐름의 애플리케이션 서비스를 그대로 거쳐** 만들고, 시각만 지난주로 고정한다.
- **시각 고정 방법(Claude 결정, 빌더 체크 반영)**: 모든 주문·결제·배송·반품 서비스는 주입받은 `Clock`으로 시각을 정한다. demo 프로필에만 "시더가 실행하는 스레드에서만 시각을 옮길 수 있는 `Clock`" 빈을 두고(스레드 로컬 오프셋 — 다른 요청·스케줄러 스레드는 실제 시각), 공용 `ClockConfig`의 시스템 시계 빈은 다른 `Clock` 빈이 없을 때만 등록되게 한다. 운영(demo 아님)에서는 지금과 똑같이 시스템 시계 하나다. 서비스 코드에는 시각을 덮어쓰는 분기를 넣지 않는다. 틀렸을 때 비용: 낮음 — 공용 설정 한 줄(조건부 등록)과 demo 전용 클래스 하나.
- 주문 일시(`created_at`)는 JPA 감사 값이라 `Clock`을 쓰지 않는다. 감사 시각도 같은 `Clock` 빈을 쓰게 바꿀 수 있으면(운영에서는 시스템 시계라 동작이 같다) 그렇게 하고, 기존 테스트에 영향이 크면 바꾸지 않고 "주문 일시는 오늘, 확정은 지난주"로 보이는 것을 받아들인다(Claude 결정. 틀렸을 때 비용: 시연 화면에서 날짜가 어색해 보인다).
- 구성(빌더 체크 반영): 데모 상품에는 맞는 가격이 없으므로 **전용 상품**(50,000 / 30,000 / 20,000 / 15,000 / 30,000원)을 만든다. 기존 시더의 "판매 중 상품 20개" 보충 계산이 흔들리지 않게 별도 브랜드에 두거나 그 계산에서 제외한다. 구매자는 **전용 시연 구매자**를 쓴다(`buyer@kairos.demo`의 주문 내역을 더럽히지 않는다). 판매자 쿠폰 정책은 옮긴 시각 아래에서 만들어 주문 시점에 유효하게 한다. C4 예시의 장바구니 쿠폰과 포인트는 정산 금액에 영향이 없으므로 **넣지 않는다**(포인트는 잔액을 미리 만들 경로도 없다).
- 데이터는 C4 스펙 §8-7의 정산 예시와 같은 숫자가 나오게 구성한다: 데모 판매자(`seller@kairos.demo`, 수수료율 1000bp) 한 명에게 판매자 주문 3건 — 라인 **70,500**(매출 80,000, 판매자 쿠폰 5,000, 수수료 7,500, 배송비 3,000), **13,500**(불량 반품 뒤 남은 15,000, 수수료 1,500, 배송비 3,000, 반품비 3,000), **−3,000**(전부 불량 반품, 배송비 환불). 조정(−10,000)은 시더가 넣지 않는다 — 조정은 기간이 끝난 뒤 넣으면 다음 정산에 붙으므로 화면에서 직접 등록해 "미부착" 상태를 보인다. 조정 없이 합계 **81,000**.
- 시더는 정산을 **생성하지 않는다**. 관리자가 화면에서 지난주 정산을 생성한다(시연과 E2E의 일부).
- **정산 시작일과 생성 순서(Claude 결정, 빌더 체크 반영)**: 서버는 `kairos.settlement.start-date` 이후 기간을 오래된 순으로만 생성하게 한다. 설정값이 고정이면 "지난주 생성"은 시작일이 지난주일 때만 통과한다. 그래서 (1) **새 환경(E2E·로컬 시연)은 실행할 때 환경 변수로 시작일을 지난주 월요일로 준다** — E2E 실행 절차와 README에 적고, 지난주 월요일을 구하는 방법(한 줄 명령)을 함께 적는다. (2) 오래 떠 있는 시연 서버는 매주 월요일 03:00 작업이 지난주 정산을 자동으로 만든다 — 이 경우 관리자는 생성 대신 "이미 생성된 기간" 안내를 보고 확정·지급을 시연한다. 운영 코드의 생성 순서 규칙은 바꾸지 않는다. 틀렸을 때 비용: 낮음 — 시작일을 안 맞추고 띄우면 생성 창에 서버 안내가 뜨고, 환경 변수를 주고 다시 띄우면 된다.
- 멱등: **주 단위**로 판정한다 — 지난주 시연 주문 묶음이 이미 있으면 다시 만들지 않고, 주가 바뀌어 다시 실행되면(기동·`POST /demo/reseed`) 새 지난주 묶음을 만든다.
- 테스트: demo 프로필 통합 테스트에서 시더 실행 뒤 지난주 정산 생성 → 그 판매자 정산의 라인 금액이 70,500 / 13,500 / −3,000, 합계 81,000. 같은 주에 시더를 두 번 실행해도 주문 수 동일. 시더 실행 중 다른 스레드의 `Clock`은 실제 시각(동시 요청에 시각이 새지 않음). demo가 아닌 프로필에서는 시더 빈이 없음.
- 틀렸을 때 비용: 중간. 시더가 실제 규칙과 어긋나면 시연 화면의 숫자가 틀려 보인다(운영 코드에는 영향 없음). 그래서 서비스 경유와 예시 숫자 테스트를 요구한다.

### 5-4. 하지 않는 것

정산 생성 가능 기간 조회 API, 회원 검색 API, 판매자 수수료율 변경 API, 인덱스·마이그레이션, 위 §5-1 외의 돈 계산 클래스 변경.

## 7. 구매자 화면

### 7-1. 주문 상세 — 반품 요청

- 노출 조건(순수 함수, 서버 규칙과 같게 — 빌더 체크 반영): 판매자 주문 `DELIVERED` + 항목 `ORDERED` + `returnableUntil`이 지나지 않음 + **항목에 반품 요청이 없거나 철회(`WITHDRAWN`)된 것뿐**. 거절(`REJECTED`)과 관리자 중단(`CANCELED_BY_ADMIN`)은 서버가 재요청을 받지 않으므로 버튼을 보이지 않는다. 버튼 옆에 "○월 ○일 ○○:○○까지 반품 가능"(`returnableUntil` 서버 값). 기한이 지났으면 버튼 없이 "반품 가능 기간이 지났습니다". 거절된 항목은 "반품이 거절된 상품입니다", 중단된 항목은 "반품이 중단된 상품입니다"와 반품 상세 링크(둘 다 다시 요청할 수 없다).
- **요청 창**: 상품 요약, 사유 라디오(단순 변심 / 상품 불량 / 오배송), 상세 내용(선택, 500자), **환불 예정 금액**.
  - 사유를 고르면 `return-preview`를 부른다(사유가 바뀔 때마다). 표시: 결제 금액(`paidAmount`), 반품비(`returnFee`, 0이면 숨김), 발송 배송비 회수(`outboundFeeRecovered`, 0이면 숨김 — "무료배송으로 받은 상품이라 발송 배송비 3,000원이 함께 차감됩니다" 설명), 배송비 환불(`shippingFeeRefund`, 0이면 숨김), **환불 예정 금액**(`refundAmount`), 포인트 반환(`pointsRefund`, 0이면 숨김), 상품 쿠폰 안내(`productCouponReturnable`이면 "사용한 상품 쿠폰은 유효기간이 남아 있으면 돌아옵니다"). 부담 주체 문구: `feeBearer=BUYER` "반품 배송비는 구매자 부담입니다", `SELLER` "판매자 부담이라 차감이 없습니다".
  - **"예상" 표시**: 금액 제목은 "환불 예정 금액"이고, 아래에 "실제 환불 금액은 판매자가 상품을 받은 뒤 확정됩니다. 같은 주문의 다른 상품을 취소·반품하면 달라질 수 있습니다"를 항상 보인다.
  - 사유를 고르기 전에는 금액 영역에 "사유를 선택하면 환불 예정 금액을 보여 드립니다". 미리보기가 로딩·실패 중이면 요청 버튼을 막지 **않는다**(미리보기는 안내일 뿐 요청의 전제가 아니다 — 실패 시 "환불 예정 금액을 불러오지 못했습니다" 안내). 단 미리보기가 409(`RETURN_NOT_ELIGIBLE`·`RETURN_WINDOW_EXPIRED`·`RETURN_ALREADY_REQUESTED`)면 서버 메시지를 보이고 요청 버튼을 막는다.
  - 제출: `useIdempotentSubmit`으로 `POST /orders/{orderId}/items/{orderItemId}/returns`(`reason`, `detail`). 성공 → 토스트 "반품을 요청했습니다. 판매자가 3일 안에 확인합니다"(3일은 문구), 주문 상세·반품 목록 무효화. 409 → 창을 닫고 서버 메시지 토스트 + 주문 상세 다시 읽기. 400 `RETURN_INVALID` → 폼 상단.
- **항목의 반품 상태**(주문 항목의 `returnRequest` 요약): `REQUESTED` "반품 요청됨" + "철회", `APPROVED` "반품 승인 · 수거 대기", `REFUNDING` "환불 확인 중", `COMPLETED` "반품 완료" + 환불 금액(`refundAmount`), `REJECTED` "반품 거절", `CANCELED_BY_ADMIN` "반품 중단됨", `WITHDRAWN`은 상태를 보이지 않고 반품 요청 버튼을 다시 보인다. 각 상태에서 반품 상세 링크.
- **철회**: `REQUESTED`일 때만. 확인 창 뒤 `DELETE /returns/{returnId}`(키 없음, 이미 철회면 200). 409 `RETURN_INVALID_STATE_TRANSITION`(그사이 승인됨) → 서버 메시지 + 다시 읽기.
- **자동 재조회**: 항목이 `RETURN_REFUNDING`이면 F2의 취소 확인 중과 같은 규칙으로 다시 읽는다(3초 간격, 최대 2분).
- **구매 확정**: 확인 창에 "확정하면 이 판매자의 상품은 반품할 수 없습니다"를 더한다. 409 `SELLER_ORDER_HAS_OPEN_RETURN` → "반품이 진행 중인 상품이 있어 확정할 수 없습니다. 반품을 철회하거나 완료된 뒤 다시 시도해 주세요". 판매자 주문에 `hasOpenReturn`이면 구매 확정 버튼을 비활성으로 두고 같은 이유를 보인다.
- 판매자 주문이 `allItemsReturned`면 상태 칩을 "구매 확정" 대신 "전체 반품"으로 보인다.
- 결제 요약: 부분 반품 뒤 결제가 `PARTIAL_CANCELED`인 것은 기존 표시 그대로다. 전부 반품인데 누적 환불이 결제 금액보다 적은 경우(구매자 부담 반품비)를 위해, 환불 금액 줄 아래에 반품이 완료된 항목이 있으면 "반품 배송비가 차감된 금액입니다"를 보인다(차감액 합을 화면이 계산하지 않는다 — 각 반품의 금액은 반품 상세에서 본다).

### 7-2. 반품 내역 `/my/returns`

- `GET /returns/me?page&size`(최신 요청순): 카드 — 상품 이미지·이름·옵션·수량, 판매자, 사유, 상태 칩, 요청일, 환불 금액(`COMPLETED`일 때 `refundAmount`, 그 전에는 "수거 확인 뒤 확정"). 카드 → 상세.
- 빈 상태: "반품 내역이 없습니다" + 주문 내역 링크.

### 7-3. 반품 상세 `/my/returns/[returnId]`

- `GET /returns/{returnId}`. 404 → 없음 페이지.
- 진행 단계 표시: 요청 → 승인 → 수거 확인 → 환불 완료(거절·철회·중단은 그 자리에서 끝난 것으로 표시). 각 단계의 일시(`requestedAt`, `decidedAt`, `receivedAt`, `completedAt`)와 승인 주체(`decidedBy`: 판매자 / 자동 승인 / 관리자).
- 사유·상세 내용, 거절 사유(`rejectReason`), 주문번호(주문 상세 링크).
- **환불 내역**(`COMPLETED`·`REFUNDING`일 때, 전부 서버 값): 결제 금액(`paidAmount`), 반품비(`returnFee`), 발송 배송비 회수(`outboundFeeRecovered`), 배송비 환불(`shippingFeeRefund`), 환불 금액(`refundAmount`), 포인트 반환(`pointsRefund`). 0인 줄은 숨긴다. 그 전 상태에서는 "환불 금액은 판매자가 상품을 받은 뒤 확정됩니다".
- `REQUESTED`면 철회 버튼, `REFUNDING`이면 자동 재조회.

## 8. 판매자 화면

### 8-1. 반품 관리 `/seller/returns`, `/seller/returns/[returnId]`

- 목록 `GET /seller/returns?status&page&size`: 상태 탭(전체 / 요청 / 승인 · 수거 대기 / 환불 확인 중 / 완료 / 거절, URL 쿼리 `status`). 표 — 요청일, 주문번호, 상품(이미지·이름·옵션·수량), 사유, 부담 주체(구매자/판매자), 상태, `REQUESTED`면 "○월 ○일 자동 승인"(`autoApproveAt`).
- 상세 `GET /seller/returns/{returnId}`: 사유·상세 내용, 주문번호(판매자 주문 상세 링크), 진행 일시, 환불 내역(구매자 상세와 같은 컴포넌트 + `sellerBorneFee`가 0보다 크면 "판매자 부담 반품비 3,000원 — 정산에서 차감됩니다").
- **승인**: `REQUESTED`일 때. 확인 창 뒤 `PATCH …/approve`(키 없음, 이미 승인이면 현재 상태). 안내: 사유는 바꿀 수 없다 — "불량이 아니라고 판단되면 거절해 주세요. 관리자가 다시 확인합니다".
- **거절**: `REQUESTED`일 때. 사유(필수, 500자) 창 뒤 `PATCH …/reject`. 안내: "거절하면 구매자는 같은 상품을 다시 반품 요청할 수 없습니다".
- **수거 확인**: `APPROVED`일 때. 확인 창 "상품을 받으셨나요? 확인하면 구매자에게 환불이 실행되며 되돌릴 수 없습니다" 뒤 `PATCH …/receive`(키 없음, 처리 중 재호출 막기 — 서버가 멱등). 응답 상태에 따라: `COMPLETED` → "환불을 완료했습니다. 환불 금액 ○원"(`refundAmount`), `REFUNDING` → "환불을 확인하고 있습니다"(상세가 3초 간격으로 다시 읽는다, 최대 2분), 409 `PAYMENT_CANCEL_FAILED` → "환불이 거절되었습니다. 반품은 승인 상태로 돌아갔습니다. 잠시 후 다시 시도해 주세요". 응답을 못 받은 경우(네트워크 오류) → "결과를 확인하지 못했습니다" + 상세 다시 읽기(자동 재시도 없음).
- 변심 반품 완료 시 재고가 복구되고, 불량·오배송은 복구되지 않는다는 안내를 수거 확인 창에 사유별로 보인다("재고는 자동으로 복구되지 않습니다. 재판매할 수 있으면 상품 관리에서 재고를 수정해 주세요").
- 409 `RETURN_INVALID_STATE_TRANSITION` → 서버 메시지 + 다시 읽기(그사이 구매자 철회·자동 승인 등).

### 8-2. 정산 `/seller/settlements`, `/seller/settlements/[settlementId]`

- 목록 `GET /seller/settlements?page&size`(기간 시작 최신순): 기간(`periodStart` ~ `periodEnd`), 지급 예정일(`payoutDate`), 상태(정산 생성 / 확정 / 지급 완료), 포함 주문 수(`lineCount`), 합계(`totalAmount`), **지급액**(`payableAmount`). 빈 상태: "아직 정산이 없습니다. 정산은 매주 월요일에 지난주 구매 확정 주문으로 만들어집니다".
- 상세 `GET /seller/settlements/{id}`:
  - **계산 내역**(전부 서버 값, 화면은 더하거나 빼지 않는다): 상품 매출(`salesAmount`), 판매자 쿠폰 할인(−`sellerCouponDiscount`), 수수료(−`commissionAmount`), 배송비(+`shippingFeeOwed`), 판매자 부담 반품비(−`returnFeeBorne`), 조정(`adjustmentAmount`, 부호 그대로), **합계**(`totalAmount`), **지급액**(`payableAmount`). 0인 줄도 숨기지 않는다(정산 명세는 항목이 고정이어야 읽기 쉽다 — Claude 결정). 부호는 표시용 문자만 붙인다.
  - 합계가 음수면: "합계가 0원보다 적어 이번 지급액은 0원입니다. 부족한 금액은 다음 정산으로 넘어갑니다"와, 조정 목록의 `CARRY_OVER` 행("이월").
  - **포함된 주문 표**(`lines`): 주문번호(판매자 주문 상세 링크), 확정일, 매출, 판매자 쿠폰, 수수료 기준액, 수수료율(`commissionRateBp` → `formatBp`), 수수료, 배송비, 반품비, 라인 금액(`lineAmount`). 음수 라인은 음수 그대로.
  - **조정 표**(`adjustments`): 종류(수동 조정 / 이월), 금액, 사유.
  - 안내: "플랫폼이 부담한 쿠폰·포인트·무료배송은 정산에서 차감되지 않습니다", 지급 완료면 지급일·메모(`paidMemo`).

## 9. 관리자 화면

### 9-1. 반품 `/admin/returns`, `/admin/returns/[returnId]`

- 판매자 반품 관리의 표·상세 컴포넌트를 재사용한다. 목록 필터: 상태, 판매자 ID, 회원 ID(URL 쿼리, `parseId`). 표에 판매자 이름 열을 더한다.
- 버튼: **승인**(`REQUESTED` 또는 `REJECTED` — 거절된 건 재승인. 409 `RETURN_NOT_ELIGIBLE`은 "이미 구매 확정된 주문이라 승인할 수 없습니다. 정산 조정으로 처리해 주세요"), **대신 수거 확인**(`APPROVED` — 판매자 수거 확인과 같은 창·응답 처리), **중단**(`APPROVED` — "구매자 요청으로 반품을 중단합니다. 상품은 주문 상태로 돌아가며, 구매자는 이 상품을 다시 반품 요청할 수 없습니다" 확인 뒤 `PATCH …/cancel`). 중단 뒤 재요청이 안 되는 것은 현재 서버 규칙이다(C4 스펙은 "거절만 최종"이라고 적었지만 구현은 철회만 재요청을 허용한다). F4에서는 서버 규칙을 바꾸지 않고 화면 문구를 맞춘다(Claude 결정. 틀렸을 때 비용: 중단 뒤 다시 반품하려는 구매자는 CS로 가야 한다 — 서버 규칙을 바꾸는 것은 별도 결정).

### 9-2. 정산 `/admin/settlements`, `/admin/settlements/[settlementId]`

- 목록 `GET /admin/settlements?sellerId&status&page&size`: 판매자(이름, 상태가 승인이 아니면 표시), 기간, 지급 예정일, 상태, 합계, 지급액.
- **주간 정산 생성**: "정산 생성" → 창에서 기간 시작일(월요일)을 고른다. 기본값은 **가장 최근에 끝난 주의 월요일**(KST, `lib/datetime.ts`의 순수 함수로 계산 — 금액 계산이 아니다). 월요일이 아닌 날짜와 아직 끝나지 않은 주는 화면에서 먼저 막는다. `useIdempotentSubmit`으로 `POST /admin/settlements/generate`. 결과 표시(`GenerateSettlementResult`): 기간, 대상 판매자 수, 생성·건너뜀·실패 수, `alreadyGenerated`면 "이미 생성된 기간입니다". 400 `SETTLEMENT_PERIOD_INVALID` → 서버 메시지 + "앞선 기간이 아직 생성되지 않았다면 그 기간부터 생성해 주세요". 성공 뒤 목록 무효화. `failedCount > 0`이면 경고로 "다시 생성하면 실패한 판매자만 만들어집니다".
  - Claude 결정: "아직 생성되지 않은 가장 오래된 주"를 알려주는 API가 없어 기본값을 지난주로 둔다(브레인스토밍에서 한 말과 다르다). 틀렸을 때 비용: 낮음 — 작업이 여러 주 밀린 경우 관리자가 오류 안내를 보고 앞 기간부터 고른다. 조회 API를 더하면 기본값을 바꿀 수 있다.
- 상세 `GET /admin/settlements/{id}`: 판매자 정산 상세와 같은 컴포넌트 + 판매자 정보(이름·상태) + 버튼.
  - **확정**: `GENERATED`일 때. 확인 창 뒤 `PATCH …/confirm`.
  - **지급 완료**: `CONFIRMED`일 때. 메모(선택, 200자) 창 — "지급액 ○원을 지급 완료로 표시합니다(실제 이체는 따로 진행합니다)" — 뒤 `PATCH …/pay`. 지급액이 0원이면 "지급할 금액이 없는 정산입니다. 지급 완료로 닫습니다".
  - 409 `SETTLEMENT_INVALID_STATE_TRANSITION` → 서버 메시지 + 다시 읽기.
  - "이 판매자의 조정 보기" 링크.

### 9-3. 정산 조정 `/admin/settlements/adjustments`

- 판매자 ID 입력(URL 쿼리 `sellerId`, `parseId`) → `GET /admin/sellers/{sellerId}/settlement-adjustments`: 종류, 금액, 사유, 근거 주문, 부착 여부(붙은 정산 링크 / "다음 정산에 반영 예정").
- **등록**: 구분(가산 / 차감) + 금액(양의 정수 원) + 사유(필수, 500자) + 근거 판매자 주문 ID(선택). 요청의 `amount`는 차감이면 음수로 보낸다(부호 붙이기 — 곱셈이 아니라 `money.ts`의 부호 함수로). `useIdempotentSubmit`으로 `POST /admin/sellers/{sellerId}/settlement-adjustments`. 안내: "조정은 다음에 만들어지는 정산에 반영됩니다. 이미 끝난 기간의 정산을 아직 생성하지 않았다면, 그 기간이 끝난 뒤 등록한 조정은 그다음 정산에 붙습니다". 400 `SETTLEMENT_ADJUSTMENT_INVALID` → 폼 상단.
- **삭제**: 미부착 `MANUAL` 조정만. 확인 뒤 `DELETE /admin/settlement-adjustments/{id}`. 409 `SETTLEMENT_ADJUSTMENT_APPLIED` → "이미 정산에 반영된 조정은 삭제할 수 없습니다" + 다시 읽기. `CARRY_OVER`와 부착된 조정에는 삭제 버튼이 없다.

## 10. 프론트 구조와 공통 규칙

- 디렉터리(Claude 결정): `features/returns`(구매자 요청 창·내역·상세, 상태·사유 문구, 환불 내역 컴포넌트 — 판매자·관리자가 공유), `features/seller/returns`, `features/seller/settlements`, `features/admin/returns`, `features/admin/settlements`, `features/settlements`(정산 상세 컴포넌트·상태 문구 — 판매자·관리자 공유).
- **금액**: 화면의 환불액·반품비·정산 금액은 전부 서버 값이다. F4에서 새로 허용되는 프론트 계산은 **조정 금액의 부호 붙이기**(차감이면 음수)뿐이다. 날짜 계산(가장 최근에 끝난 주의 월요일, 월요일 판정)은 금액이 아니지만 `lib/datetime.ts`의 순수 함수로만 하고 KST 경계 테스트를 둔다.
- **멱등성**: 서버가 키를 강제하는 요청 — 반품 요청, 정산 생성, 정산 조정 등록 — 은 `useIdempotentSubmit`으로 보낸다. 철회, 승인, 거절, 수거 확인, 중단, 정산 확정·지급 완료, 조정 삭제는 키 없이 처리 중 재호출을 막고 서버의 멱등 처리에 기댄다. **수거 확인은 응답을 못 받아도 자동으로 다시 보내지 않는다**(사용자가 상세를 보고 판단).
- **에러**: 새 코드를 `errors.ts` 표에 넣는다(`RETURN_NOT_FOUND`·`SETTLEMENT_NOT_FOUND` → 페이지, `RETURN_INVALID`·`SETTLEMENT_ADJUSTMENT_INVALID`·`SETTLEMENT_PERIOD_INVALID` → 폼, 나머지는 각 절의 화면 동작 또는 서버 메시지 토스트).
- **상태 칩**: 반품 상태 7가지, 정산 상태 3가지, 조정 부착 여부, 주문 항목의 반품 상태 문구(F2에서 칩 문구만 정의해 둔 것을 §7-1 문구로 맞춘다).
- **쿼리 키**: `returns`(내 목록·상세·미리보기), `sellerReturns`, `adminReturns`, `sellerSettlements`, `adminSettlements`, `adminAdjustments`. 무효화: 반품 요청·철회 → 주문 상세·반품 목록; 승인·거절·수거 확인·중단 → 해당 반품 목록·상세; 수거 확인 완료 → (구매자 쪽은 다른 세션이라 무효화 대상이 아님); 정산 생성·확정·지급 → 정산 목록·상세; 조정 등록·삭제 → 조정 목록.
- **F3 후속 수정**: 주문 생성 성공 직후 `useCreateOrder`가 견적 캐시를 무효화해, 아직 켜져 있는 견적 조회가 한 번 더 나가 409(쿠폰 사용됨)를 받는다(화면 영향 없음, 콘솔 오류). 주문 성공 뒤에는 견적을 다시 받지 않게 한다(무효화하되 재요청하지 않거나 캐시를 지운다). E2E에서 주문 생성 뒤 `POST /orders/quote` 409가 없음을 확인한다.

## 11. 데모

- 데모 바는 그대로다. 구매자(반품 요청) → 판매자(승인·수거 확인) → 구매자(환불 확인) → 관리자(정산 생성·확정·지급) → 판매자(정산 확인) 흐름을 화면에서 시연한다.
- 정산 시연 데이터(§5-3)는 백엔드 demo 프로필에만 있다. 프론트에 데모 전용 코드를 더하지 않는다. 번들 규칙은 그대로다(`check:bundle`).

- **컴포넌트**: 반품 요청 창(사유 변경 시 미리보기 재요청, 409면 요청 차단, 미리보기 실패는 요청을 막지 않음, 제출 키), 수거 확인(연타에 요청 1회, `REFUNDING` 표시, 실패 안내), 조정 등록(키, 부호).
- **E2E(Playwright, 실제 백엔드 `local,demo` + Mock PG, 데모가 아닌 빌드, 새 빈 스키마에서 한 번에)**: 금액은 `toHaveText`로 정확히 비교한다.
  1. `c4-return-change-of-mind.spec`: 판매자 S의 40,000원 + 20,000원 주문(무료배송) → 발송·배송 완료 → 20,000원 항목 반품 요청 창에서 변심 선택 → 환불 예정 **14,000원**(반품비 3,000원, 발송 배송비 회수 3,000원) → 요청(연타해도 한 건) → 판매자 승인 → 수거 확인 → "환불 금액 14,000원" → 구매자 반품 상세의 환불 내역 14,000원 → 남은 40,000원 항목 미리보기 **37,000원**(반품비 3,000원만) → 반품 완료 → 판매자 주문 "전체 반품", 주문 상세 환불 금액 51,000원.
  2. `c4-return-defective.spec`: 판매자 T의 30,000원 주문(배송비 3,000원 구매자 부담) → 불량 선택 → 환불 예정 **33,000원**(차감 없음, 배송비 환불 3,000원) → 요청 → 철회 → 다시 요청 → 판매자 거절(사유) → 구매자 화면 "반품 거절"과 사유, 다시 요청 불가 → 관리자 재승인 → 관리자 대신 수거 확인 → 환불 33,000원. 반품이 열린 상태에서 구매 확정 버튼이 막혀 있음도 확인한다.
  3. `c4-settlement.spec`(§5-3 시연 데이터 사용, 백엔드를 정산 시작일 = 지난주 월요일로 띄운다): 관리자 정산 생성(지난주) → 결과에 생성 1건 이상 → 데모 판매자 정산 상세: 라인 **70,500원 / 13,500원 / −3,000원**, 합계·지급액 **81,000원** → 확정 → 지급 완료(메모) → 같은 기간 다시 생성하면 "이미 생성된 기간" → 조정 −10,000원 등록 → "다음 정산에 반영 예정" → 삭제 → 판매자 로그인(`seller@kairos.demo`) 정산 목록·상세에 같은 금액과 "지급 완료".
- **화면 캡처 대조**(PR 전 필수 — F3 교훈): 주요 화면을 실제로 띄워 캡처하고 시안과 대조한다(구매자 반품 요청 창·반품 상세·주문 상세, 판매자 반품 목록·상세·정산 목록·상세, 관리자 정산 목록·생성 결과·상세·조정, 관리자 반품). 결함은 고친 뒤 다시 캡처한다.
