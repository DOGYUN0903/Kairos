# Kairos 커머스 확장 로드맵

> 작성일: 2026-11-09 · 상위 설계 `2026-11-08-kairos-design.md`의 방향을 바꾼다. 하위 프로젝트는 각각 따로 설계 문서를 둔다.

## 1. 의도와 스토리

Kairos는 처음에 타임딜 전용 서비스로 시작했다. 사용자는 이것을 **"일반 마켓플레이스로 운영하던 중에 핫딜 기능이 새로 추가되고, 오픈 순간의 트래픽이 쇼핑몰 전체를 흔드는"** 이야기로 바꾸기로 했다(사용자 결정). 이유는 세 가지다.

- 실무에서 실제로 일어나는 상황이라, 면접관이 공감하고 흥미를 갖는다.
- 핫딜이 일반 기능(상품 조회, 일반 주문)에 주는 영향까지 측정할 수 있다. 나중에 서비스를 나눌 때 가장 강한 근거가 된다.
- 운영하는 동안 쌓인 주문, 리뷰, 상품 데이터가 의미 있는 대용량 데이터(100만~1,000만 건)가 된다.

**프로젝트 한 문장 (유지)**: 데이터 정합성을 지키면서 대용량 데이터와 트래픽을 견디는 구조를 모놀리식에서 MSA까지 단계적으로 만들고, 장애가 나도 버티게 한다.

**보여 주는 대상**: 포트폴리오를 보는 면접관이 데모 서버(AWS)에서 사용자, 판매자, 관리자 화면을 직접 써 본다.

## 2. 결정 사항 (사용자 결정)

- 저장소를 새로 만들지 않는다. 같은 저장소에서 도메인만 다시 짠다. 기존 타임딜 작업은 태그(`v0-hotdeal-prototype`)로 남긴다.
- 형태: **여러 브랜드가 입점하는 마켓플레이스.**
- 기능 범위: 브랜드 입점, 판매자 관리(정산까지), 관리자 화면, 카테고리, 상품 옵션, 장바구니, 쿠폰, 포인트 적립과 사용, 리뷰, PG 테스트 연동, 핫딜(나중에 추가).
- 결제: 토스페이먼츠 테스트 모드와 Mock PG를 같은 인터페이스 뒤에 둔다. 데모는 실제 PG 테스트 모드를 쓰고, 부하 테스트와 자동 테스트는 Mock PG를 쓴다. 두 구현은 같은 흐름(주문 생성 → 결제 대기 → 승인)을 따른다.
- 배송은 넣지 않는다(결제 완료 → 구매 확정을 판매자나 시간 경과로 처리하는 정도).
- 단계 전환 원칙: 단일 인스턴스 → ALB 다중 인스턴스 → MSA. 다음 단계로 넘어갈 때는 반드시 측정한 근거가 있어야 한다(CLAUDE.md).

## 3. 하위 프로젝트와 순서 (작성자 제안)

| 순서 | 하위 프로젝트 | 내용 | 나중 단계와의 연결 |
|---|---|---|---|
| C1 | 판매자와 상품 | 브랜드 입점 신청과 관리자 승인, 판매자 계정, 카테고리(2단계), 상품과 옵션(옵션 단위 재고), 상품 목록·검색·상세 | 3-2 검색, 페이징, 정렬 |
| C2 | 구매 | 장바구니, 다중 판매자 주문(판매자별 주문 항목), 결제(PG 테스트 연동과 Mock PG), 결제 대기 정리, 구매 확정, 취소 | 3-1 동시성(여러 옵션 동시 차감), 4 Saga |
| C3 | 혜택과 후기 | 쿠폰(정액·정률, 최소 금액), 포인트 적립과 사용, 리뷰(구매 확정자만, 평균 별점) | 정합성(결제 실패 시 쿠폰·포인트 복구), 3-2 집계 |
| C4 | 정산 | 판매자별 매출 집계, 수수료, 정산 내역 | 3-2 대용량 집계, 배치 |
| C5 | 운영 데이터 | 의미 있는 대용량 데이터 생성(주문, 리뷰, 상품) | 3-2 |
| C6 | 핫딜 추가 | 특정 상품 옵션을 정해진 시각에 한정 수량과 특가로 판매 | 일반 트래픽이 흐르는 중의 기준선 재측정 → 3-1 |

- 각 하위 프로젝트는 **설계 → 계획 → 구현 → PR** 순서로 하나씩 진행한다.
- 기존 deal·order·payment 코드는 C1·C2에서 새 도메인에 맞게 다시 짠다. 기존 Phase 3-1 계획(`2026-11-09-phase3-1-concurrency.md`)은 C6 이후에 다시 손봐서 재개한다. 락 방식 비교, 결제 분리, 정리 작업 같은 설계 원칙은 그대로 쓴다.
- Phase 2 기준선(빈 시스템에서 핫딜만 측정)은 비교 자료로 남긴다.

## 4. 화면 (작성자 제안, C1 설계 때 확정)

- 사용자, 판매자, 관리자 화면 세 개를 만든다.
- 진행 방식(사용자 결정): 디자인 → 시안 → 프론트 제작. 화면은 Claude가 만든다(Next.js).
- 시점: 백엔드 API를 먼저 만들고, 디자인 방향과 시안은 C1과 함께 시작한다. 화면 구현은 하위 프로젝트마다 API가 나온 뒤에 붙인다. 마지막에 몰아서 만들면 범위가 커지고, 중간에 화면으로 확인할 수 없기 때문이다.

## 5. 하지 않을 것

- 배송, 반품과 교환, 실시간 채팅, 추천 알고리즘, 검색 엔진(Elasticsearch)은 지금 넣지 않는다. 검색 엔진은 3-2에서 근거가 생기면 검토한다.
- 선착순 쿠폰처럼 동시성이 핵심인 기능은 C3에서 빼고 핫딜 단계에서 다룬다.
- 실제 결제(라이브 키)는 하지 않는다.

## 6. 범위를 지키는 규칙

새 기능 아이디어가 나오면 프로젝트 한 문장에 비춰 본다. 정합성, 대용량, 트래픽, 장애 중 어디에도 기여하지 않으면 미룬다.
