# C3 혜택·후기 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** C2 구매 위에 쿠폰(상품·장바구니), 포인트(적립·사용·만료·되돌림), 후기(작성·수정·삭제·판매자 답글·적립금), 상품 좋아요를 얹되, 돈(할인·환불·되돌림)과 집계(별점·후기 수·좋아요 수)가 실제 행과 어긋나지 않게 구현한다.

**Architecture:** 새 모듈 `benefit`(쿠폰 정책·발급 쿠폰·포인트 잔액/로트/원장)과 `review`(후기·답글)를 추가하고, 좋아요와 후기 집계는 `catalog`의 `product` 컬럼·`product_like` 테이블로 둔다. `order`는 `benefit`을 포트 `BenefitApplier`(주문 생성 시 쿠폰·포인트 확정), `BenefitReverter`(취소·만료 되돌림), `PointEarner`(구매 확정 적립)로만 부르고 구현은 `order.infrastructure`가 `benefit.application` 서비스를 호출한다. 할인·포인트 배분은 order 도메인의 순수 함수 `DiscountAllocator` 한 곳에서만 계산하고 항목별 `paidAmount`를 저장한다. 주문 생성 트랜잭션이 order·catalog(재고)·benefit(쿠폰 상태·포인트)을 함께 바꾸는 것은 ADR 0003의 연장으로 **ADR 0004**에 남긴다(락 순서 포함). 0원 주문은 PG 없이 `OrderPaymentService`의 승인 확정 단계를 재사용해 즉시 `PAID`로 만든다.

**Tech Stack:** Kotlin 2.3, Spring Boot 4.1(`TransactionTemplate`, `@Scheduled`), JDK 21, MySQL 8.4, Flyway, QueryDSL 7.7, JUnit5, Testcontainers, ArchUnit. 새 의존성 없음(property 식 테스트는 `kotlin.random.Random(seed)`로 직접 만든다).

**Spec:** `docs/superpowers/specs/2026-11-10-c3-benefits-reviews-design.md`(실행자는 반드시 함께 읽는다. 특히 4-2장 할인 계산 규칙, 5-2장 로트·원장, 6장 계산 예시, 7장 주문 흐름 변경, 14장 증명할 테스트). 상위: `docs/superpowers/specs/2026-11-09-c2-purchase-design.md`, C2 계획 `docs/superpowers/plans/2026-11-09-c2-purchase.md`(기존 order·payment 구조).

## Global Constraints

- 루트 패키지 `com.dogyun.kairos`. 새 모듈 `benefit`, `review`; 계층 `presentation/ application/ domain/ infrastructure/`, 의존 방향 `presentation → application → domain ← infrastructure`. `domain`은 순수 Kotlin. `ArchitectureRules.modules`에 `benefit`, `review`를 추가하고 규칙을 완화하지 않는다.
- 다른 모듈 호출: 호출하는 쪽 `application`에 인터페이스, 자기 `infrastructure`에서 상대 `application` 서비스 호출. 모듈 간 DTO에 도메인 타입 노출 금지. 이 계획의 호출 방향: order → benefit(`BenefitApplier`, `BenefitReverter`, `PointEarner`), review → order(`OrderItemReader`), review → benefit(`ReviewRewardGranter`), review → catalog(`ProductRatingUpdater`), review → file(`ReviewImageFileReader`), review → member(`ReviewerNameReader`), benefit → catalog(`BenefitProductReader`).
- JPA 엔티티는 `BaseEntity` 상속 + `@SQLRestriction("status = 'ACTIVE'")`, 소프트 딜리트만. 도메인 상태 컬럼명 `policy_status`, `coupon_status`; 좋아요는 `liked BIT`(스펙 9장, `status`가 아닌 도메인 플래그). 쿠폰 수량·사용 상태·좋아요 플래그·상품 집계는 모두 **조건부 UPDATE의 영향 행 수**로 판정하고 비관적 락·Redis를 쓰지 않는다. 유일한 행 락은 `member_point`(FOR UPDATE)와 C2의 주문 행 락이다.
- 락 순서(스펙 3·12장, ADR 0004): 주문 생성 **`member_point → coupon → sku`**(주문 행은 INSERT라 잠그지 않음); 취소·만료·확정·결제 실패 **`orders(FOR UPDATE) → member_point → coupon → sku`**(benefit 되돌림을 재고 복구보다 **먼저** 호출한다). 후기 적립은 `member_point`만, 좋아요는 `product_like → product`만.
- Flyway 새 버전만: `V17__benefit.sql`, `V18__order_benefit_columns.sql`, `V19__product_stats_and_like.sql`, `V20__review.sql`. 인덱스는 PK/UNIQUE만: `coupon(policy_id, member_id)`, `member_point(member_id)`, `point_transaction(transaction_type, ref_type, ref_id)`, `review(order_item_id)`, `product_like(product_id, member_id)`.
- 금액·포인트는 원/P 단위 `Long`, 정률은 bp(`Int`, 10% = 1000)이며 **버림**. 설정값(`kairos.benefit.*`): 적립률 **100bp(1%)**, 최소 사용 잔액 **1,000**, 사용 단위 **10**, 사용 상한 **3000bp(30%)**, 적립 만료 **365일**, 환불 로트 만료 **30일**, 후기 적립 텍스트 **100P**/사진 **500P**; `kairos.review.write-deadline` **90일**; `kairos.jobs.point-expiry-delay` **1h**. 무료배송 기준은 C2 그대로 할인 전 `itemsAmount` ≥ 50,000(스펙 4-3).
- 적용 순서 **상품 쿠폰 → 장바구니 쿠폰 → 포인트 → PG**. 포인트 조건: 0 이상 10의 배수(아니면 `POINT_INVALID_AMOUNT`), 0보다 크면 잔액 ≥ 1,000 이고 `pointsToUse` ≤ `floor(쿠폰 후 상품 금액 × 30%)`를 10P 단위로 내린 값(아니면 `POINT_EXCEEDS_LIMIT`), 잔액 부족은 `POINT_INSUFFICIENT`(409). 쿠폰 후 상품 금액이 0이면 포인트 사용 불가(`POINT_EXCEEDS_LIMIT`).
- 포인트 원장 `UNIQUE(transaction_type, ref_type, ref_id)` 키 목록: `EARN_PURCHASE/PURCHASE_CONFIRM/sellerOrderId`, `EARN_REVIEW/REVIEW/reviewId`, `USE/ORDER/orderId`, `REFUND/ORDER/orderId`, `REFUND/ORDER_ITEM/orderItemId`, `EXPIRE/POINT_LOT/lotId`.
- 에러 코드(스펙 13장 그대로, `ErrorCode` enum과 OpenAPI `ErrorResponse.code` 일치): `COUPON_POLICY_INVALID`(400), `COUPON_POLICY_NOT_FOUND`(404), `COUPON_POLICY_ENDED`(409), `COUPON_SOLD_OUT`(409), `COUPON_ALREADY_ISSUED`(409), `COUPON_NOT_FOUND`(404), `COUPON_NOT_AVAILABLE`(409), `COUPON_NOT_APPLICABLE`(400), `COUPON_MIN_AMOUNT_NOT_MET`(400), `POINT_INVALID_AMOUNT`(400), `POINT_EXCEEDS_LIMIT`(400), `POINT_INSUFFICIENT`(409), `REVIEW_INVALID`(400), `REVIEW_NOT_ELIGIBLE`(409), `REVIEW_ALREADY_WRITTEN`(409), `REVIEW_NOT_FOUND`(404). 좋아요는 `PRODUCT_NOT_FOUND`, `expectedTotalAmount` 불일치는 `ORDER_PRICE_CHANGED` 재사용.
- 멱등성: `POST`(정책 생성·쿠폰 발급·후기 작성·주문 생성)는 `IdempotencyProperties.paths`에 추가해 C2 필터를 탄다. `PATCH`/`PUT`/`DELETE`는 멱등(이미 목표 상태면 200/204). `POST /api/v1/orders/quote`는 상태를 바꾸지 않으므로 멱등 키 없음.
- SDD: `OpenApiContractTest`는 스펙과 구현의 (method, path) 집합이 **같아야** 통과하므로, Task 1은 경로를 추가하지 않는 공통 변경(버전·태그·에러 enum·기존 스키마 확장)만 하고 **각 Task의 Step 1이 자기 경로를 `docs/api/openapi.yaml`에 먼저 추가**한다. `OpenApiContractTest`, `ErrorCodeContractTest`, `ArchitectureTest`가 매 커밋에서 통과한다. 응답 `ApiResponse`/`ErrorResponse`/`PageResponse`, 일시 `LocalDateTime`(KST), 목록 `?page&size` 기본 20 최대 100.

## Review Focus

1. **같은 쿠폰 ID를 두 항목(또는 상품 쿠폰과 장바구니 쿠폰 자리)에 중복 지정한 주문 요청**: 조건부 UPDATE가 첫 번째만 성공해 두 번째가 `COUPON_NOT_AVAILABLE`로 보이면 안 되고, 검증 단계에서 400 `ORDER_INVALID`로 거절해야 한다. → Task 5 `같은_쿠폰_ID를_두_번_지정하면_ORDER_INVALID이고_쿠폰은_AVAILABLE_그대로다`.
2. **장바구니 쿠폰 대상 금액이 0인 주문**(상품 쿠폰이 전액 할인): 장바구니 쿠폰은 할인 0이 아니라 `COUPON_MIN_AMOUNT_NOT_MET`(최소 금액이 있을 때) 또는 `COUPON_NOT_APPLICABLE`(대상 금액 0)이어야 하고, 포인트도 쓸 수 없다. → Task 4 `쿠폰_적용_후_금액이_0이면_장바구니_쿠폰과_포인트를_거절한다`.
3. **`paidAmount`가 3,000원보다 작은 항목의 구매자 취소로 무료배송이 깨질 때**: 차감은 `paidAmount + shippingFeeRefund`까지만이고 포인트 되돌림은 배분액 전액이어야 한다(스펙 6장 끝). → Task 4 `paidAmount가_3000보다_작으면_차감은_현금_환불까지만이고_포인트는_전액_돌아온다`.
4. **판매자가 남의 상품을 대상으로 한 `PRODUCT` 쿠폰 정책을 만들려는 요청**: 정책은 저장되지 않고 400 `COUPON_POLICY_INVALID`여야 한다(자기 돈만 쓴다는 규칙). → Task 2 `판매자가_남의_상품을_대상으로_하면_COUPON_POLICY_INVALID`.
5. **삭제된(`status = DELETED`) 후기의 상품 후기 목록·내 후기 목록·답글 PATCH**: 목록에서 빠지고 답글·수정은 404 `REVIEW_NOT_FOUND`이며, `review_count`는 삭제 시점에 1 줄어든 뒤 다시 바뀌지 않아야 한다. → Task 10 `삭제한_후기는_목록에서_빠지고_수정_답글은_REVIEW_NOT_FOUND이며_집계는_한_번만_준다`.

## 계획자 판단(스펙 15장 "빌더에게 맡기는 것"과 스펙이 비워 둔 것)

- **쿠폰 할인 계산 위치**: order 도메인은 benefit 도메인을 import할 수 없으므로, 쿠폰 정책의 할인 조건을 order 도메인 값 객체 `CouponTerms`로 옮겨 `DiscountAllocator`가 계산한다. benefit은 "본인 소유·`AVAILABLE`·만료 전"만 판정하고 "대상 일치·최소 금액"은 `DiscountAllocator`가 판정한다.
- **주문 생성에서 orderId가 아직 없는 문제**: 원장 `USE`와 `coupon.used_order_id`에는 orderId가 필요하지만 주문 행은 재고 차감 뒤에 INSERT된다(C2 Task 7의 `clearAutomatically` 주의). 그래서 `BenefitApplier`를 두 단계로 나눈다: `reserve`(member_point 락 → 쿠폰 조건부 UPDATE `AVAILABLE → USED`, `used_order_id`는 아직 NULL → 쿠폰 조건·잔액 반환)와 `commit`(주문 저장 뒤 `used_order_id`·`used_at` 기록, 포인트 FIFO 차감, 원장 `USE`). 둘 다 `OrderService.place`의 한 트랜잭션 안이라 실패하면 함께 롤백된다. 락 순서는 스펙대로 `member_point → coupon → sku`가 된다.
- **되돌림 호출 순서**: `finishCancel`·`expire`·`finishApproval(REJECT)`에서 `BenefitReverter`를 `stockManager.restore` **앞에** 부른다(`orders → member_point → coupon → sku`).
- **항목 단위 포인트 되돌림의 기록**: 같은 `USE`의 로트 사용분을 항목마다 조금씩 되감아야 하므로 `point_lot_usage`에 `reverted_amount` 컬럼을 둔다(스펙 10장 컬럼 세부는 빌더 몫). 되감기는 usage를 id 역순으로 돌며 `amount − reverted_amount`만큼 되돌린다.
- **요청의 항목 식별자**: 스펙 7-1의 `productCoupons[{orderLine, couponId}]`에서 `orderLine`은 **`skuId`** 다(C2가 같은 SKU를 한 항목으로 합치므로 SKU가 곧 항목이다).
- **배분 "마지막 항목"**: `Order.create`의 항목 생성 순서 = 판매자 ID 오름차순 → SKU ID 오름차순. `DiscountAllocator`도 같은 순서로 정렬해 나머지를 마지막 항목에 얹는다.
- **0원 주문 승인**: `OrderService.place`에서 `@Transactional`을 떼고 `TransactionRunner`로 트랜잭션을 연 뒤, 커밋 후 `totalAmount == 0`이면 `OrderPaymentService.approveWithoutPg(orderId)`를 부른다. `Payment.approveWithoutPg`는 `READY`(금액 0)에서 `paymentKey` 없이 `APPROVED`로 간다. 승인 뒤 처리는 `finishApproval`의 `APPROVE` 분기를 private 메서드로 빼서 재사용한다. 0원 주문의 항목 취소는 `refundAmount`가 항상 0이므로 C2의 "환불 0원이면 PG 생략" 경로를 그대로 탄다(새 분기 없음, 테스트로 고정).
- **후기 작성 기한 설정 키**: review 모듈이 benefit 설정을 읽지 않도록 `kairos.review.write-deadline: 90d`(`ReviewProperties`)로 둔다. 적립 금액(100/500)은 benefit이 `kairos.benefit.review-reward-text/photo`로 가진다.
- **후기 작성자 마스킹**: 회원 `name`의 첫 글자 + `**`(예: `김**`). 이메일은 쓰지 않는다. member 모듈에 `MemberQueryService.findNames(memberIds): Map<Long, String>`를 추가한다.
- **좋아요 upsert**: `INSERT … ON DUPLICATE KEY UPDATE liked = VALUES(liked)`(MySQL) 한 문장으로 영향 행 수를 본다(INSERT 1, 0→1 변경 2, 변경 없음 0). 취소는 `UPDATE … SET liked = 0 WHERE … AND liked = 1`. 변경된 경우에만 `product.like_count ± 1`. 엔티티 `ProductLikeEntity`는 조회(내 좋아요 목록)에만 쓰고 쓰기는 native `@Modifying` 쿼리다(이 upsert는 `modified_at`을 갱신하지 않는다 — 주석으로 남긴다).
- **상품 목록의 `liked`**: 로그인 선택 엔드포인트. `SecurityContextHolder`에 `LoginMember`가 있으면 그 회원의 좋아요를 조회해 채우고, 없으면 `null`.
- **쿠폰 목록(`GET /coupons/policies?productId=`)**: 장바구니 쿠폰 + `ALL_PRODUCTS` + 그 상품의 `PRODUCT` + 그 상품 판매자의 `SELLER` 정책 중 `ACTIVE`·기간 안·수량 미소진. `productId`가 없으면 장바구니·`ALL_PRODUCTS`만. 응답에 `claimed`(내가 이미 받았는지).
- **`POST /orders/quote`**: `place`와 같은 계산을 `BenefitApplier.quote`(락·UPDATE 없음)로 한 뒤 저장하지 않고 돌려준다. `maxUsablePoints`를 함께 준다.
- **ADR 0004** 본문: 맥락(주문 생성이 order·catalog·benefit을 한 트랜잭션에서 바꾼다), 결정(ADR 0003의 연장, 락 순서 두 가지, benefit 되돌림은 재고 복구보다 먼저, 조건부 UPDATE 원칙, 0원 주문은 PG 없이 승인 단계 재사용), 결과(Saga는 Phase 4, 크래시 시 15분 만료 작업이 되돌림).
- 화면(HTML 시안)과 정산 집계(C4)는 이 계획 밖이다.

## 스펙과의 차이 (실행 전 확인)

- 스펙 11장 "`openapi.yaml` 먼저"는 Task 1(공통 스키마·에러·버전)과 각 Task Step 1(경로)로 나눠 지킨다. `OpenApiContractTest`가 스펙·구현 경로 집합의 일치를 요구해 경로를 한꺼번에 먼저 넣을 수 없기 때문이다.
- 스펙 7-1의 `productCoupons[{orderLine, couponId}]`에서 `orderLine`은 `skuId`다.
- 스펙 10장 `point_lot_usage`에 `reverted_amount`를 추가했다(항목별 부분 되돌림을 같은 `USE`의 usages에 누적하기 위해).
- 스펙 15장의 후기 기한 설정 키는 `kairos.benefit.*`가 아니라 `kairos.review.write-deadline`이다(review 모듈이 benefit 설정을 읽지 않게).
- 스펙 4-2 "`DiscountAllocator`는 order 도메인"을 지키기 위해 쿠폰 할인 조건은 order 도메인 값 객체 `CouponTerms`로 번역해 넘긴다. "대상 일치·최소 금액" 판정은 benefit이 아니라 `DiscountAllocator`가 한다.
- 스펙 7-1의 "benefit이 쿠폰을 `USED`로, 포인트를 FIFO로 차감"은 orderId가 저장 뒤에 생기므로 `reserve`(저장 전, 쿠폰 `USED`·잔액 락)와 `commit`(저장 뒤, `used_order_id`·포인트 차감·원장)으로 나눴다. 같은 트랜잭션이라 스펙의 "어느 하나라도 실패하면 전부 롤백"은 그대로다.
- 좋아요 upsert(`INSERT … ON DUPLICATE KEY UPDATE`)는 바뀌지 않은 행의 `modified_at`을 갱신하지 않는다. `BaseEntity` 감사 컬럼의 의미를 약간 느슨하게 쓴 것이며 주석으로 남긴다.
