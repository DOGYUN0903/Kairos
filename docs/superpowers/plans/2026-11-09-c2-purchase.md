# C2 구매 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** C1 상품을 실제로 산다. 장바구니 → 다중 판매자 주문(결제 대기, 재고 차감) → PG 승인(Mock/토스 테스트) → 항목 취소·부분 환불 → 배송 상태 → 구매 확정까지를, 돈과 재고가 어긋나지 않게 구현한다.

**Architecture:** Phase 1 프로토타입 `order`·`payment` 모듈을 **삭제하고 새로 짠다**(태그 `v0-hotdeal-prototype`에 보존). 새 모듈 `cart`를 추가한다. 주문 생성·승인 확정·취소 확정은 `order`가 오케스트레이션하며 한 DB 트랜잭션에서 `catalog` 재고·판매량과 `payment` 상태를 함께 바꾼다(ADR 0003, "애그리거트당 한 트랜잭션"의 예외). **PG·택배 조회 호출은 트랜잭션 밖**에서 하고, 결과가 불확실하면 `IN_PROGRESS`/`UNKNOWN`/`CANCEL_REQUESTED`로 남겨 정리 작업이 PG 조회로 맞춘다. 환불액 계산은 도메인 함수 `RefundCalculator` 한 곳에서만 한다. `Idempotency-Key`는 `common`의 서블릿 필터가 처리한다.

**Tech Stack:** Kotlin 2.3.21, Spring Boot 4.1.2(RestClient, `@Scheduled`, `TransactionTemplate`), JDK 21, MySQL 8.4, Flyway, QueryDSL 7.7, JUnit5, Testcontainers, ArchUnit, `MockRestServiceServer`(토스·스마트택배 클라이언트 테스트).

**Spec:** `docs/superpowers/specs/2026-11-09-c2-purchase-design.md`(실행자는 반드시 함께 읽는다. 특히 5장 환불 규칙과 예시, 7장 승인 흐름, 8장 멱등성, 14장 정합성 테스트). 상위: `docs/superpowers/specs/2026-11-09-commerce-roadmap-design.md`. C1 스냅샷 인수 조건: `docs/superpowers/specs/2026-11-09-c1-seller-catalog-design.md` 13장.

## Global Constraints

- 루트 패키지 `com.dogyun.kairos`. 모듈 `cart`, `order`, `payment`(새로 작성), 계층 `presentation/ application/ domain/ infrastructure/`, 의존 방향 `presentation → application → domain ← infrastructure`. `domain`은 순수 Kotlin(`org.springframework..`, `jakarta.persistence..`, `tools.jackson..`, `com.fasterxml..` 금지). `ArchitectureTest` 규칙을 완화하지 않는다. `ArchitectureRules.modules`에 `cart`를 추가한다.
- 다른 모듈 호출: 호출하는 쪽 `application`에 인터페이스, 자기 `infrastructure`에서 상대 `application` 서비스를 호출해 구현. 모듈 간 DTO에 도메인 타입 노출 금지. order → catalog(`SkuQueryService`, `SkuStockService`), order → seller(`SellerQueryService`), order → payment(`PaymentService`, `PgClient`), order → cart(`CartService`), cart → catalog(`SkuQueryService`).
- JPA 엔티티는 `BaseEntity` 상속 + `@SQLRestriction("status = 'ACTIVE'")`, 소프트 딜리트만, 애그리거트 안 연관만(`LAZY`, `@ManyToOne` 단방향). 도메인 상태 컬럼명 `order_status`, `seller_order_status`, `order_item_status`, `payment_status`. **예외**: `idempotency_key` 테이블은 JPA 엔티티 없이 `JdbcTemplate`으로만 다룬다(필터 안에서 트랜잭션과 무관하게 써야 하므로).
- Flyway 새 버전만: `V12__drop_phase1_order_payment.sql`, `V13__idempotency_key.sql`, `V14__cart.sql`, `V15__payment.sql`, `V16__order.sql`. 앞 Task의 파일을 고치지 않는다. 인덱스는 PK/UNIQUE만(`orders.order_no`, `payment.payment_key`, `idempotency_key(member_id, idem_key)`).
- 금액은 원 단위 `Long`. 설정값(모두 `kairos.order.*`, `kairos.payment.*`, `kairos.delivery.*`, `kairos.idempotency.*`, `kairos.jobs.*`): 무료배송 기준 **50,000**, 기본 배송비 **3,000**, 결제 대기 **15분**, 자동 구매 확정 **7일**, 멱등 키 보관 **24시간**, `IN_PROGRESS` 정체 판정 5분, `CANCEL_REQUESTED` 정체 판정 1분. 키·비밀값(`TOSS_SECRET_KEY`, `SWEETTRACKER_API_KEY`)은 `.env`로만 주입하고 `.env.example`에 추가한다.
- 상태(스펙 9장): 주문 `PENDING_PAYMENT → PAID → COMPLETED | CANCELED`; 판매자 주문 `PENDING_PAYMENT → PAID → SHIPPING → DELIVERED → CONFIRMED | CANCELED`(결제 전 상태는 계획자 추가, 아래 "계획자 판단"); 주문 항목 `ORDERED, CANCEL_REQUESTED, CANCELED`; 결제 `READY, IN_PROGRESS, APPROVED, PARTIAL_CANCELED, CANCELED, UNKNOWN, FAILED`. 허용되지 않는 전이는 409 `ORDER_INVALID_STATE_TRANSITION` / `SELLER_ORDER_INVALID_STATE_TRANSITION` / `PAYMENT_INVALID_STATE_TRANSITION`. PATCH(배송 시작·완료·구매 확정)는 이미 목표 상태면 200.
- 멱등성(스펙 8장): `POST /api/v1/orders`, `POST /api/v1/payments/confirm`, 취소 POST 세 개는 `Idempotency-Key` 헤더 필수(없으면 400 `IDEMPOTENCY_KEY_REQUIRED`). 같은 회원·같은 키·같은 본문 해시 → 저장된 응답 재전송, 다른 본문 → 422 `IDEMPOTENCY_KEY_REUSED`, 처리 중 → 409 `IDEMPOTENCY_IN_PROGRESS`. 처리 중 행이 60초(`kairos.idempotency.in-progress-timeout`)를 넘기면 정체로 보고 같은 해시면 다시 실행한다. 5xx 응답은 저장하지 않는다(재시도 가능, `release`는 `finally`에서). `payment.payment_key` UNIQUE가 마지막 방어선. `idempotency_key` 테이블은 JPA 엔티티 없이 다루는 `BaseEntity` 규칙의 예외다(사용자 승인).
- **주문 행 락(사용자 결정, 2026-11-10)**: 주문 상태를 바꾸는 모든 트랜잭션(승인 tx1·tx2, 취소 tx1·tx2, 배송 시작·완료·구매 확정, 만료, 대사)은 먼저 `OrderRepository.findByIdForUpdate` / `findByOrderNoForUpdate`(`SELECT … FOR UPDATE`)로 주문 행을 잠근다. tx2는 다시 읽은 현재 상태를 재확인하고(결제 `IN_PROGRESS`/`UNKNOWN`, 항목 `CANCEL_REQUESTED`, 판매자 주문 `PAID`) 아니면 아무것도 하지 않는다. 이 락은 Phase 1 "재고 락 금지"와 별개다(ADR 0003에 기록). `Payment.start`는 `READY`에서만 허용한다(`FAILED` 재시도 없음).
- 재고(스펙 6장): 주문 생성 시 SKU ID 오름차순으로 `UPDATE sku SET stock = stock - ? WHERE id = ? AND stock >= ?`; 한 건이라도 0행이면 409 `STOCK_SOLD_OUT`으로 전부 롤백. 취소·만료 시 `stock + ?`(DISCONTINUED여도). 판매량은 결제 승인 시 `+`, 결제 후 취소 시 `-`.
- SDD: 각 Task 첫 단계에서 `docs/api/openapi.yaml`을 먼저 고친다. `OpenApiContractTest`, `ErrorCodeContractTest`, `ArchitectureTest`가 매 커밋에서 통과한다. 응답 `ApiResponse`/`ErrorResponse`/`PageResponse`, 일시는 오프셋 없는 `LocalDateTime`(KST), 목록 `?page&size` 기본 20 최대 100.
- `deal` 모듈은 손대지 않는다(컴파일·테스트 유지). `perf/`, `monitoring/`, `compose.perf.yaml`은 Phase 1 측정 산출물로 그대로 둔다(C6에서 재작업).
- Lombok 금지, Mock 라이브러리 금지(애플리케이션 서비스 테스트는 인메모리 Fake; HTTP 클라이언트는 `MockRestServiceServer`). 테스트 이름은 한국어. 스케줄러는 테스트에서 끄고(`kairos.jobs.enabled=false`) 작업 메서드를 직접 호출한다.

## Review Focus

1. **주문 요청에 같은 SKU가 두 번 들어온 경우**: 수량을 합쳐 항목 하나로 만들어야 한다(재고 차감도 합산 수량 1회). → Task 7 `같은_SKU가_두_번_오면_수량을_합쳐_한_항목으로_만든다`.
2. **환불액이 0이 되는 취소**(예: 2,000원 항목 취소로 무료배송이 깨짐): PG를 호출하지 않고 바로 `CANCELED`, 환불 0, 회수금 2,000이어야 한다. → Task 5 `차감이_환불액을_넘지_않아_환불_0원이_된다`, Task 10 `환불_0원_취소는_PG를_호출하지_않고_바로_확정된다`.
3. **`CANCEL_REQUESTED` 항목이 있는 판매자 주문의 배송 시작**: PG 결과가 불확실한 항목을 배송하면 안 되므로 409. → Task 11 `취소_확인_중인_항목이_있으면_배송_시작은_409다`.
4. **남의 주문번호로 결제 승인 요청**: 존재를 드러내지 않고 404 `ORDER_NOT_FOUND`, PG 호출 없음. → Task 8 `남의_주문번호_승인은_404이고_PG를_호출하지_않는다`.
5. **일부 판매자 주문이 취소된 주문의 자동 확정**: 남은 판매자 주문이 모두 `CONFIRMED`면 주문이 `COMPLETED`가 되어야 하고, `CANCELED`·`CONFIRMED` 판매자 주문은 자동 확정이 건드리지 않아야 한다. → Task 12 `취소된_판매자_주문이_있어도_나머지가_확정되면_주문은_COMPLETED다`.

## 계획자 판단(스펙 15장 "빌더에게 맡기는 것"과 스펙이 비워 둔 것)

- **기존 order·payment 코드와 테스트는 삭제한다**(`OrderApiTest`, `OrderMetricsApiTest`, `OrderServiceTest`, `OrderTest`, `MicrometerOrderMetricsTest`, `PaymentServiceTest`, `MockPgClientTest`, `PaymentRepositoryImplTest`, `MicrometerPaymentMetricsTest`). Phase 1 테이블 `orders`·`payment`는 `V12`에서 DROP하고 같은 이름으로 다시 만든다(프로토타입 데이터는 보존하지 않는다). Phase 1 메트릭(`kairos.order.placed`, `kairos.deal.sold`, `kairos.payment.duration`)은 사라지며 Grafana 대시보드는 C6까지 그대로 둔다.
- **판매자 주문에도 `PENDING_PAYMENT` 상태를 둔다.** 스펙 9장은 `PAID`부터 적지만 판매자 주문은 주문 생성 시 금액·배송비와 함께 만들어져야 하므로 결제 전 상태가 필요하다. 결제 전 만료·실패 시 `CANCELED`.
- **주문번호 `orderNo`**: `"K" + yyyyMMddHHmmss + 영대문자·숫자 6자`(21자, UNIQUE). 토스 결제창의 `orderId`로 쓰고 사용자에게 보여 준다. 결제 승인 API는 토스 리다이렉트와 같은 입력(`orderNo`, `paymentKey`, `amount`)을 받는 `POST /api/v1/payments/confirm`이다(컨트롤러는 order 모듈).
- **결제 전 주문의 사용자 취소 API는 두지 않는다**(15분 만료로 정리). `PENDING_PAYMENT` 주문의 항목 취소는 409 `ORDER_INVALID_STATE_TRANSITION`.
- **승인 흐름의 트랜잭션 분할**: tx1(주문 행 락 → **결제 상태 먼저 확인**: `APPROVED`+같은 키 → PG 없이 200, `IN_PROGRESS`+같은 키 → 409 `PAYMENT_IN_PROGRESS`, `UNKNOWN`+같은 키 → 200 `UNKNOWN`; 그 다음 주문 상태·금액 검증 → 결제 `READY → IN_PROGRESS` + paymentKey 저장) → PG 승인(트랜잭션 밖) → tx2(주문 행 락, 결제가 아직 `IN_PROGRESS`/`UNKNOWN`인지 재확인 후 반영). PG 결과 해석(승인·대사 공통): `Done`이고 `status == DONE`이고 금액 일치 → 승인; `status`가 `ABORTED`/`EXPIRED`/`CANCELED`이거나 `Failed` → 실패; `DONE`인데 금액 불일치 → PG 전액 취소(void) 후 실패; `OTHER`/`Unknown` → 보류. 승인: 주문 `PAID`, 판매량 `+`, 장바구니에서 해당 SKU 제거(200); 실패: 결제 `FAILED`, 주문 `CANCELED`, 재고 복구(402 `PAYMENT_REJECTED`); 보류: 결제 `UNKNOWN`(200, `paymentStatus: UNKNOWN`, 클라이언트는 주문 상세를 폴링). tx2에서 주문이 이미 닫혀 있으면(만료가 먼저) tx 밖에서 PG 전액 취소를 호출하고 `Payment.voidAfterApproval`(`IN_PROGRESS`/`UNKNOWN` → `CANCELED`, `refundedAmount = amount`)로 기록한다.
- **같은 paymentKey 재승인**: 다른 주문이면 409 `PAYMENT_KEY_DUPLICATED`; 같은 주문은 위 tx1 규칙(멱등).
- **취소 흐름**: tx1(주문 행 락, 항목 `ORDERED → CANCEL_REQUESTED`, `RefundPlan` 계산·저장) → PG 부분 취소(환불액 0이면 생략, `cancelReason = "orderItem:{itemId}"`, 멱등 키 `refund-{itemId}`) → tx2(주문 행 락, 항목이 아직 `CANCEL_REQUESTED`인지 재확인 → `CANCELED` 확정, 결제 누적 환불, 재고 복구, 판매량 `-`, 판매자 주문·주문 상태 갱신). PG `Failed`(확정 실패)면 항목을 `ORDERED`로 되돌리고 409 `PAYMENT_CANCEL_FAILED`. `Unknown`이면 `CANCEL_REQUESTED`로 두고 정리 작업이 PG 조회의 `cancels[].reason`으로 확인한다(없으면 같은 멱등 키로 재시도). 같은 항목 재요청: `CANCEL_REQUESTED`/`CANCELED`면 현재 상태를 200으로 돌려준다.
- **환불 규칙 구현**(스펙 5장): `RefundPlan(itemAmount, shippingFeeRefund, shippingFeeDeducted, refundAmount)`. `shippingFeeRefund` = 이 취소로 판매자 주문의 남은 항목이 0이 되고 그 배송비를 구매자가 냈으면 그 배송비. `shippingFeeDeducted` = 구매자 취소이고 주문이 무료배송이었고 취소 후 남은 상품 금액이 `0 < 남은 금액 < 기준`이고 아직 차감한 적 없으면 `min(기본 배송비, itemAmount + shippingFeeRefund)`. 판매자·관리자 취소는 차감 0. **남은 상품 금액이 0이 되는 마지막 취소**(스펙 5장, 2026-11-10)는 차감하지 않고 `shippingFeeReturned = order.shippingFeeRecovered`(앞서 차감한 금액)를 환불에 더하며 `shipping_fee_recovered`를 0으로 되돌린다. `refundAmount = itemAmount + shippingFeeRefund − shippingFeeDeducted + shippingFeeReturned`. 차감액은 `orders.shipping_fee_recovered`에 누적한다(플랫폼 회수금). 불변식 검사에 쓰는 `Order.remainingBuyerShippingFee` = 아직 `CANCELED`가 아닌 판매자 주문 중 `payer == BUYER`인 배송비 합.
- **장바구니**: 회원당 `Cart` 애그리거트(= `cart_item` 행 모음, 가격 저장 안 함). 담기는 `AVAILABLE` SKU만(아니면 409 `SKU_NOT_ORDERABLE`), 수량 1~999. 담은 뒤 품절·중지·단종·종료된 항목은 `availability`로 표시만 한다. `(member_id, sku_id)` UNIQUE는 소프트 딜리트와 충돌하므로 두지 않고 도메인이 합친다.
- **주문 가능 판정**(catalog `SkuAvailability`): SKU `DISCONTINUED` → `DISCONTINUED`; 상품 `ENDED` → `ENDED`; 상품이 `ON_SALE`이 아니거나 SKU `onSale=false` → `PAUSED`; 재고 0 → `SOLD_OUT`; 그 외 `AVAILABLE`. 판매자 정지 여부는 C1의 노출 조건(검색)에서만 걸고 여기서는 보지 않는다(정지된 판매자의 판매자 주문은 그 판매자가 처리할 수 없을 뿐이다).
- **Mock PG 동작**은 paymentKey 접두사로 고른다: `fail-` → `Failed`, `unknown-` → PG에는 승인을 기록하되 `Unknown` 응답(응답 유실 재현), `lost-` → 기록 없이 `Unknown`, `cancelunknown-` → 승인은 `Done`, 취소는 기록 후 `Unknown`, `cancellost-` → 취소를 기록하지 않고 `Unknown`, `cancelfail-` → 취소 `Failed`, 그 외 → `Done`. 취소 동작도 **paymentKey 접두사**로만 고른다(사유 문자열은 보지 않는다). Mock 택배 조회는 송장번호가 `-D`로 끝나면 `DELIVERED`.
- **정리 작업**은 `@Scheduled(fixedDelayString)` 단일 인스턴스 전제(분산 락 없음, ALB 단계에서 재검토). 주기: 만료 60s, 결제·환불 대사 60s, 배송 조회 10m, 자동 확정 1h, 멱등 키 정리 1h. 각 대상은 건별 트랜잭션으로 처리해 한 건 실패가 나머지를 막지 않는다.
- **배송 시작 조건**: 판매자 주문 `PAID`이고 `CANCEL_REQUESTED` 항목이 없어야 한다. 같은 택배사·송장으로 다시 PATCH하면 200, 다른 송장이면 409.
- **ADR 0003**으로 "C2 주문 트랜잭션이 catalog 재고·판매량과 payment 상태를 함께 바꾸고 PG 호출은 밖에서 한다"를 남기고, ADR 0001은 대체(superseded)로 표시한다.

## 스펙과의 차이 (실행 전 확인)

- 스펙 9장 판매자 주문 상태에 `PENDING_PAYMENT`를 추가했다(결제 전 판매자 주문을 금액·배송비와 함께 만들어야 하므로).
- 스펙 13장 "결제 승인" 경로는 토스 리다이렉트 입력을 그대로 받는 `POST /api/v1/payments/confirm`(`orderNo`, `paymentKey`, `amount`)으로 두었다. 컨트롤러는 order 모듈이 가진다.
- 스펙 6장의 ADR은 재고만 말하지만 ADR 0003은 같은 트랜잭션에서 바뀌는 payment 상태와 판매량까지 함께 기록한다(같은 예외의 한 결정).
- 스펙 7장 "PG에서 이미 승인된 상태라면 즉시 결제 취소"는 승인 응답이 늦게 반영될 때(`finishApproval`이 `ORDER_ALREADY_CLOSED`)와 대사 작업에서 PG 조회가 `DONE`인데 주문이 닫혀 있을 때, 두 곳에서 PG 전액 취소로 구현한다.
- 스펙 5장에 2026-11-10 사용자 결정(무료배송 주문 전부 취소 시 차감액 반환)을 반영해 스펙 본문을 한 줄 추가했다. 그 외 스펙은 고치지 않았다.
- 주문 상태를 바꾸는 모든 트랜잭션이 주문 행을 `SELECT … FOR UPDATE`로 잠그는 것은 사용자 결정(2026-11-10)이며 ADR 0003에 기록한다. Phase 1 재고 락 금지와는 별개다.
- 스펙 5장 "결과가 불확실하면 그대로 두고 정리 작업이 맞춘다"에 더해, PG가 **확정 실패**를 돌려준 취소는 항목을 `ORDERED`로 되돌리고 409 `PAYMENT_CANCEL_FAILED`로 응답한다(불확실과 실패를 구분).
