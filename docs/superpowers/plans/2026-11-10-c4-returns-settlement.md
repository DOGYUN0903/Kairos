# C4 반품·정산 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** C2 구매·C3 혜택 위에 항목 단위 반품(요청 → 승인/거절/철회/자동 승인 → 수거 확인 → 2-트랜잭션 환불)과 판매자 주간 정산(생성 시점 스냅샷·불변, 판매자별 한 트랜잭션, 재실행·동시 실행·중간 실패에 결과가 같은 생성)을 얹되, 돈(환불액·배송비 회수·되돌림·정산 라인)이 원 단위로 재현되게 구현한다.

**Architecture:** 반품은 `order` 모듈 안에 둔다. `OrderItem`이 `ReturnRequest`를 1:1로 가지며 모든 상태 변경은 주문 행 락 아래에서 일어나고, 환불은 `OrderCancelService`와 같은 tx1 → PG → tx2 구조의 `OrderReturnService`가 한다. 환불 금액은 order 도메인 순수 함수 `ReturnRefundCalculator`가, C2 취소와의 발송 배송비 이중 회수 방지는 `RefundCalculator` 조건 확장이 맡는다. 정산은 새 모듈 `settlement`로, 포트 `ConfirmedSellerOrderReader`(→ `order.application`)와 `SettlementSellerReader`(→ `seller.application`)로 읽기만 하고 주문 테이블에 쓰지 않는다. 정산 금액은 settlement 도메인 순수 함수 `SettlementCalculator` 한 곳에서 저장 스냅샷만으로 계산하고, 생성은 판매자별 한 트랜잭션 + `UNIQUE(seller_id, period_start)` + `settlement_line.seller_order_id UNIQUE` + `settlement_run.period_start UNIQUE`로 멱등하다. 반품 환불 트랜잭션·락 순서와 정산 불변성은 **ADR 0005**에 남긴다.

**Tech Stack:** Kotlin 2.3, Spring Boot 4.1(`TransactionTemplate`, `@Scheduled(cron)`), JDK 21, MySQL 8.4, Flyway, QueryDSL 7.7, JUnit5, Testcontainers, ArchUnit. 새 의존성 없음. Spring Batch 금지(스펙 §8-9).

**Spec:** `docs/superpowers/specs/2026-11-10-c4-returns-settlement-design.md`(실행자는 반드시 함께 읽는다. 특히 §5 환불 금액 규칙과 §5-1 예시 A~D, §6 상태, §8-2 라인 정의, §8-3 생성·멱등, §8-7 정산 예시, §8-8 정확성 다섯 가지, §14 증명할 테스트). 상위: C2 스펙·계획(`2026-11-09-c2-purchase*.md`), C3 스펙·계획(`2026-11-10-c3-benefits-reviews*.md`), ADR 0003·0004.

## Global Constraints

- 루트 패키지 `com.dogyun.kairos`. 새 모듈 `settlement`(계층 `presentation/ application/ domain/ infrastructure/`). `ArchitectureRules.modules`에 `settlement`를 추가하고 규칙을 완화하지 않는다. `settlement`는 `order.domain`·`order.infrastructure`를 import하지 않고 `settlement.infrastructure`만 `order.application`·`seller.application`을 호출한다. `order`는 `settlement`를 모른다.
- 반품은 `order` 모듈 안(새 모듈 없음). `ReturnRequest`는 `Order` 애그리거트 안(`OrderItem.returnRequest`), 별도 Repository 없음. 반품 상태 변경·환불은 모두 `findByIdForUpdate(orderId)` 락 아래. 판매자·관리자 엔드포인트는 트랜잭션 밖에서 `findOrderIdBySellerOrderId`/`findOrderIdByReturnId`로 주문 ID를 찾고 안에서 잠근다. 정산 생성은 주문 행 락을 잡지 않는다(읽기만).
- 락 순서(ADR 0003/0004/0005): 반품 환불 tx2 `orders(FOR UPDATE) → member_point → coupon → sku → product`(benefit 되돌림 → `CHANGE_OF_MIND`면 재고 복구 → 판매량 감소). PG 부분 취소는 트랜잭션 밖, 현금 환불 0원 또는 `paymentKey` 없음이면 PG 호출 없이 tx2.
- Flyway 새 버전만: `V21__return_request.sql`, `V22__settlement.sql`. 인덱스는 PK/UNIQUE만: `return_request(order_item_id)`, `settlement(seller_id, period_start)`, `settlement_line(seller_order_id)`, `settlement_run(period_start)`, `settlement_adjustment(source_settlement_id)`(NULL 허용 UNIQUE). 도메인 상태 컬럼명 `return_status`, `settlement_status`, `adjustment_type`(조정 삭제는 `BaseEntity.status = DELETED` 소프트). 정산·라인은 **삭제·수정 없음**(생성 뒤 불변, 보정은 조정 행으로만).
- 금액은 원 단위 `Long`, 수수료율 bp(`Int`), 나눗셈은 수수료 한 곳 `floor(commissionBase × rateBp / 10_000)` **라인별 버림**. 모든 시각 KST `LocalDateTime`, 정산 기간은 `[periodStart 00:00:00, periodStart+7일 00:00:00)` 반열린 구간, `periodStart`는 월요일 `LocalDate`, `periodEnd = periodStart + 7`, `payoutDate = periodStart + 9`(수요일).
- 설정값: `kairos.order.return-window: 7d`, `kairos.order.return-auto-approve-after: 3d`, `kairos.order.return-shipping-fee: 3000`(회수 구간 `returnFee`·`sellerBorneFee`), 발송 구간 회수(`outboundFeeRecovered`)는 기존 `kairos.order.base-shipping-fee: 3000`; `kairos.settlement.late-confirm-lookback: 28d`, `kairos.settlement.start-date`(월요일, 운영 `2026-11-16`, 테스트 `2026-10-05`); `kairos.jobs.return-auto-approve-delay: 1h`, `kairos.jobs.settlement-generate-cron: "0 0 3 * * MON"`. `auto-confirm-after: 7d`·`auto-confirm-delay: 1h` 변경 없음. `return-window ≠ auto-confirm-after`면 기동 시 WARN 로그.
- 반품 규칙(숫자): `DELIVERED` 판매자 주문의 `ORDERED` 항목, `deliveredAt + return-window ≥ now`, 사유 `CHANGE_OF_MIND`(구매자 부담, `returnFee` 3,000 + 무료배송이고 주문에서 발송 구간 미회수면 `outboundFeeRecovered` 3,000)·`DEFECTIVE`/`WRONG_DELIVERY`(판매자 부담, `sellerBorneFee` 3,000, 판매자 주문이 비고 `BUYER` 배송비면 `shippingFeeRefund` = `shippingFee`). 구매자 부담 반품비는 현금 환불(`paidAmount`)까지만. `refundAmount = paidAmount − returnFee − outboundFeeRecovered + shippingFeeRefund`, PG 멱등 키 `refundKey(itemId, refundAmount)`, 사유 `"orderItem:$itemId"`(C2와 같음). 미응답 자동 승인 3일. 거절은 최종(관리자만 판매자 주문 `CONFIRMED` 전까지 재승인).
- 정산 규칙(숫자): 대상 `CONFIRMED` 판매자 주문, `confirmed_at ∈ [max(periodStart − lookback, startDate), periodEnd)`이고 아직 어느 `settlement_line`에도 없는 것. 라인 = 판매자 주문 1개. `sales = Σ ORDERED lineAmount`, `sellerCoupon = Σ ORDERED && issuer == SELLER productCouponDiscount`, `base = sales − sellerCoupon`, `commission = floor(base × 판매자 주문 commissionRateBp / 10000)`, `shippingOwed = shippingFee − shippingFeeRefund(완료 반품)`, `returnBorne = Σ 완료 반품 sellerBorneFee`, `line = sales − sellerCoupon − commission + shippingOwed − returnBorne`. 헤더 `total = Σ line + Σ 붙은 조정`, `payable = max(total, 0)`, 음수면 `CARRY_OVER` 조정(정산당 최대 1개) 생성. 판매자 순서 ID 오름차순, 라인 순서 판매자 주문 ID 오름차순.
- 에러 코드(스펙 §13 그대로, `ErrorCode` enum과 OpenAPI `ErrorResponse.code` 일치): `RETURN_INVALID`(400), `RETURN_NOT_FOUND`(404), `RETURN_NOT_ELIGIBLE`(409), `RETURN_WINDOW_EXPIRED`(409), `RETURN_ALREADY_REQUESTED`(409), `RETURN_INVALID_STATE_TRANSITION`(409), `SELLER_ORDER_HAS_OPEN_RETURN`(409), `SETTLEMENT_NOT_FOUND`(404), `SETTLEMENT_PERIOD_INVALID`(400), `SETTLEMENT_INVALID_STATE_TRANSITION`(409), `SETTLEMENT_ADJUSTMENT_INVALID`(400), `SETTLEMENT_ADJUSTMENT_APPLIED`(409). `PAYMENT_CANCEL_FAILED`, `ORDER_ITEM_NOT_CANCELABLE` 재사용.
- 멱등성: `POST` 반품 요청·정산 생성·조정 등록은 `IdempotencyProperties.paths`에 추가. `PATCH`/`DELETE`는 이미 목표 상태면 200/204.

## Review Focus

1. **같은 주문의 다른 판매자 주문 항목을 구매자가 취소하는 동안 어떤 항목은 `RETURN_REQUESTED`인 경우**: 열린 반품 항목은 '남은 항목'이라 마지막 취소 판정(`shippingFeeReturned`)이 일어나면 안 되고, 반품이 거절돼 `ORDERED`로 돌아와도 돈 불변식이 그대로여야 한다. → Task 3 `열린_반품_항목은_남은_항목으로_세어_다른_항목_마지막_취소에_차감_반환이_없다`, Task 5 `ReturnConsistencyApiTest`.
2. **`paidAmount`가 6,000원보다 작은 항목의 무료배송 변심 반품**(포인트·쿠폰으로 거의 다 낸 항목): 환불은 0 이상이어야 하고, `returnFee + outboundFeeRecovered`는 `paidAmount`까지만 받되 **발송 구간은 실제 받은 만큼만 회수한 것으로 기록**해 다음 반품에서 다시 이중 청구가 되지 않아야 한다. → Task 3 `paidAmount_4000_변심_무료배송은_환불_0_returnFee_3000_outbound_1000이다`.
3. **PG 실패로 `RETURN_REFUNDING → RETURN_APPROVED`로 되돌린 뒤 다시 수거 확인**: 되돌림이 `return_request`의 환불 계획 값(`refund_amount`, `outbound_fee_recovered` 등)을 0으로 지워야 두 번째 계산이 "이미 발송 구간을 회수했다"고 착각하지 않는다. → Task 4 `PG_실패_되돌림_뒤_다시_수거_확인하면_같은_환불액이다`.
4. **정산 생성 중 조정을 등록하는 관리자**: `created_at < periodEnd`인 조정만 붙고, 기간이 끝난 뒤 등록된 조정은 다음 정산으로 가야 하며, 생성 트랜잭션과 동시에 들어온 조정이 두 정산에 붙거나 어디에도 안 붙는 일이 없어야 한다. → Task 10 `생성과_동시에_등록한_조정은_정확히_한_정산에만_붙는다`.
5. **정지·탈퇴 판매자의 정산 조회**: 판매자 토큰으로 자기 정산은 보이고 남의 정산은 `SETTLEMENT_NOT_FOUND`이며, 정지 판매자의 정산도 생성·관리자 목록에 남아야 한다. → Task 11 `정지된_판매자도_확정_판매자_주문이_있으면_정산이_생기고_상세에_판매자_상태가_보인다`.

## 계획자 판단(스펙 §15 "빌더에게 맡기는 것"과 스펙이 비워 둔 것)

- **`ReturnRequest`는 `Order` 애그리거트 안**(`OrderItem.returnRequest: ReturnRequest?`). `OrderRepositoryImpl.save`가 `return_request` 행을 함께 upsert하고, `toDomain`이 항목에 붙인다. 목록·작업용 조회(`findReturnPage`, `findReturnRequestIdsRequestedBefore`, `findOrderIdByReturnId`)는 `OrderRepository`에 둔다(별도 Repository 없음).
- **`ReturnRefundCalculator`**는 `RefundCalculator`와 별도 `object`, 결과 `ReturnRefundPlan`. "발송 구간 회수한 적" 판정은 `Order.outboundFeeRecoveredEver = Σ item.shippingFeeDeducted + Σ returnRequest.outboundFeeRecovered(REFUNDING·COMPLETED)`이며 `RefundCalculator`의 `everDeducted == 0L` 조건을 이 값으로 바꾼다.
- **남은 항목 정의 변경**: `OrderItemStatus.isRemaining = ORDERED || isOpenReturn`(`RETURN_REQUESTED`, `RETURN_APPROVED`, `RETURN_REFUNDING`). `SellerOrder.remainingItemsAmount`·`remainingPaidAmount`·`Order.remainingItemsAmount`·`remainingPaidAmount`는 `isRemaining` 기준으로 바꾼다. `confirmedPaidAmount`(적립)와 정산 `sales`는 **`ORDERED`만**(열린 반품이 있으면 확정이 막히므로 차이가 생기지 않는다).
- **구매자 배송비 환불 반영**: `SellerOrder.buyerShippingFeeRefunded: Long = Σ returnRequest.shippingFeeRefund(COMPLETED)`. `Order.remainingBuyerShippingFee`는 `shippingFee − buyerShippingFeeRefunded`를 더한다.
- **`OrderReturnService`와 `OrderCancelService`의 공통부**는 추출하지 않는다(tx2의 마무리 순서는 같지만 갱신 필드·조건이 달라 공통화 이득이 작다). `refundKey`·`"orderItem:$itemId"` 사유는 그대로 재사용한다(PG 멱등 키 공간을 항목 ID가 나눈다).
- **대사 확장**: `OrderRepository.findCancelRequestedItems`를 `findItemsInStatusBefore(statuses: Set<OrderItemStatus>, before, afterItemId, limit)`로 넓히고, `PaymentReconciliationService.reconcileCancels`가 상태별로 `finishCancel`/`finishReturn`에 넘긴다.
- **`sweepByKeyset`·`TransactionRunner` 공용화**: 둘 다 `common`으로 올린다 — `common/application/KeysetSweep.kt`(`fun <T> sweepByKeyset(...)`, public)와 `common/application/TransactionRunner.kt`(인터페이스), 구현은 `common/infrastructure/TransactionRunnerImpl.kt`. order의 `KeysetSweep.kt`·`TransactionRunner.kt`·`TransactionRunnerImpl.kt`는 삭제하고 import만 바꾼다(`common`은 `ArchitectureRules.modules` 밖이라 모든 모듈이 import할 수 있다). **`common/infrastructure`에 두면 안 된다**: `ArchitectureRules.applicationNotOnPresentationInfrastructure`가 `..application..` → `..infrastructure..` 의존을 패키지 패턴으로 막으므로 `order.application`·`settlement.application`이 `common.infrastructure.TransactionRunner`를 import하면 `ArchitectureTest`가 깨진다(현재 application 계층은 `common.infrastructure`를 하나도 import하지 않는다). `common/application` 패키지는 새로 만든다.
- **포트 DTO는 항목 단위 원시값**: `ConfirmedSellerOrderReader`가 돌려주는 `ConfirmedSellerOrderSnapshot`은 집계값이 아니라 항목별 `lineAmount`·`productCouponDiscount`·`productCouponIssuer`·`ordered`·`sellerBorneFee`를 담고 계산은 `SettlementCalculator`가 한다(정산 규칙이 order에 새지 않게).
- **정산 생성 순서·`settlement_run`**: `SettlementGenerationService.generate(periodStart)`는 (1) 월요일·`periodEnd ≤ now`·`periodStart ≥ startDate`·**직전 기간(`periodStart − 7`, `≥ startDate`일 때)의 `settlement_run`이 있음**을 검사하고(아니면 `SETTLEMENT_PERIOD_INVALID`), (2) 이미 `settlement_run`이 있으면 기존 결과를 돌려주고, (3) 판매자별 트랜잭션을 돈 뒤 **실패한 판매자가 0명일 때만** 별도 트랜잭션으로 `settlement_run`을 INSERT한다. 스케줄 작업 `generateDue()`는 `startDate`부터 끝난 기간을 오래된 순으로 돌며 `settlement_run`이 없는 기간을 차례로 만들고, 한 기간이 실패(`failedSellerCount > 0`)하면 멈춘다. 직전 기간만 검사해도 귀납적으로 그 앞 기간이 모두 생성돼 있다.
- **판매자 트랜잭션 안 예외 처리**: `DataIntegrityViolationException`(UNIQUE 위반 = 동시 실행·재실행)은 "건너뜀"으로 세고, 그 밖의 `RuntimeException`은 로그 + "실패"로 센다. 둘 다 다음 판매자로 간다.

## 스펙과의 차이 (실행 전 확인)

- 스펙 §7 "`openapi.yaml` 먼저"는 Task 1(공통 스키마·에러·버전)과 각 Task Step 1(경로)로 나눠 지킨다(`OpenApiContractTest`가 경로 집합 일치를 요구하기 때문. C3와 같은 방식).
- 스펙 §5 "구매자 부담 반품비는 `paidAmount`까지만"에서 `paidAmount < 6,000`일 때 어느 구간부터 깎는지 스펙이 정하지 않았다. **`returnFee`를 먼저 채우고 남는 만큼만 `outboundFeeRecovered`로 기록**한다(발송 구간 회수 상한 3,000 판정이 `outboundFeeRecoveredEver`에 실제 회수액만 반영되게. 덜 회수한 발송 구간은 플랫폼 손실로 둔다는 스펙 원칙과 같다).
- 스펙 §6 "`RETURN_REQUESTED`/`RETURN_APPROVED` 항목은 남은 항목으로 센다"에 **`RETURN_REFUNDING`도 포함**한다(아직 환불 전이고 PG 실패 시 `RETURN_APPROVED`로 돌아온다). 돈 불변식의 "남은 항목"도 같은 정의다.
- 스펙 §8-3 "앞 기간이 비어 있으면 `SETTLEMENT_PERIOD_INVALID`"는 **직전 기간의 `settlement_run`만** 검사한다(귀납적으로 그 앞도 생성돼 있다).
- 스펙 §8-3 "실패 건은 로그만 남기고 다음 건으로"와 "`settlement_run`은 모두 끝난 뒤"를 합쳐, 판매자 트랜잭션 실패(UNIQUE 위반 제외)가 하나라도 있으면 `settlement_run`을 남기지 않는다(재실행이 남은 판매자를 채운다). `generateDue`는 그 기간에서 멈춘다.
- 스펙 §8-6 조정 삭제 응답·조정 조회 경로, §8 판매자·관리자 정산 경로는 스펙이 정하지 않아 계획자 판단 절의 경로로 고정했다.
- 스펙 §8-6 "`created_at < periodEnd`인 조정을 붙인다"는 **MANUAL에만** 적용하고, §8-5 `CARRY_OVER`는 `created_at`과 무관하게 다음 생성되는 정산에 붙인다(작업이 밀려 여러 기간을 한 번에 따라잡을 때 CARRY_OVER가 한 기간 건너뛰는 것을 막기 위해. Task 7 `attach` 참조).
- 스펙 §8-8 "동시 2회 실행"에서 둘 다 판매자 루프를 끝내면 `settlement_run` INSERT가 UNIQUE 위반이 되므로, 이 위반도 잡아 `alreadyGenerated`로 돌려준다(Task 9).
- 스펙 §15 `sweepByKeyset` 공용화는 `common/application`으로 옮기는 쪽을 택했고, 같은 이유로 order의 `TransactionRunner` 인터페이스도 `common/application`으로(구현 `TransactionRunnerImpl`만 `common/infrastructure`) 옮긴다(settlement가 order.application을 import할 수 없고, `common/infrastructure`에 두면 ArchUnit의 application → infrastructure 금지 규칙에 걸리므로). - 스펙 §14 "같은 입력으로 `SettlementCalculator`를 두 번 돌리면 같은 결과"와 "바이트 단위 비교"는 각각 단위 테스트(`==`)와 `settlementRows()` 덤프(`id`·`created_at`·`modified_at` 제외) 비교로 증명한다.
